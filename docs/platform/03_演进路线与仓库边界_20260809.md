# 演进路线与仓库边界（2026-08-09）

状态：**候选总路线，未批准实施**。它重排平台级顺序；
[plans/10](../plans/10_模型资产与呈现架构演进计划_20260809.md)降为资产/端点子计划，
不再代表整个平台从哪里开工。

## 一、代码放在哪里

### 1.1 本轮已经执行的文档边界（不等于批准平台实施）

- 在本仓新增`docs/platform/`作为上位愿景与跨仓架构孵化区；
- `src/physics_engine/`继续是无头、零必需依赖的Python科学计算内核；
- 本轮不在本仓建立Node workspace、renderer、Studio或重型adapter；
- 本轮不创建新仓、不提交、不推送、不迁移GCW、WII、WDS、FTS四个领域项目。

### 1.2 进入实现后的建议

平台代码宜使用一个独立monorepo，工作名`rtime-engineering-platform`，用户应用名
`RTime Engineering Studio`：

```text
rtime-engineering-platform（工作名，未创建）
├── engines/
│   └── physics-engine      目标态可保留历史迁入；首轮仍消费独立发布包
├── packages/
│   ├── core                 最小协议+artifact/compute/scene/timeline/workspace runtime
│   ├── design-system        自有原则、token、组件、图表/3D语义与主题
│   └── plugin-sdk           领域与adapter API
├── renderers/
│   ├── three                默认WebGL2实现，Three类型不外泄
│   └── webgl2               WDS/raw WebGL路线或专用高性能实现
├── plugins/
│   ├── fts                  薄集成插件，不复制FTS领域仓源码
│   ├── wii                  薄集成插件，不复制WII领域仓源码
│   ├── wds                  薄集成插件，不复制WDS领域仓源码
│   └── gcw                  薄集成插件，不复制GCW领域仓源码
├── adapters/
│   ├── physics-engine
│   ├── occt
│   ├── blender
│   ├── vtk
│   └── interchange
├── workers/
│   ├── local-runner
│   └── asset-compiler
└── apps/
    └── studio
```

第一批只建`packages/core`、`packages/design-system`最小token、`renderers/three`、
`apps/studio`和`plugins/{fts,wii}`两个真实插件；`plugin-sdk`先作为core内部模块，不建空包。
后续只在依赖、发布节奏或性能边界真实分化时，把core拆成protocol、engineering-model、
artifact/compute/scene/timeline/workspace等独立包。
`engines/physics-engine`是可裁决的目标位置，不表示本轮已经或应当直接移动当前仓。

### 1.3 为什么不塞进`physics-engine`

| 约束 | 塞入本仓的后果 | 建议边界 |
|---|---|---|
| `dependencies=[]` | Node/CAD/DCC/GPU依赖破坏单wheel基线 | 科学内核只暴露facet/API/adapter |
| Python域隔离 | Studio编排多个域会让基座反向import领域 | 平台runtime作包外编排者 |
| 发布节奏 | 浏览器库和UI迭代远快于数值内核 | 独立语义版本与兼容矩阵 |
| 性能预算 | 前端资产会污染import、wheel和full门 | 各仓有自己的体积/启动/验收预算 |
| 部署形态 | Web、桌面、worker、服务器不是一个Python包 | 共协议、多壳、可选adapter |

产品可以是一体的，源码和发布单元不必是一个巨型包。即使未来将`physics-engine`历史迁入
monorepo，它仍保持独立Python发布单元、零依赖门和公开镜像；GCW、WII、WDS、FTS仍不应
因此全部并入。统一的是语义、工作流和验收，不是所有依赖与发布节奏。

### 1.4 物理迁仓采用两阶段，不做普通文件移动

推荐先创建平台monorepo并通过已发布wheel/adapter消费`physics-engine`。M2与两个纵切只开放
迁仓评审；只有出现重复、真实的跨仓原子变更成本，并通过M2.5临时clone迁移演练后，才单独
批准把本仓完整历史导入`engines/physics-engine/`。如果版本化协议与wheel长期足够顺畅，
可以永久保持独立仓。旧远程、包名、import名、版本、wheelhouse和已发字节均保留。
完整前置、迁移波次、消费方影响和回滚见
[05 仓库迁移与相关项目改造方案](05_仓库迁移与相关项目改造方案_20260809.md)。

## 二、三个纵切先反证“通用”

纵切是贯穿阶段的**验收主线**，阶段是能力的建设顺序，两者不是两套相互竞争的排期。
VS-A在P1先做FTS/WII只读协议映射，P2接artifact/runtime，P3接SceneIndex/renderer，
P4才形成同一Studio壳的完整闭环；VS-B和VS-C按各自反证点进入相应阶段。不能在P1之前
一次性“做完VS-A”，也不能把P1—P4做成没有真实数据消费的横向空包。

### VS-A：FTS+WII，共用Studio壳但保持领域不同

先以**只读**方式接两种数据：

- FTS：加载冻结run/scene资产，显示仪器3D、波形/光谱和完整性；
- WII：加载冻结frontend JSON、模型manifest和刚体时间线，显示机器人/工位回放。

共同验证artifact store、workspace、SceneIndex、timeline和Three backend；各插件保留光学拓扑、
FK/IK、领域Widget和业务picking。之所以不只搬FTS，是防止把`route_ids`、
`signal_channel_ids`或`simulate/analyze/compare/fit`误冻成通用协议。

退出门：切换插件不重启；静态网格只上传一次；WII每帧只更新transform；离线静态部署可用；
旧前端和物理结果字节不变。

### VS-B：WDS，反证时间和renderer抽象

接冻结FramePacket与静/动态WebGL资源；要求timeline同时支持`exact`、`hold`与显式
`display_interpolated`，raw WebGL2作为独立backend，不复制WDS物理语义。

退出门：精确帧不被补造；预热后无每帧对象分配；稳定拓扑只更新必要buffer；context loss可
恢复；证据模式保持原判据。

### VS-C：GCW，反证CAD选择和长事务

接CAD显示资产、实体映射、中心线与覆盖层；把pointer/camera基础动作交给公共内核，
CAD raycast、面/样本选择、后端确认和中心线判据留在GCW插件。

退出门：选择command可取消/代际隔离；busy/resource lock无竞态；CAD源SHA变化时旧primitive
映射失败关闭；renderer替换不改变中心线结果。

三个纵切均通过后，才有资格声称公共Studio内核覆盖静态装配、刚体时间线、连续形变和CAD
事务四类不同问题。

## 三、平台阶段路线

### P0愿景、词汇和边界冻结

工作：审阅本目录；裁决平台/Studio工作名、仓库所有者；处理旧spec“前端栈不统一”的冲突；
固定VS-A/B/C输入与许可；建立平台自己的consumer registry；冻结首版产品原则、信息层级、
状态语义与设计token分层。

退出门：删除任何第三方工具后，自有对象、任务、结果和工作区仍能完整描述；没有代码先于
边界出生。

### P1跨语言最小协议

只蒸馏identity/revision、unit/frame/time、representation binding、artifact ref、job、
frame/result envelope和run引用。FTS/WII先做只读adapter，WDS作为反证审阅者。

退出门：两种不同领域数据能无损映射公共字段；未知扩展保留；错单位、错SHA、错版本必红；
既有产物指纹逐字节不变。

### P2headless runtime

实现project/world session、command/event、job状态机、cancel/resume、artifact store、插件发现和
本地worker；不先做漂亮UI。

退出门：一条命令完成“加载→运行/取消→发布→严格复读”；无网络、无GPU、无Blender成立；
作业不能由UI直接伪造complete。

### P3视觉运行时

实现SceneIndex、change set、资源生命周期、timeline、selection、dirty scheduler、质量档和
性能计数；先藏Three/WebGL2backend，再接WDS raw WebGL2反证。

退出门：renderer类型不泄漏；静/动态资源计数满足纵切门；换backend不改领域插件协议；
context loss可重建。

### P4Studio最小产品

实现项目树、检查器、参数草案、作业面板、3D/曲线/时间线/诊断Widget、split/stack、命令和
workspace迁移；从第一天使用design token，后续再做系统化视觉精修。

退出门：非开发使用者不改代码完成“打开→配置→运行→检查→比较→导出”；任何隐藏Widget
可恢复；view state不污染run；关键页面通过token、键盘、对比度和视觉回归门。

### P5模型/资产构建与外部适配器

按真实需要接OCCT的STEP→GLB、LOD/碰撞代理、Blender动画/渲染、VTK场、USD/Alembic或
URDF/SDF。具体门沿用research/14与plans/10。

退出门：adapter删除不影响平台核心；有损转换不冒充往返无损；工具版本、recipe、误差、
源/产物SHA完整入回执；冷/热构建可测且热命中零重建。

### P6硬件和部署

分别建立numeric、asset、render backend registry；增加Worker/WASM、本地服务、可选远程、
桌面壳和恢复机制。

退出门：CPU/WebGL2单机基线长期存在；数值GPU仍过spec/13三门槛；缓存不跨平台/后端误命中；
没有master不丢功能。

### P7插件生态、知识组件和产品化

建立版本化组件/领域包、SDK、示例、模板、许可和兼容矩阵；在P0—P4已经落下的设计系统上
完善品牌主题、排版、科学色表、动效、内容规范与不同任务的默认工作区。P7做体系化产品化，
不是第一次考虑美学与可访问性。

退出门：第三方能在不改核心的情况下增加一个组件、Provider和Widget；插件卸载失败关闭；
至少一次跨版本workspace/plugin迁移有证据；人工使用测试完成。

## 四、性能与硬件路线不等于“以后再优化”

每阶段从出生起记录结构计数和墙钟，但功能门与性能报告正交：

| 路径 | 结构门 | 墙钟/资源报告 |
|---|---|---|
| 协议复读 | SHA覆盖、读取文件、未知字段保留 | 冷/热读取、峰值内存 |
| 资产DAG | 输入不变`rebuilt_nodes=0` | 各质量档冷/热时间、IO |
| SceneIndex | 只dirty受影响node | change传播、CPU占用 |
| 刚体回放 | 几何重建=0、网格上传=0 | 帧时、draw call、显存 |
| 连续形变 | 预热后对象分配=0、更新范围受控 | 帧时、带宽、内存 |
| 作业 | 状态机合法、可取消恢复 | 排队、执行、传输、发布耗时 |
| 数值后端 | 逐位或声明容差等价 | 端到端三次中位、资源占用 |

首选优化顺序是删重复转换/上传/分配、增量和分块，再讨论并行/GPU；数值求解热点继续服从
[spec/13](../spec/13_算法与硬件后端_v0.md)和
[research/06](../research/06_引擎自身性能画像_20260805.md)，不被视觉流畅度替代。

## 五、进入实现前必须裁决

| 决策 | 推荐项 | 为什么不能默认 |
|---|---|---|
| 产品、应用与仓名 | 平台`RTime Engineering Platform`；应用`RTime Engineering Studio`；仓工作名`rtime-engineering-platform` | 品牌、包名与仓库治理是三件事，仍需用户批准最终名称 |
| 平台代码位置 | 新monorepo；`physics-engine`先独立接入，真实原子变更成本+M2.5演练后再评审是否迁入`engines/` | 不能用普通文件移动破坏历史、发布和回滚；长期独立也是允许目标 |
| 领域项目位置 | GCW/WII/WDS/FTS保持独立仓，以插件/adapter接入 | 领域资产、硬件、治理和发布节奏不同 |
| 首批纵切 | VS-A FTS+WII只读，VS-B WDS，VS-C GCW | 单一FTS会把领域词冻进核心 |
| 初始renderer | Three/WebGL2隐藏backend | 复用现有资产，保留raw WebGL2反证 |
| desktop壳 | PWA/Web先行，Tauri/Electron实测后选 | 体积、本地服务和跨平台代价未测 |
| 插件安全模型 | manifest+SHA+能力声明，代码信任等级另定 | 本地插件与第三方插件风险不同 |
| 跨语言schema权威 | 一个字节面一个正本；现有physics facet归本仓，平台新面归平台仓 | Python/TypeScript双写会必然漂移 |
| 旧spec冲突 | 新决策明确统一机制、不统一领域实现 | 不能在研究页静默改历史范围 |
| 大资产分发 | 清单走git，内容地址/资产库另裁决 | 大STEP、纹理、帧序列不适合普通git |

## 六、明确不在本轮发生的事

- 不创建`rtime-engineering-platform`仓，不移动或合并任何Git历史；
- 不选择Tauri/Electron、Three/Babylon或WebGPU为永久唯一方案；
- 不引入Node、OCCT、Blender、VTK或GPU依赖；
- 不修改四项目源代码或已有产物；
- 不把FTS未接线草案登记为“平台已实现”；
- 不修改冻结spec或登记新facet；
- 不提交、推送、发版或部署。
