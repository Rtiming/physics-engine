# RTime工程设计与计算平台孵化文档

状态：**上位产品架构提案，2026-08-09；未冻结、未实现**。

本目录记录这段时间跨GCW、WII、WDS、FTS与`physics-engine`逐步显现的共同目标：

> 建设一套由我们自己掌握工程对象语义、科学与数值权威、工程工作流、前端视觉运行时、
> 产品设计系统、工业工作台、插件体系和部署策略的通用工程设计与计算平台。

架构工作名改为**RTime Engineering Platform**；面向用户的工作台暂称
**RTime Engineering Studio**。二者都不是已批准的仓名或最终品牌。“仿真”是平台的
核心能力之一，但不是平台总边界：CAD/中心线分析、机构设计、参数扫描、标定、实测对比、
科学可视化、知识组件和工程交付也属于同一产品闭环。

Blender、OpenCASCADE、Three.js、WebGL/WebGPU、VTK、OpenUSD、glTF、Alembic、
URDF/SDF等均是可替换的工具、后端、格式或生态适配器。它们可以帮助平台完成CAD解析、
实时绘制、科学可视化和离线动画，但不拥有平台的对象身份、参数语义、物理真值、任务生命
周期、工作区状态或用户体验。

## 为什么单独建立本目录

此前的[research/14](../research/14_多表示模型资产与硬件适配架构_20260809.md)和
[plans/10](../plans/10_模型资产与呈现架构演进计划_20260809.md)正确识别了多表示模型、
资产编译、硬件适配和Blender/VTK端点，但把产品中心说窄成了“资产/呈现层”。最新复盘确认：

- 多表示资产和物理仿真都是平台子系统，不是平台的全部；
- 前端不是计算末端的Viewer，而是设计、运行、检查、比较和导出的主要产品入口；
- 我们需要拥有自己的工作台和可视化运行时，第三方图形库只能藏在backend/adapter边界内；
- 设计原则、视觉语言、设计token、组件、图表和3D交互规范必须由我们自己拥有，不能只给
  第三方组件库换主题；
- `physics-engine`仍是无头、零必需依赖的科学计算内核，不能吞入Node、CAD、DCC和浏览器栈。

因此用`docs/platform/`承载产品级愿景与跨仓边界；它不等于在本仓创建了平台代码包。

## 三个容易混淆的“域”与“引擎”

- **物理域**：mechanics、optics、electromagnetics等科学方程子包；
- **领域应用插件**：GCW、WII、WDS、FTS对公共平台的业务扩展，不等于Python物理域；
- **外部backend/adapter**：Three、VTK、Blender、OCCT等执行器或工具边界；
- **物理引擎**：现有`physics-engine`科学内核；
- **平台/Studio**：包外编排、视觉交互和用户工作流，不是物理引擎的`frontend/`子目录。

## 一条删除测试

判断某能力是否真正属于自有平台，可使用下面的反事实：

> 假设删除Blender、Three.js、VTK、OCCT、某套UI组件库或某个远程服务器，平台是否仍能
> 说明并复读同一工程对象、参数revision、作业、结果、时间线、工作区、设计语义与可信度？

若不能，说明平台语义错误地泄漏给了工具；若能，工具才真正处于可替换适配器位置。
