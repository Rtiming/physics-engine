# 产品设计系统与美学规范（2026-08-09）

状态：**一级产品架构提案，未冻结token、未建立组件包、未完成视觉方案**。本页明确设计系统
应拥有什么、怎样与科学可信度和前端运行时结合；它不是一份已经完成的品牌手册。

## 一、结论：设计系统是平台协议，不是最后换皮

RTime Engineering Platform需要自己的产品设计系统，原因不是“页面要更好看”，而是四个
项目都在反复表达相同的高风险语义：对象身份、设计revision、计算状态、可信度、缺失数据、
单位、选择、时间、证据与显示插值。如果这些含义由各页面临时选颜色、图标和组件表达，用户
会在跨项目时重新学习，甚至把视觉状态误认成物理结论。

设计系统因此拥有五类权威：

1. **产品原则**：信息如何取舍，证据与演示怎样分离；
2. **视觉语言**：排版、密度、空间、色彩、形状、图标和动效；
3. **交互语言**：选择、编辑、运行、比较、撤销、恢复、时间和相机行为；
4. **组件与模式**：工程表单、状态、图表、3D、工作区和复杂流程；
5. **设计治理**：token版本、组件兼容、可访问性、视觉回归和人工任务测试。

设计系统不拥有物理真值。它只能分别映射上游声明的`job.phase.complete`、
`evaluation.status.not_evaluated`、`timeline.sample_policy.exact`、
`evidence.qualification.display_only`或`origin.as_simulated`等正交语义，不能通过颜色或动画
自行推断，也不能把它们压成一个总状态枚举。

## 二、产品气质：精密、安静、可信、可操作

推荐的美学方向不是消费级炫技，也不是模板化AI仪表盘，而是**精密仪器感与现代工程工作台**：

- **精密**：对齐严格、数字稳定、单位可见、标注清楚，光影不妨碍读数；
- **安静**：大面积中性表面承载高密度信息，品牌色和强调色克制使用；
- **可信**：来源、时间、revision、状态和限制在需要时可见，未知不伪装成零；
- **可操作**：主要动作明确，危险动作有后果说明，长任务可取消、恢复和追踪；
- **有层次**：初学者先看到任务，专家可以逐层展开参数、诊断、场和证据；
- **空间连续**：场景树、3D对象、图表曲线和检查器对同一对象保持同一选择语义；
- **有自己的识别度**：统一的比例、线条、图标、动效和数据语言构成品牌，而不是复制某套
  外部组件的默认主题。

原则冲突时按以下顺序裁决：**科学真实性与人身/设备安全→可恢复性与可访问性→任务效率→
跨领域一致性→品牌表现与装饰**。高密度不能以读错数据为代价，简洁不能隐藏会改变判断的
证据和限制，品牌识别不能占用状态色或科学色表。

首版可以以石墨/冷灰中性色为工作面，以单一冷色品牌强调作为交互锚点；成功、警告、失败、
未知等功能色独立于品牌色，科学色表再独立于功能色。具体色值要经过屏幕、投影、暗室、强光、
色觉和图表叠加测试后冻结，本页不凭审美猜测写死十六进制值。

## 三、设计系统的九层结构

| 层 | 主要产物 | 关键规则 |
|---|---|---|
| D1产品原则 | 原则、任务优先级、证据/演示边界 | 每个组件和模式都能解释为什么存在 |
| D2基础token | 原始色阶、字体、字号、间距、圆角、边框、阴影、时长 | 应用和插件不直接引用散落常量 |
| D3语义token | surface/content/action/focus/status/evidence/selection | 同一语义跨亮暗主题不变 |
| D4科学数据语言 | 分类、顺序、发散、循环、置信区间、缺失/无效色表 | 数据色与UI状态色分离；颜色不是唯一编码 |
| D5空间与3D语言 | 背景、网格、选中、悬停、遮挡、剖切、测量、锚点、ghost | PBR外观不压过工程语义和证据 |
| D6组件 | 按钮、字段、表格、树、面板、状态、工具条、对话框 | 有状态机、键盘、空态、错误和长任务规范 |
| D7工程模式 | 参数编辑、运行、比较、选择事务、导出、恢复 | 模式由任务定义，不由页面随意拼组件 |
| D8工作区与模板 | Explore/Design/Run/Inspect/Compare/Present默认布局 | 可停靠、可恢复、可迁移；领域插件只扩展 |
| D9内容与治理 | 术语、文案、图标命名、版本、审阅、视觉回归 | 设计文件、代码和文档使用同一token与版本 |

建议未来以版本化`design-system`包承载D2—D7，以文档站和设计源文件承载D1、D8、D9。
React、Web Components或其他UI框架只是实现后端；公共语义不绑定某个框架组件类型。

token内部采用`reference→semantic→component`三层别名：原始色阶/尺寸不能直接进入应用，
组件token不能重新定义语义。机器可读token schema是token名称和值的唯一正本，CSS变量、
TypeScript常量、设计工具变量和文档样例均由它生成或做conformance校验；组件行为的正本是
组件状态机与测试，产品原则的正本是本目录决策文档，不能让三个载体共同声称同一字节面权威。

## 四、状态轴、品牌色和科学色表必须分开

### 4.1 状态必须分轴，不能再造一个总状态机

下面各轴可以同时成立。例如一个job可以`complete`，artifact完整但相对当前revision为
`stale`，当前视图使用`display_interpolated`且整张图只具有`display_only`资格，并伴随一个
`warning`诊断。设计系统只为每条轴提供命名空间化token和组合规则：

| 轴 | 典型值 | 上游所有者 | 设计系统责任 |
|---|---|---|
| `job.phase` | queued/running/cancelled/failed/complete | 工作流状态机 | 阶段、进度、取消和失败恢复；不能仅用颜色 |
| `diagnostic.severity` | info/warning/error/critical | 产生诊断的领域/运行时 | 紧急程度、影响范围和建议的一致表达 |
| `evaluation.status` | not_evaluated/evaluated/invalid | 计算/验证协议 | 与数值零、空数组和作业失败分开 |
| `artifact.integrity` | unchecked/valid/invalid | artifact验证器 | SHA/版本/缺件的可见性和失败关闭 |
| `revision.freshness` | current/stale | 工程模型与binding | 同时显示来源revision和重算/切回动作 |
| `timeline.sample_policy` | exact/hold/display_interpolated | timeline+领域插件 | 显示采样政策；`display_interpolated`永不升级为证据帧 |
| `evidence.qualification` | evidence/display_only/unverified | 科学/证据协议 | 持久标记、限制和切回证据路径 |
| `view.mode` | explore/design/run/inspect/compare/present | Studio workspace | 改变布局与主动作，不改变上述任何科学状态 |

`display_interpolated`只表示时间采样政策，`display_only`只表示证据资格，Present只表示工作区
模式；三者不得互作同义词。

### 4.2 科学数据

- 分类数据使用有离散区分度的categorical palette；
- 单调量使用顺序色表，中心有物理零点的偏差使用发散色表；
- 相位、角度等周期量使用首尾连续的循环色表；
- 缺失、无效、超范围和未计算分别表达，不能都画成透明或零；
- 置信区间、容差带和测量不确定度有独立的填充/线型规范；
- 图例必须带量名、单位、范围、缩放方式和采样/时间信息；
- 任何关键差异同时提供线型、形状、标签或纹理，不以颜色作为唯一编码。

色表类别、物理零点、domain、linear/log/symlog尺度、截断/越界、缺失值、插值和降采样政策
必须由字段元数据或领域插件声明；设计系统只验证、选择兼容视觉实现并披露。缺少声明时不得
自行猜测“零点”“最佳范围”或对数尺度。灰度、打印、常见色觉模拟和离散分级均进入色表门。

图表交互统一brush/link、游标、选择同步、轴重置、缩放撤销和数据导出；默认避免容易误读的
双Y轴。任何降采样或平滑在图内可见，并可回到原始数据。关键Canvas/SVG图表提供等价数据表、
文本摘要和键盘选择路径。

### 4.3 3D工程语义

- `hover`、`selected`、`active edit target`、`locked`、`hidden`、`ghost`不得只靠同一轮廓色；
- design、collision、physics、render、measurement表示切换时始终显示当前角色和revision；
- 剖切、透明和X-ray是view state，不能暗改碰撞或物理参与性；
- 证据模式禁用可能伪造形状或时间的平滑处理；演示模式允许更丰富的材质、灯光和插值，但
  必须显示`display_only`并保留一键回到证据模式；
- 相机、测量、框选、定位和坐标轴行为跨领域一致，CAD面选择等业务裁决仍归插件。

3D视口必须由项目树/对象列表提供可键盘遍历的等价选择路径；当前选择、transform、表示角色、
单位、bounds和关键诊断能以结构化文本读取。测量和相机定位至少有非拖拽入口；屏幕阅读器不必
解释像素，但必须能获得当前对象、动作结果和错误。

## 五、六种工作模式

| 模式 | 用户主问题 | 默认主视图 | 允许的主要改动 |
|---|---|---|---|
| Explore | 这个项目里有什么 | 项目树+3D+摘要 | view state、选择和导航 |
| Design | 我要怎样改设计 | 参数/装配+3D+约束 | 草案command，提交后产生revision |
| Run | 这次计算怎样执行 | 作业、进度、资源、诊断 | 提交、取消、恢复；不能伪造完成 |
| Inspect | 结果是否可信、哪里异常 | 3D/场/曲线+证据检查器 | 联动游标、测量、诊断过滤 |
| Compare | 两个revision/run差在哪里 | 对齐视口+差异图表+表格 | 配准、基线和比较配置 |
| Present | 怎样向别人说明结果 | 叙事布局、相机、图表、注释 | 只生成交付recipe，不修改原run |

模式不是六套完全不同的应用。它们共享对象、命令、Widget和快捷键，只改变默认布局、主动作
与风险提示。用户切换模式后，选择和上下文应连续，未提交草案必须得到明确处理。

## 六、首批组件和模式，不先造完整组件宇宙

第一纵切只需要围绕FTS+WII实际任务落下：

1. 应用框架、项目树、命令面板、可恢复工作区；
2. 属性/参数检查器，含单位、约束、来源、默认值和草案状态；
3. 作业状态、进度、取消、失败诊断和artifact完整性；
4. 3D viewport工具条、选择路径、表示/revision标识和时间控制；
5. 曲线/波形/光谱Widget，含单位、游标、缩放、图例和缺失数据；
6. timeline/event、run比较、通知、空态和离线状态；
7. 导出对话框，显式区分数据、模型、动画、视频和报告及其来源回执。

表格、树、dock、图表或无障碍primitive可以复用成熟库，但必须包在我们的语义组件和token
边界内。领域插件不能绕过公共组件自行发明`complete`、`warning`、选择或时间控件。

## 七、动效和动画规范

- 动效解释状态变化，不以持续运动制造“高级感”；空闲工程页不应持续重绘；
- 工作区重排、选择转移和层级展开使用短、可中断的过渡；
- 作业进度不使用无法反映真实状态的假百分比；未知时显示阶段或活动而不是伪精确；
- 刚体/形变回放服从timeline的`exact/hold/display_interpolated`政策；UI缓动不改变物理时间；
- 遵守减少动效偏好；所有关键操作在关闭动画后仍可理解；
- 导出的演示动画记录相机、可见性、插值和渲染recipe，不能只交付不可追溯的视频字节。

## 八、文字、数字和术语

- 文案准确、简短、可执行；警告说明后果，错误说明恢复路径；
- 对象名、操作名和状态名进入术语表，GCW/WII/WDS/FTS的同义词不进入公共core；
- 数字使用等宽数字特性，保留工程有效位规则；单位不靠列标题猜测；
- 时间明确时区、时基和采样；revision、run、artifact和workspace不互称“版本”；
- 中文、英文符号、公式和代码在同一排版系统中可读；重要诊断可复制为结构化文本；
- AI生成的解释、建议或布局必须标记来源，不能与求解器诊断使用同一权威样式。

## 九、设计系统的验收矩阵

| 维度 | 自动门 | 人工/设备门 |
|---|---|---|
| 语义 | token引用、状态枚举、未知状态失败关闭 | 用户能区分零/缺失/未计算/失败 |
| 可访问性 | WCAG 2.2 AA目标、键盘、焦点、ARIA、对比度、200%缩放、减少动效 | 键盘完成核心任务；色觉模拟、图表/3D等价通道和屏幕阅读抽测 |
| 视觉回归 | 固定数据、固定主题、关键尺寸截图diff | 审阅差异是否是有意变更 |
| 工程图表 | 单位、图例、色表类型、缺失值和范围校验 | 专家判断是否可能误读物理意义 |
| 3D交互 | pick ID、选择同步、资源与帧计数 | CAD、刚体、形变三类任务走查 |
| 性能 | 首帧、空闲重绘、Widget更新、DOM/GPU资源预算 | 低端机、缩放、多窗口和长时间使用 |
| 恢复 | 布局迁移、context loss、插件缺失、离线状态 | 用户能找回隐藏Widget和未提交草案 |
| 一致性 | 禁止裸常量、组件API兼容、术语lint | 跨两个领域不重新学习同一动作 |

“截图一样”只能证明一层；可访问性、数据准确性、交互行为、性能和真实任务均需独立证据。
每条新自动门都要有至少一个必须红fixture：例如只有颜色区分、错色表scale、缺单位、隐藏焦点、
`display_interpolated`冒充证据或插件绕过token。设备/浏览器矩阵、截图容差和性能阈值由首个
纵切实测后入版本化基线，不在本页凭空写数。

设计系统由平台design-system owner维护；科学色表元数据需领域所有者共同审阅，可访问性和
跨领域交互需独立审核。新增兼容token/组件可走minor，删除或改变既有语义必须给一版弃用期并
附迁移器；插件引用未知/禁用token或覆盖平台状态语义时构建失败。设计源、生成代码、文档和
视觉基线都记录同一design-system版本。

## 十、阶段安排

### P0原则与语义

冻结真实性优先级、信息层级、六种模式、正交状态轴和设计token分层；建立设计决策记录。
“精密仪器感、石墨/冷灰、冷色强调”仍是候选美学方向，须经真实纵切和多设备视觉实验后冻结。

### P1设计协议

定义token schema、命名、主题继承、领域扩展和版本迁移；建立最小文档预览与对比度/裸常量门。

### P2headless阶段

沿用P0/P1设计协议，不新增视觉冻结；只为作业、诊断、错误和恢复补齐可被未来UI准确呈现的
语义。P2没有独立美术交付不是编号遗漏。

### P3视觉运行时语义

落实3D选择、表示状态、证据/演示模式、timeline和性能计数；以WDS反证精确帧不能被动效污染。

### P4Studio组件与真实任务

随FTS+WII纵切实现首批组件、工作区、图表和任务模式；开始视觉回归、键盘和人工任务测试。

### P5以后产品化

扩展GCW/WDS领域模式、品牌主题、报告/动画模板、设计源文件、图标、内容规范和第三方插件指南。

## 十一、行业参照只提供原则

- Siemens Industrial Experience把工业设计系统定义为组件、设计基础、内容指南和可访问性等
  一套协作体系，并强调清晰、灵活、赋能和以人为本；可借鉴工业任务与设计治理，不复制其品牌：
  https://ix.siemens.io/docs/guidelines/overview
- IBM Carbon的数据可视化规范区分分类、顺序和告警色，并以可访问性和邻近区分度组织色板；
  可借鉴数据色与UI色分离：
  https://carbondesignsystem.com/data-visualization/getting-started/
- NASA Open MCT以可组合对象、布局、时间和插件支持多数据源操作工作台；可借鉴用户可组合视图，
  不把它直接当我们的工程模型或Studio实现：
  https://nasa.github.io/openmct/about-open-mct/
- WCAG 2.2要求颜色不能成为表达信息的唯一方式，并给出文本对比度等可检验要求；这是最低门，
  不是设计完成证明：
  https://www.w3.org/TR/WCAG22/

## 十二、明确非目标

- 不在没有用户任务和视觉实验前冻结最终Logo、字体和整套色值；
- 不自写浏览器基础控件、排版引擎或图表光栅器来证明“自主”；
- 不用巨大留白、卡片堆叠、渐变背景或持续动效冒充现代化；
- 不让主题切换改变状态含义、科学色表、物理精度或证据等级；
- 不要求领域插件视觉完全相同，但要求相同语义和交互保持一致；
- 不把设计文件、组件代码和产品文档分成三个互相漂移的正本。
