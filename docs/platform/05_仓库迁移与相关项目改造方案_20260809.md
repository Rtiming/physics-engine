# 仓库迁移与相关项目改造方案（2026-08-09）

状态：**迁移设计与只读影响审计，未创建目标仓、未移动文件、未改远程、未改消费方**。
本页回答“是否把`physics-engine`迁进上位平台文件夹，以及相关项目怎样一起改”。

## 一、当前建议

目标产品使用一个新的平台monorepo，工作名`rtime-engineering-platform`。推荐分两阶段：

1. **先统一产品与协议，不先搬引擎**：新仓承载协议、工程模型、工作流、视觉运行时、
   design system、Studio、SDK和adapter；通过已发布wheel连接独立`physics-engine`。
2. **被真实跨仓改动证明后再评审迁历史**：P1协议闭环且至少两个纵切跑通后，只获得迁仓
   评审资格；如反复需要平台协议、adapter和引擎同一提交原子变化，还须先通过M2.5临时clone
   演练，才可单独批准把`physics-engine`完整Git历史导入`engines/physics-engine/`。如果
   独立wheel和版本化协议一直顺畅，可以永久保持A形态。

这不是回避迁移，而是把“目录看起来整齐”和“架构真正一体”分开。普通文件移动只改变本机
路径；历史保留的monorepo导入才改变代码治理，必须有独立迁移批次和回滚证据。

GCW、WII、WDS、FTS不建议一起吸入monorepo。它们是具有独立资产、硬件、领域算法、治理和
发版节奏的应用仓，应通过版本化协议、插件、adapter和制品联邦协作。

## 二、四种仓库形态比较

| 形态 | 好处 | 主要风险 | 裁决 |
|---|---|---|---|
| A平台新仓+引擎独立 | 回滚清楚；不动现有发布；最快验证边界 | 初期跨仓协议变更需兼容矩阵 | **立即阶段推荐** |
| B平台monorepo内含引擎历史 | 协议/adapter/引擎可原子提交；统一CI | 导入、tag、镜像、发版脚本与权限更复杂 | **达门后的目标候选** |
| C1上位文件夹嵌套多个独立`.git` | 本地看起来集中 | 工具、同步、搜索、dirty状态和新贡献者容易混淆；没有原子治理 | **不推荐** |
| C2平台仓使用Git submodule | 能钉精确commit并保留独立远程 | clone/init/update、分支与CI摩擦；跨仓变更仍不原子 | 只可作集成清单候选，不作默认开发形态 |
| D把引擎和四个领域项目全并进巨仓 | 单次clone得到全部 | 大资产、硬件、隐私、许可、活跃分支与发布互相污染 | **明确不做** |

如果用户只想在Finder里集中项目，可另建不入git的workspace配置或仓库清单；不要用移动多个
独立`.git`目录替代平台架构。若集成测试需要“引擎+四领域仓的确切组合”，优先让manifest记录
仓URL、commit、制品SHA与获取方式；只有现有工具链证明manifest不足时再评测submodule。

## 四、为什么`physics-engine`可以迁，但身份不能变

`physics-engine`适合成为上位平台中的一个引擎目录，因为它是平台自有科学计算内核，未来
跨语言协议、作业adapter、结果conformance和性能基线会与平台长期共同演进。但迁入后必须
继续满足以下不变量：

| 不变量 | 迁移后要求 |
|---|---|
| Python分发名 | 仍为`physics-engine` |
| Python import | 仍为`physics_engine` |
| 版本与旧wheel | 已发版本不覆盖、不删除，旧环境继续离线安装 |
| 运行时依赖 | 核心wheel继续`dependencies=[]`，前端依赖不能渗入 |
| 物理与数值门 | spec/13、逐字节/容差对拍、30/120验收纪律保持 |
| 开源与许可 | 现有MIT公开身份保留，第三方平台包另做许可清册 |
| Git历史 | M0记录迁移当日真实提交数、分支与tag；所有历史及迁移基准commit可追溯，不复制成一次“初始导入” |
| 远程 | 旧舰队远程和GitHub镜像在过渡期继续可用 |
| 消费关系 | WDS/FTS继续消费发布制品或稳定协议，不依赖monorepo本机路径 |

当前`tools/release.py`虽然以脚本位置寻找包根，但它检查的是整个Git工作树，并把tag和push
发往当前仓远程。迁入monorepo前必须把“包根”“Git根”“包级dirty范围”“tag命名”和
“独立镜像远程”拆清，并用同一源码构建逐字节相同wheel。不能假设目录嵌套后原脚本自然正确。

## 五、当前实测为什么阻止立即搬动

2026-08-09只读盘点显示：

- `physics-engine`有本轮尚未提交的平台文档修改；
- GCW有尚未登记入库的拆分STEP/STL资产；
- WDS有基准、契约、测试和新设施的活跃修改；
- FTS有大量前端和合同文档活跃修改；
- WII当前工作树干净，但位于功能分支；
- `viewport-input`当前干净并独立发布。

因此现在执行目录移动、subtree导入或相关仓批量改写，会把“平台迁移”和其他人的未完成工作
混成一个不可审计状态。本轮只写方案，不触碰这些仓。

另外，现有治理已经把仓身份写入多处：

- `physics-engine`决策0001/0002固定了中立顶层仓与包名；0010/0012固定了wheelhouse、tag、
  公开镜像和旧版本共存；
- WDS钉住`physics-engine==0.4.0`并vendor带SHA的wheel，运行时并不依赖本机checkout路径；
- FTS ADR 0036只放开独立`physics-engine`上游并要求依赖箭头无环，尚未切换代码依赖；
- `viewport-input`要求消费方vendoring，不允许运行时import兄弟checkout。

迁移不能改写这些已接受历史来假装从未发生；应新增决策记录显式取代路径/仓拓扑部分，保留
包、版本、无环依赖和制品绑定部分。

## 六、迁移波次

### M0冻结与回执

1. 等待本轮文档和各相关仓活跃修改各自提交、暂存或形成明确交接；
2. 记录每仓分支、HEAD、远程、tag、dirty清单、许可和大资产策略；
3. 运行各仓自己的全量门，保存结果和关键制品SHA；
4. 决定目标仓所有者、可见性、最终名称和哪些包开源；
5. 在`physics-engine`新增一份决策记录，明确取代0001的“物理目录位置”，不改其科学承诺。
6. 明确单一写入源：M3前独立`physics-engine`是权威，切换窗口双方冻结写入；若M3完成，
   monorepo成为权威，旧远程只接受自动engine-only split，不再接受人工双写。

退出门：任何输入仓都能独立恢复，dirty工作不靠迁移脚本“顺便带走”。

### M1创建空平台骨架

只创建平台文档、workspace配置、最小协议/设计系统包和CI；不复制引擎源码。添加
`physics-engine`adapter，验收从固定wheel安装后可执行一条只读能力发现和run复读。

退出门：新仓离线、无GPU、无Blender可启动；删除引擎checkout仍可使用已发布wheel。

### M2协议与纵切证明

用FTS+WII只读纵切建立跨语言conformance fixture；再以WDS反证时间和renderer边界。记录
跨仓修改频次、发布等待和真正需要原子提交的案例。

M2通过只开放迁仓评审，不自动触发M3。至少满足以下一项真实触发条件，才进入M2.5：

1. 已发生两次以上必须协调发布的平台协议、adapter和engine facet变更；
2. WDS与FTS均成为代码级引擎消费者，且兼容发布等待成为可测瓶颈；
3. 一个真实平台作业必须同时修改`physics-engine`与跨语言conformance，
   expand→migrate→contract仍无法安全解耦。

退出门：至少两个领域使用同一协议，旧产物字节不变；有证据说明迁入能解决实际成本，而不是
只让目录更整齐。没有触发证据时，A形态即是长期目标，不继续M2.5/M3。

### M2.5临时clone迁移演练

只在可删除的临时clone中执行，不改变任何权威远程：

1. 比较`git filter-repo`前缀重写与`git subtree`导入，选择并记录唯一算法；
2. 验证分支、merge、作者、时间、tag和签名处理，产出原commit→新commit映射；
3. 在monorepo嵌套路径构建wheel，与M0基准做逐字节对拍；
4. 运行`accept.py full`、跨平台路径门和平台conformance；
5. 演练包级release dry-run、namespaced tag、wheelhouse发布与部分失败补偿；
6. 生成engine-only split，证明可在不force push的前提下衔接旧公开仓历史；
7. 演练删除导入分支、monorepo损坏和独立仓恢复三种回滚。

退出门：上述七项全部有回执；任何force push、历史断裂、错远程、wheel漂移、私有内容泄漏或
无法回滚均阻断M3。

### M3保留历史导入`physics-engine`

采用M2.5已裁决并验证的算法，把完整历史放到`engines/physics-engine/`前缀，再合入平台仓；
源仓和旧远程保持不动直到全部验收。不得手工复制工作树或只导入最新快照。

导入后建立：

- 原commit→新commit映射和迁移基准说明；
- 包级路径/依赖/测试/覆盖/体积门；
- `physics-engine-vX.Y.Z`一类不冲突tag策略，旧`vX.Y.Z`仍可在独立镜像解析；
- 平台tag、独立镜像tag、平台commit与split commit的发布回执映射；
- 可快进的engine-only split流程，禁止通过force push“修正”旧公开历史；
- 包级CODEOWNERS/变更清单，前端依赖不进入引擎wheel；
- public-split-safe提交规则与secret/license/path扫描，防止私有平台上下文、资产或许可越界。

退出门：从迁移commit构建的wheel与迁移前基准逐字节相同；`accept.py full`与跨平台门通过；
旧远程未丢历史，旧消费方无需改动即可继续运行；切换窗口后只有monorepo接受人工写入。

### M4相关项目接入

按第七节逐仓新增adapter/plugin和新ADR，不做批量搜索替换。领域仓拥有权威exporter、领域
schema和自身回归；平台仓拥有consumer adapter/plugin、Studio Widget和公共conformance；
协议包拥有不可变fixture与兼容矩阵。每仓仍以自己的输入、产物、门禁和发布节奏验收。

退出门：相关项目不import平台源码目录，不出现写死的兄弟仓路径；旧前端和科学结果保持。

### M5远程、镜像与发布切换

只有M3/M4稳定后，才把旧`physics-engine`远程正式切为只读/自动split镜像；不提供双向人工维护。
发布脚本必须防止错远程、错tag、错包范围和平台其他dirty文件造成不确定发布。

退出门：从全新clone可构建、测试、发布dry-run；公开用户能找到历史、许可、版本和迁移说明。

### M6观察与收口

至少跨一个引擎版本和一次平台版本运行；验证Windows/macOS/Linux开发路径、wheelhouse、CI、
旧消费者和回滚。没有观察期不得删除旧工作流或归档旧远程。

观察期必须持续维护兼容矩阵：platform、protocol/facet、physics-engine wheel、WDS FramePacket、
FTS run/render-state、WII timeline/manifest、GCW geometry bundle和各plugin版本。跨仓schema升级
使用expand→双读/双写或adapter迁移→contract，不要求四仓同日升级。

## 七、相关项目逐仓改造

| 仓 | 保持不变 | 未来新增 | 迁移时禁止 |
|---|---|---|---|
| `physics-engine` | 科学真值、包名/import、零依赖、spec、发布制品 | 平台adapter、协议conformance、包级发布边界 | 引入浏览器/Node/Three；重写历史或覆盖版本 |
| WDS | vendor wheel+SHA、FramePacket、证据门、raw WebGL2 | 平台WDS插件、精确timeline adapter、资源计数对拍 | 改成本机monorepo路径依赖；公共插值补帧 |
| FTS | standalone治理、六文件包、光学语义、现有活跃前端 | 新ADR放开平台协议/插件；Provider/workspace草案蒸馏 | 原样升格FTS枚举；在未冻结dirty树上批改 |
| WII | FK/IK、机器人语义、模型manifest、资产SHA、bind pose | 刚体timeline/SceneIndex adapter、WII领域Widget | 公共core重算FK；宽松JSON直接升格协议 |
| GCW | CAD权威、中心线、选择事务、实体映射、制造资产 | CAD/中心线插件、长事务与resource lock adapter | 把业务picking塞进公共renderer；搬未登记资产 |
| `viewport-input` | renderer-neutral输入政策、版本/SHA、独立消费 | 可作为平台依赖或以后保留历史导入独立package | 运行时import兄弟源码；抹掉GCW/WII适配层 |

### 7.1 WDS

WDS已经消费版本化wheel，所以平台仓位置变化不要求立刻改`pyproject.toml`。真正需要改的是：

- 新增平台插件manifest和WDS领域schema命名空间；
- 让FramePacket adapter明确`exact/hold/display_interpolated`；
- 保留现有逐字节/性能/证据门，增加平台前后对拍；
- 用新决策或活文档取代“兄弟checkout路径”的说明，不修改历史证据页。

### 7.2 FTS

FTS目前只接受`physics-engine`作为无环上游，平台若成为新上游必须由FTS自己的新ADR裁决：

- 明确允许的是发布的protocol/SDK/adapter，不是任意兄弟源码；
- 继续保证standalone复读、固定run package和没有平台时的基础能力；
- 从当前Provider/workspace草案蒸馏公共字段，FTS操作名和route/signal留在插件；
- 等当前前端dirty工作形成自己的提交/交接后再改，避免覆盖另一条工作流。

### 7.3 WII与GCW

二者首先是工程作者/领域工作台和平台插件，不冒充`physics-engine`的两个现有消费方。
WII提供刚体、资产绑定和机器人反证；GCW提供CAD身份、picking和长事务反证。它们可以共享
Studio壳与输入策略，但领域算法、制造权威和选择裁决仍留原仓。

### 7.4 `viewport-input`

保持其独立包身份是当前最低风险路线。若以后迁入monorepo，也应作为有自己版本、manifest、
测试和公开API的package导入历史，不能把源码复制进`apps/studio`后失去上游身份。

### 7.5 设计系统怎样进入旧前端

相关项目不做一次性“全局换皮”。每个项目先保留原前端作为行为与视觉基线，在平台插件纵切中
逐层接入语义token、基础组件、工作区模式和视觉回归；同一模式至少被两个领域真实使用后，
再从领域样式提升到公共设计系统。FTS的工业主题是重要种子但不是默认正本；WDS的证据色、
GCW的CAD选择和WII的机器人状态都要先映射语义，再决定共同外观。任何换肤不得改变选择、
作业、时间、物理帧或结果字节。

## 八、迁移验收与回滚

### 8.1 必须同时通过的证据

1. **历史**：迁移前HEAD、tag、原提交和新路径映射可查；
2. **构建**：同一源树的sdist/wheel文件清单、元数据和SHA达到声明等价；
3. **科学**：引擎full门、数值容差和正式产物对拍通过；
4. **消费方**：WDS钉旧wheel仍通过，FTS standalone仍通过；
5. **平台**：协议conformance、两个纵切、视觉和性能门通过；
6. **跨设备**：Windows/macOS/Linux路径检查，绝对路径和行尾门通过；
7. **发布**：dry-run不会向错误远程、错误tag或错误wheelhouse落盘；
8. **回滚**：删除目标仓clone后，旧仓和已发布制品仍能恢复工作。

### 8.2 回滚策略

- M0—M2只新增平台仓，回滚就是停止使用，不改旧远程；
- M2.5只在临时clone中完成，未过门直接删除演练结果；
- M3合入先留在独立分支，全部门通过且写入源切换获批后才进入主线；
- 合入后仍保留独立源仓和远程至少一个观察期；
- 消费方升级以精确版本和自己的门禁为准，可各自回退；
- 不使用破坏性历史覆盖、不删除旧wheel、不让大资产随代码迁移脚本隐式移动。

## 九、执行前仍需用户裁决的一项
