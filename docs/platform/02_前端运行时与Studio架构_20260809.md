# 前端视觉运行时、Studio与设计系统架构（2026-08-09）

状态：**候选架构，未建包、未迁移消费方**。本页把“搞自己的前端”展开为可实现、可替换
backend、可验收的范围。

## 一、前端不是末端Viewer

面向用户的前端同时承担六种职责：

1. **设计入口**：创建参数草案、选择模型revision、校验单位与约束；
2. **执行控制面**：发现能力、提交/取消/恢复作业、显示进度和诊断；
3. **观察分析面**：联动3D、曲线、场、表格、日志和对比；
4. **工程工作区**：停靠、分屏、标签、隐藏、恢复、布局迁移和命令系统；
5. **交付入口**：导出数据、报告、动画、视频或第三方格式，并绑定来源回执。
6. **产品语言载体**：用一致的视觉、文字、图表、3D和交互规范表达工程语义与可信度。

它不拥有物理真值：相机、窗口、曲线缩放、视觉质量和显示插值都属于view state；修改物理
参数必须产生新draft/revision和新job。

## 二、自己的前端引擎应拥有到哪一层

```text
engineering-studio（概念结构，不是已建目录）
├── contracts
│   └── ID/schema/unit/frame/time/SHA/artifact/evidence
├── artifact-runtime
│   └── decoder registry/校验/cache/chunk/worker/transferable
├── compute-runtime
│   └── capability/operation/job/progress/cancel/artifact publication
├── scene-runtime
│   └── renderer-neutral node/representation/binding/change-set
├── timeline-runtime
│   └── clock/track/event/exact/hold/display-interpolated
├── workspace-runtime
│   └── widget/split/stack/selection/command/lock/undo/migration
├── render-runtime
│   └── dirty schedule/resource/dispose/context-loss/quality/counters
├── design-system
│   └── token/typography/density/chart/status/accessibility/theme
├── plugin-sdk
│   └── domain/compute/renderer/import/export/widget plugin
└── app-shells
    └── web/PWA/desktop/headless/local-service
```

第一阶段不要按这棵树创建十几个空包。它描述所有权边界；实际代码应从少量可运行包和两个
真实插件起步，再按依赖与发布节奏拆分。

## 三、五种状态绝不能混在一起

| 状态 | 例子 | 是否可改 | 权威与生命周期 |
|---|---|---|---|
| 工程文档状态 | 组件、参数草案、设计revision | 可通过command修改 | 版本化、可审计、可撤销 |
| 作业状态 | queued/running/cancelled/failed/complete | 由runtime状态机改变 | 不允许UI伪造完成 |
| 仿真结果状态 | run、精确帧、场、诊断 | 完成后不可变 | 科学内核/run package权威 |
| 工作区/view状态 | 窗口、相机、选择、曲线缩放、主题 | 用户自由修改 | 本地持久化，可迁移但非物理证据 |
| backend临时状态 | THREE.Group、WebGLBuffer、GPUTexture | 由renderer拥有 | 不落公共协议，必须dispose/可重建 |

FTS当前`workspace/contracts.ts`草案与`computeProvider.ts`草案是重要种子，但当前仍含
FTS专有的route/signal/operation词汇，且并未证明已经接入主应用；只能蒸馏，不能原样升格。
同理，任何`THREE.Group`、WebGL句柄或vtk对象都只能留在backend插件。

### 3.1 2026-08-09现有种子与证据等级

| 种子 | 已经证明 | 尚未证明/不能直接升格 |
|---|---|---|
| `viewport-input`独立包 | renderer-neutral core、Three依赖注入、策略数据化、幂等dispose、离线vendoring；GCW/WII已有消费 | 只覆盖输入/视口政策，不是SceneIndex、timeline或Studio |
| FTS Provider/workspace草案 | DTO、artifact locator、job/cancel、split/stack/widget/binding形制可用作蒸馏输入 | 当前快照仍是未接主应用的草案，且含FTS术语；不是平台已实现 |
| GCW前端 | renderer依赖显式、camera/resize边界、selection事务与busy/generation思路 | CAD raycast、后端确认和中心线判据仍是领域逻辑 |
| WII前端/运动模块 | visual/collision用途、资产SHA、`kinematics_hash`、bind pose/link transform、刚体轨道 | `source_identity`不足、可选字段宽泛；不能原样成为公共timeline |
| WDS WebGL舞台 | 静/动态VBO、容量复用、quality governor、context-loss和生命周期治理 | FramePacket/evidence、带材/接触shader与禁止物理插值仍归WDS |

这张表只记录当前源码/文档快照的证据，不把“有一个类型或测试”升级成“已经形成共享运行时”。

## 四、视觉内核的核心抽象

### 4.1 SceneIndex而不是共享renderer对象树

`SceneIndex`提供领域中性的视图投影：稳定node ID、层级、transform、representation binding、
visibility、layer、bounds、semantic tags和change set。领域插件把工程模型和run映射进
SceneIndex；renderer adapter只观察added/removed/dirtied变化。

这样可以同时支持：

- GCW的CAD实体与分析覆盖层；
- WII的静态link网格+每帧transform；
- WDS的静态工位+动态带材buffer；
- FTS的仪器组件、光束、标签和状态覆盖层。

公共SceneIndex不裁决“是否碰撞”“中心线是否合格”或“光路是否正确”。

### 4.2 Timeline不是统一插值器

时间内核至少显式区分：

- `exact`：只有求解器给出的帧才可作为证据；
- `hold`：保持上一真实状态，不制造中间物理；
- `display_interpolated`：仅为观看生成的插值，必须带显示标记；
- `event`：离散状态、告警、接触建立/解除或配置切换。

WDS证明不能为了流畅统一插值；WII刚体播放可以在明确政策下插值transform；FTS曲线游标与
3D状态需要共享时基但不一定共享采样率。

### 4.3 Widget是数据绑定视图，不是领域真值

首批Widget类型：

- 3D viewport；
- 曲线/波形/光谱；
- 网格、标量/矢量/张量场；
- 项目/场景树；
- 参数检查器；
- timeline/event；
- run比较与完整性；
- 表格、日志、诊断和报告预览。

每个Widget声明可消费的数据类型、单位、时间能力、选择能力和renderer需求。工作区只保存
Widget ID、布局与binding，不保存renderer内部对象。

### 4.4 Command、事务与资源锁

参数编辑、运行、比较、导出、选择提交等通过可命名command进入；长操作声明所锁资源和
generation，避免GCW中选择事务、后端确认和busy状态互相覆盖。撤销/重做只适用于可逆设计
命令，不能“撤销”已经发布的run；正确动作是生成新revision或新run。

## 五、backend与领域插件边界

| 层 | 公共内核拥有 | 插件/backend拥有 |
|---|---|---|
| renderer | SceneIndex、资源/帧生命周期、性能计数、基础pick hit | Three/WebGL/WebGPU/vtk对象、shader、GPU buffer |
| 交互 | pointer/key/gesture标准动作、selection model、camera intent | CAD面选择、机器人关节操纵、带材证据picking |
| 计算 | capability、namespaced operation、job状态、artifact ref | FTS simulate/fit、WII IK、WDS solve等领域操作 |
| 资产 | identity、representation、缓存与decoder协议 | NPZ/GLB/STEP/VTK等具体解析器 |
| 工作区 | widget registry、split/stack、binding、迁移 | 领域Widget、默认布局和参数编辑器 |

默认实时backend可先使用Three.js/WebGL2，但公共API不得暴露Three类型。WDS已有raw WebGL2
资源治理，应作为第二backend/反证，而不是强行迁移成Three。WebGPU进入同一backend registry，
不成为平台启动前置。

## 六、现成方案能替代多少

| 方案 | 可直接借力 | 不能替代 | 当前建议 |
|---|---|---|---|
| Three.js | Web实时场景、材质、加载器、WebGL2；新renderer可探测WebGPU | 工程模型、workspace、作业、证据和领域语义 | 首个隐藏renderer backend |
| Babylon.js | 更完整的Web图形/交互与WebGPU路线 | 我们的科学数据/工作流语义，且迁移现有Three资产有成本 | 保留对拍候选，不先换栈 |
| VTK/vtk.js | PolyData/ImageData、场、切片、体绘制和科学Widget | PBR装配与整个Studio | 科学可视化插件 |
| OpenUSD Hydra | Scene Index/renderer解耦的成熟架构模式 | 浏览器Studio和我们的跨域协议 | 借架构，不设核心依赖 |
| Omniverse Kit | 薄内核+扩展+事件/update loop的应用平台模式 | 自托管轻量Web基线、非NVIDIA机器底线 | 生态端点/架构参照 |
| Godot/Unreal | 原生交互、写实、XR或仿真端点 | Web优先工业工作台和科学可信度 | 有明确产品场景再接 |
| Blender | DCC、材质、镜头、离线渲染和脚本 | 实时工作台、物理权威和平台对象模型 | 导入/导出/渲染adapter |

Three.js官方当前说明`WebGPURenderer`可在缺少WebGPU时回退WebGL2，但仍标为实验状态，并且
自定义材质/后处理迁移并非无成本。因此当前基线仍应是WebGL2，WebGPU以能力发现后的可选
backend进入：
https://threejs.org/manual/en/webgpurenderer

vtk.js官方定位是Web科学可视化库，覆盖ImageData/PolyData、常用reader和pipeline基础设施，
也明确其目标不是复制全部VTK/C++ filter；这支持“按领域插件接入”，而不是拿它承包整个
Studio：
https://kitware.github.io/vtk-js/docs/index.html

## 七、部署和硬件适配

### 7.1 四种壳，共用协议

| 形态 | 作用 | 基线 |
|---|---|---|
| Web/PWA | 默认交互入口、易部署和远程访问 | 静态资源+本地/远程Provider |
| 桌面壳 | 离线文件、原生菜单、可选本地worker管理 | 待选Tauri/Electron，不提前冻结 |
| 本地服务 | Python/CAD/计算进程与浏览器的安全桥 | loopback、显式project root、无路径泄漏 |
| headless/server | 批次、资产编译、渲染、CI和远程计算 | 同一job/artifact协议、可取消恢复 |

平台不应依赖云账号、Blender或master才能完成基础打开、复读和CPU基线任务。第三方依赖应可
打包、自托管、钉版本并记录许可；插件加载要有manifest、能力与内容SHA。

### 7.2 三个独立backend registry

1. **numeric backend**：精度、确定性和结果等价优先；
2. **asset backend**：转换误差、工具recipe、缓存可复读优先；
3. **render backend**：设备能力、画质、帧时间和资源恢复优先。

三者不能共用一个“GPU开关”。探测只陈述能力，显式profile才作选择；降低视觉质量不得
降低物理精度或证据等级。

### 7.3 优先级明确的提速点

- 内容寻址增量DAG，输入和recipe不变时零重建；
- SceneIndex change set与dirty rendering，只更新变化分支；
- 静态/动态资源分离，WII每帧只传transform，WDS预分配并局部更新buffer；
- typed/chunked array、Worker和transferable，避免主线程解析和重复复制；
- LOD、实例化、proxy先到、分块和可恢复流式；
- 视口不可见或静态时停止无意义重绘；
- 计算、资产和渲染分别profile，不用页面帧率冒充求解器提速。

任何“倍数”都要在固定纵切输入上测冷/热、首帧、帧更新、CPU、内存、GPU、IO和结果等价；
本页不预报尚未测出的收益。

## 八、美学不是最后换皮

设计系统从平台P0就定义原则与语义，从Studio MVP开始落实token和组件；视觉精修可以后置，
语义和交互规范不能后置：

- **信息层级**：工程对象、参数、运行状态、证据和诊断优先于装饰；
- **工业密度**：支持长时间工作与高信息密度，不做巨大卡片式AI仪表盘；
- **状态色**：complete/warning/failed/not-evaluated与物理数据色表分离；
- **科学色彩**：顺序、发散、循环和分类色表按数据语义选，不能靠品牌色替代；
- **模式分离**：Explore/Run与Design具有明确动作边界；证据模式与演示模式显式区分；
- **可恢复布局**：任何被隐藏、脱离或提升的Widget都能找回、重置和迁移；
- **可访问性**：键盘、焦点、对比度、缩放、非颜色状态提示和减少动效；
- **一致交互**：相机、框选、测量、时间游标、图表工具条和快捷键形成跨领域视觉语法。

完整的产品原则、token分层、模式、组件、科学色表、3D语义、验收和治理见
[04 产品设计系统与美学规范](04_产品设计系统与美学规范_20260809.md)。领域插件可以增加
命名空间化的领域token和Widget，不能改写平台的状态色、证据语义、焦点行为或基础交互。

## 九、前端纵切验收

首个自有Studio不能只测“页面能打开”。至少同时验证：

- FTS或WII的静态/刚体场景能加载、选择和按时间回放；
- WDS的精确帧/连续形变能作为不同renderer和timeline政策接入；
- 同一workspace能放置3D、曲线、参数、run和诊断Widget；
- 插件切换不要求重启，领域术语不进入公共协议；
- 静态网格只上传一次，空闲不持续重绘，context loss可恢复；
- 没有WebGPU、Blender、远程服务器仍能使用基础路径；
- 旧前端和物理产物字节不变，平台只新增适配路径；
- renderer对象不出backend边界，工作区保存后可严格复读与迁移。
