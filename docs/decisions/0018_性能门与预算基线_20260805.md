# 0018 性能门与预算基线（2026-08-05）

状态：已落地。plans/02的T1轨道。解决的是本仓最大的一处空档——
spec/13第零节自称最高原则、声明了逐操作延迟与体积预算，
而`tools/accept.py`**一条性能断言都没有**，"显著回退=破坏性变更"是空话。

## 一、门的形态：墙钟不进门，确定性量进门

这是本页最重要的一条裁决，与直觉相反但有数据（research/05第四节）：

- GitHub托管runner的墙钟变异系数**CV = 2.66%**；配2%阈值假阳率**45%**；
  压到1%假阳需要约7%的门——**等于测不到小回退**；
- **Drake**在`multibody/benchmarking/README.md`明写其基准"不作为性能回退测试"；
  **MuJoCo**的CI干脆不跑benchmark。

因此本仓分成两半：

| | 谁测 | 进不进门 | 理由 |
|---|---|---|---|
| 墙钟延迟 | `tools/bench.py`产报告到`work/bench/` | **不进** | 方差压不住，且负载敏感 |
| 确定性量 | `tests/perf/test_budgets.py` | **进** | 跨平台逐位稳定，不受负载影响 |

进门的三条确定性量：**源码字节数**（wheel体积的代理——wheel要构建，源码字节不用，
且逐位稳定）、**eager import模块数**（冷启动成本的结构代理，新模块进顶层
`__init__`会同时抬高它与墙钟）、**运行时依赖数**（永远为0，0014承诺+0016裁决）。

它们能进功能路径正是因为确定性：0014法则2禁止的是"宿主负载改变功能结论"，
而这三个量与负载无关。

## 二、wheel的30KB：不是硬上限，是口语化取整

**实测`physics_engine-0.4.0-py3-none-any.whl` = 30940字节**，而spec/13写的是
"wheel 30KB离线装"。30KB若按30720字节算，**这条预算在被写下的那天就已经破了**。

结论：那句话是对30940字节的口语化取整，不是硬上限。改为
**随版本记账的曲线**（`benchmarks/engine_budgets.baseline.json`的
`wheel_budget_history`），门守的是**记账义务**——发了新版本却没有对应的一行，
测试就红。这样wheel不会在没人看见的情况下长大，也不会因为一个不精确的
口语数字把每次正常增长都判成破坏性变更。

源码字节的上限设为96KiB（实测65680字节，约1.5倍余量）——plans/02第五节估算
各轨道合计约+1000行，按实测18.4字节/行约+18KB，仍在上限内。

## 三、accept.py的四处改动

1. **双档真分家**：此前`quick`与`full`的命令集**逐字相同**，双档退化成一件事。
   现在`quick`只跑交互级（`-m "not batch and not serverclass"`），
   `full` = quick全部 + 本机批级（`-m batch`）+ 案例页校验位；
   `quick ⊆ full`由governance元测试守着。marker与spec/13零之二的负载三级一一对应。
2. **轴6规则4（资源资格）**：每核1分钟负载超过1.5即判资源不合格，
   计时轴判`NOT_EVALUATED`（**不是FAIL**），功能结论一个字不改。
   反向也守着：资源不合格不是免死金牌，功能红照样红。
3. **轴6规则5（性能回执绑执行树）**：`repository_identity`扩出
   `execution_tree_sha256`，覆盖代码+构建声明+被测输入+基准与预算件+基准工具自身
   （金标件与被测输入都在树内——换了金标还沿用上一轮性能结论正是这条要挡的）。
   树变了→`performance=NOT_EVALUATED`。
4. **超时改杀整棵进程树**：`subprocess.run(timeout=)`只终止直接子进程。
   实测确认：老写法下孙进程在超时后仍然存活（`gc-alive`标记文件被写出）。
   案例套件与同行库对拍必然派生子进程，这个洞会变成挂死。
   现改为新会话组+SIGTERM→SIGKILL，元测试实跑验证孙进程被杀干净。

**硬超时是活性护栏不是SLA**：真正杀进程的线=预算×4，不是30/120本身。
直接拿预算当杀进程线，会让宿主负载改变**功能**结论——0014法则2禁止这件事。
"慢"由计时轴单独裁决，"挂死"由活性护栏兜底，两者不混。

## 四、空档位：申报过的才准空

`batch`档今天一条测试都没有，pytest以退出码5（未收集到测试）返回。
它既不是通过也不是失败，是**空档位**。裁决：只有`MAY_BE_EMPTY`里
**申报过**的命令可以空并视同通过，回执里如实记`empty_selection_commands`
并在stdout打印；**交互级绝不许为空**——它为空说明marker写错或测试没被收集，
必须红。否则一个marker笔误就能让整档静默不跑而验收照绿，
那正是轴6"零执行命令→BLOCKED"要挡的那类事。

## 五、验红记录（每个门都真红过）

- 源码字节上限压到1000、eager import上限压到3、wheel记账改成不含当前版本
  → 三条**全红**，恢复后全绿；
- 空档位：申报过的空命令判PASS，未申报的同样退出码5判**FAIL**（元测试双向验）；
- 杀进程树：独立实验确认老写法`subprocess.run(timeout=)`下孙进程存活=True，
  新实现下标记文件不存在；
- 资源不合格：超预算999秒但资源不合格→timing=NOT_EVALUATED、functional=PASS；
  功能红+资源不合格→仍然FAIL。

governance元测试从11条增至20条。

## 五之二、源码字节上限改为"抬可以，但必须记账"（2026-08-05当日补裁）

T6的`materials.py`一入仓，`source_bytes`从65680涨到89003，占用达上限的90.5%、
余量仅9301字节——下一个同量级模块必破门。这暴露了原设计的一个错误：

**固定绝对上限对本仓是错的工具**。0015已裁决要把WDS的物理搬进来（那边是约2万行），
源码字节注定大幅增长。固定上限会被反复撞破，而每撞一次就训练人"抬一下就行"，
门的价值就废了——最后退化成一个没人看的常数。

改法：与wheel同一个形制。上限**不是**"引擎必须保持小"的承诺，而是
**"增长必须是一次被记录的决定"**。抬上限允许，但必须在
`source_bytes_ceiling_history`里留一行（带决策记录路径与理由），
且门校验**现行上限等于历史末行、每行的决策记录文件真实存在**——
想悄悄抬过不去。已验红：只改`ceiling`不记账，测试当场红。

本次抬到147456字节（144KiB，实测89003，约1.65倍余量），理由入册。
**明确拒绝的选项**：把校验往薄里写来换余量。诊断性错误消息是这一层的产品价值，
不拿它换字节。

## 五之三、未跟踪符号链接让验收器崩（同日修）

`repository_identity`对每个未跟踪条目`read_bytes()`，遇到指向目录的符号链接
抛`IsADirectoryError`。触发路径很实际：并行开发的每个worktree都要软链`.venv`
（`.gitignore`的`.venv/`带斜杠只匹配目录，不匹配符号链接，于是它成了untracked）。

语义裁决：**符号链接的内容是它的目标字符串**，不是目标指向的字节。
跟随链接读目标字节会把仓外的东西算进仓库身份，比崩更糟。
链接本身仍进指纹——改指向是一次真实的工作区变化，元测试双向验过。
命名管道/套接字之类只记形态不读内容（读可能阻塞到超时）。
