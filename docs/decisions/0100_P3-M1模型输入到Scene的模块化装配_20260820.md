## 一、裁决

P3.1首片只建一条可证伪纵切：

```text
PhysicsModelMotionInput
+ 已复读碰撞资源
+ 显式接触/允许对
→ FinalizedScene
+ time_s或planning_scale运行面
+ 虚拟frame
→ 既有CollisionQuery
```

这条链不读WII/GCW目录，不自动两两生成接触，不从visual回退collision，也不把
dynamic体冻结成static。它不新增跨边界字节，因此不新建facet。

`physics_model_motion_input/0.1`仍是draft且尚无外部消费方；本批为了消除frame猜测，
将`ModelComponent.frame_id`升为必填键，这是草案面内的破坏性修订，已在CHANGELOG登记。
P3.2第一个真实WII adapter出现前必须重审版本与冻结条件，不得让外部依赖偷跑在draft后面。

## 二、模块边界

### 2.1 `pose_math`

只处理`parent_from_middle ∘ middle_from_child`刚体位姿组合。它在scene基座圈，不为了四元数相乘
反向import力学域`rigidbody`。平移先旋转再相加，旋转按xyzw Hamilton积；两个顺序都有点变换对拍。

### 2.2 `scene_resources`

资源边界分三层：

1. `ModelAssetRef`：模型包声明的资产身份、相对路径、SHA、单位、frame和安装变换；
2. `CollisionAssetLoadSpec`：不能从文件名猜的AABB、凸性与保守方向；
3. `LoadedCollisionAsset`：从包根重新读字节/核SHA后，把前两者闭合成`CollisionShape(MeshAsset)`。

路径经`resolve()`后仍必须位于包根，所以符号链接逃逸也被拒绝。本模块不解析STL/OBJ，
不证明声明AABB/凸性正确；它证明的是“当前形状记录确实指向这串被锁字节”。

`AnalyticCollisionRecord`是另一条路：shape ID、`CollisionShape`和`component_from_shape`
显式绑定，且拒绝把`MeshAsset`塞进解析形状通道。

### 2.3 `model_scene`

只做编排：

- 递归组合模型组件层级的`root_from_component`；
- 强制每条component motion track的`frame_id`与`ModelComponent.frame_id`一致，不猜隐式工具frame；
- 按`ModelPhysicsRelation`声明顺序装static/kinematic体；
- 将`component_from_asset/shape`后乘到静态或运动位姿；
- `time_s`计划通过`MotionSource`进`SceneAssembly`；
- `planning_scale`使用独立无量纲采样面，调时间API必红；
- 虚拟frame单独输出，不伪造`SimBody`；
- 只把`SceneInteractionPlan`显式声明的候选交给`BroadPhaseCollisionQuery`。

## 三、为什么dynamic本片必须红

`PhysicsBodyBinding`已能声明dynamic、material ID和mass-properties ID，但今天还没有冻结：

1. dynamic状态的position指组件frame原点还是质心；
2. `MassProperties.centroid_mm`在asset/shape frame下还是component frame下；
3. 初始参考位姿与积分状态如何交接。

随便选一个会让接触形状与惯量绕不同的点转。所以P3.1首片见到dynamic直接报错，
错误消息点名state frame/centroid欠账。故意绕过这条时，dynamic测试当场红，证明它不是装饰门。

## 四、P3-M1案例

`cases/model_scene_assembly`含两份小型合成资产字节：

- 张力机→static，AABB正负2mm；
- 工件→kinematic，AABB正负1mm；组件x由20mm移到0mm，后乘1mm资产偏置；
- process frame由10mm移到12mm；
- 机器人显示组件/运动保留在输入但不进Scene；
- 显式候选只有张力机—工件一对。0s分离，1s只报`broad_phase`重叠。

金标生成器不import被验模块，只做加法、线性中点、整数计数和文件SHA。案例总数52→53，
主能力17/42与端到端0/6不变。

## 五、性能与GPU

新增100份预加载资源两体场景装配工作负载。每组先热身，三组各9次的批中位数为
26.233/8.250/7.605ms，三组中位8.250ms，即每场景约82.5μs；最快单批7.145ms。
预算100ms，保持交互级。

首组存在明显瞬时扰动，所以墙钟仍只作观测，不进回退门。热路径是几个小dataclass、字典和
位姿组合，不是大数组核；GPU不适用。磁盘资产SHA复读是发布/加载边界，不应在每个物理步重做。

P3.0合同本批补`ModelComponent.frame_id`后，100份严格包从3494增至3529字节。三组各9次复读
批中位为40.046/42.063/40.522ms，三组中位40.522ms，较本批改前65.404ms没有性能回推。

## 六、没有做的事

1. 没有解析fixture为真实三角网格，不证明AABB、凸性、法向或侵入量。
2. 没有dynamic状态装配、材料本构、惯量接线、接触力或张力。
3. 没有WII adapter、official timeline、WDS采用或现场标定。
4. 新模块不进顶层eager re-export，运行时依赖仍为0。

## 七、后续触发条件

触发条件：下一片先在本仓冻结dynamic的state frame/质心/惯量交接，并用一个合成自由刚体让
几何与惯量绕同一个点运动；另一条可独立开工的线是为真实资产增加一个可验证AABB/凸性的后端，
但不把重型CAD/网格库变成必需运行时依赖。WII真实adapter仍在P3.2，不是上述两条的前置。
