## 一、裁决一：`accept full`预算 120 → 180 秒

`BUDGETS`在`tools/accept.py`第49行标着"轴6规则1冻结值，改这里必须走决策记录"，本页就是那份记录。

### 1.1 为什么抬，而不是分档

基础设施批次合入后在master同机同分区同核数上实测三次 **106.8 / 107.7 / 106.8**
（中位数106.8、离散0.8%、三次四轴全绿），**余量只剩11%**。
而合入前那一棵树是 **87.7秒**（2067条测试），现在是2374条——
**两组数直接可比，所以"宿主污染"这个老解释这次不成立**：这一次是套件本身真的在长。

0080那条老纪律写的是"若那时仍超120秒，则是套件真的长过了预算，**要裁的是分档而不是抬预算**"。
**本页按所有者裁决抬预算，与那条纪律相反，所以要把理由和代价都写下来**：

* **理由**：预算这一轴按spec/07规则1只裁决**开发吞吐**，不裁决物理正确性。
  120秒这个数是2026-08-05立的（当时全仓26个案例、几百条测试），
  它代表的是"一次全档验收不该打断开发节奏"这个判断，**而不是任何物理或性能上的界**。
  今天42个案例、2374条测试，同一个判断对应的数不再是120；
* **代价，逐条**：
  1. **分档这件事被推迟了，而它迟早要做**。今天full档把交互级与本机批级一起跑，
     抬到180只是把同一条曲线往后推——按最近三批的增速（+14.9%测试／批），
     **180秒的余量约够再来三批**。登记成GAP，触发条件是"第一次撞破180"；
  2. **`HARD_TIMEOUT_FACTOR`那条活性护栏跟着放大**（它是预算的倍数），
     于是一次真的挂死要更久才会被杀。本页不改那个因子——它是护栏不是SLA。

### 1.2 同批不动的两个数

* **quick档仍是30秒**。它今天实测约6.6秒，余量4.5倍，没有理由动；
* **master上批级档那条90秒预算不动**（实测59.21）。

## 二、裁决二：基础设施批次二的范围

用户的验收口径是"**所有相关的基础设施有没有补好**"与"**各种场景都要跑通并验证**"。
按能力位台账逐格核过之后，六个场景今天的**剩余前置**分三类：

| 类 | 是什么 | 本批做不做 |
|---|---|---|
| **甲｜能做且判据强** | 有解析金标、不依赖仓外输入、不需要新决策 | **做** |
| **乙｜能做但要先裁形制** | 例如自接触的接触对怎么声明、耦合目录怎么分层 | **裁了再做，裁不动就留空** |
| **丙｜不由我们控制** | 现场实测五项、WII的v2时间线导出 | **不做，只登记** |

甲类逐条（本批的活儿）见plans/18第一节。**丙类一条都不碰**——
plans/15第四节已经把它们钉死，碰它们是浪费。

## 四、裁决四：派活书里的"解开哪几位"必须由合入方逐格复核

0084第一节那张表把S3.2记进了轨甲，**而轨甲解不开它**（0074第一节自己写过
"几何判定与接触力学是两道题"）。同批还有S4.6：label三件（单缝／双缝／**矩孔**）只做了两件，
**而这一条是主代理合入时逐格核出来的，轨道自己没报**。

**裁：派活书里的能力位预期是一句期望，不是结论；合入方必须逐格对着label核一遍再动台账。**
这条写进本页而不是只留在CHANGELOG，是因为它已经是**同一形状的第三次**
（S3.7的label三件只做了第一件、同行C档第7条的转述失真变成一个进位、本次的S4.6）。
