# 0073 工具住哪，以及三维模型以什么形态进来

日期：2026-08-17
状态：**已裁决**。用户口径"项目肯定要和模型相结合，它应该是什么形态；工具应该放在哪；
派代理调研别人怎么做的"。调研为只读，四路同行核查＋两个与本仓同型的求解器库。

## 一、决定性的那条先例：PyElastica走过一趟，两年后搬回起点

**PyElastica是本次核查里与本仓形态最贴近的一个**——纯Python的Cosserat杆求解器，
和本仓一样是"库不是应用"。它2023年把网格读取放进了内核：

* v0.3.2加`elastica/mesh/mesh_initializer.py`（首行`""" Mesh Initializer using Pyvista """`）
  与`elastica/rigidbody/mesh_rigid_body.py`，读STL/OBJ；
* 代价是`pyproject.toml`里`pyvista = "^0.39.1"`成为**必需运行时依赖**——
  **一个纯Python杆求解器因此拖着VTK**；
* 2025-07-16提交`df8006b0`删掉这三个模块与三个测试，
  `pyproject.toml`的diff是`- "pyvista"`、`- "vtk"`；
* 触发它的issue #471标题就是
  **`[Mesh] Move out the mesh codes to another repository`**，
  正文："我们正在把所有网格相关代码搬到一个独立的扩展仓……为了让这里保持简单和有条理。"
* 今天master的`elastica/surface/`只剩`plane.py`，`rigidbody/`只剩`cylinder.py`与`sphere.py`。

**代价也要如实说**：#500与#520两条issue是用户在问网格接触怎么做——拆出去之后用户少了一条路。

> **本仓今天的位置，正是PyElastica 2023年之前的位置。
> 它走了一趟"进去—搬出来"的两年往返，结论回到起点。本仓不必走这一趟。**

## 二、同行把"模型"放在哪一层：没有一家放在内核之外，但有一家劈成了两半

| 项目 | 模型在哪 | 关键结构 |
|---|---|---|
| MuJoCo | **内核里，比预想更靠里** | `libmujoco`＝物理＋XML解析器＋编译器＋光栅器＋UI控件库；资产**烘进**`mjModel`。`mjSpec`没有把模型层搬出去，只是把它变成可寻址的 |
| Chrono | 内核里，但**碰撞与外观挂两个不同基类** | 视觉挂`ChObj`、碰撞挂`ChContactable`，两棵树互不认识。**关键不对称：视觉网格核心永不加载，碰撞网格加载进核心因为求解器要顶点** |
| SOFA | 分层最彻底 | 一个肝三套几何（四面体网格／平滑三角面／一堆球），只由mapping连着；`.scn`只是注册进工厂的一个loader |
| USD/PhysX | 物理是**贴在几何prim上的applied API schema** | `UsdPhysics`在OpenUSD本体；`PhysicsRigidBodyAPI`等全部`inherits APISchemaBase` |
| **Pinocchio** | **劈成两半，带几何那半编译期默认关** | `ModelTpl`全文grep几何相关只命中一个裸索引typedef；`GeometryModel`是独立对象，`BUILD_WITH_COLLISION_SUPPORT`**默认OFF**、关掉时给`FakeCollisionGeometry`桩 |
| MBDyn | 另一个极端 | 官网自称"不是开箱即用的实体建模GUI"，无几何、无CAD导入、可视化整个外包 |

**Pinocchio那条与本仓对应得最准**：它的`Model`＋算法＝本仓的`state`/`energies`/`solve`/`rod`，
它的`GeometryModel`＝本仓的`shapes`/`geometry`/`collision`。

**本仓的形状层是全场最薄的**——比Pinocchio还薄，因为Pinocchio至少有`meshPath`/`meshScale`
与一个真的`fcl::CollisionGeometry`指针。**所以"过重"这条不存在，"过轻"有两处且都已登记**
（无映射层，research/12第2.3节；`MeshAsset`无质量模型，spec/11第二之二）。

## 三、一条本仓独有、且同行没有的门

**"碰撞代理必须包住视觉网格"这道门，已核查的同行里没有一家做。**

| 栈 | 有没有 |
|---|---|
| SOFA | 无。`SceneCheck*`九条里`SceneCheckMapping`**零几何** |
| OpenUSD | 有物理validator四条，**全是结构性**——没有包含性、没有Hausdorff、没有体积比 |
| MuJoCo | 无。`discardvisual`只是把非碰撞几何删掉 |
| Chrono／Drake | 无 |

**现实后果**：USD里`convexHull`加在凹网格上会**静默改变物体形状**，
`usdchecker`、`usdPhysicsValidators`、Omni Asset Validator一个字都不说。
**这与本仓0017抓到的"包络是编的"是同一种病，差别是本仓建了门**
（`cases/mesh_asset_integrity`：SHA逐字节＋envelope逐轴包含，零容差，`fitted`拒判）。

spec/11规则5自称"外部引擎无此显式概念"，核查后**成立且比原来更强**——
不只是没有这个概念，是连结构性校验都不碰几何。

## 四、裁决一：工具住在`tools/model/`，与`validation/`同形制

**不新建仓、不动wheel、不加运行时依赖。**

```
tools/
  model/                       新增
    README.md                  身份边界（抄validation/README.md第一节）
    requirements-model.txt     钉死版本，只装进 tools/model/.venv
    mesh_aabb.py               STL/OBJ → 真实AABB + SHA-256（**纯标准库**）
    centerline_csv.py          22列CSV → GrooveStation元组（**纯标准库**）
    step_extract/              可选重依赖档，见第六节——**本仓不开工**
validation/                    已有先例（0025）：同行库对比，独立venv
```

四条理由：

1. **本仓已经有这个形制，而且它被裁决过。** 0025给`validation/`立的三条硬边界
   （永不进`dependencies`、永不被`src/`import、独立目录独立venv）逐字适用。
   **不需要发明新纪律，只需复用一次已经过门的纪律。**
2. **前两个工具是纯标准库的，连独立venv都不需要。** 证据在仓里：
   `cases/mesh_asset_integrity`的二进制STL解析器只有**17行`struct`**；22列CSV标准库`csv`足够。
3. **对零依赖承诺的影响是零。** `packages = ["src/physics_engine"]`让wheel只含`src/`
   （0.7.0实测48条目全是`.py`）；`tools/`已在sdist内、wheel外；
   `runtime_dependencies`门测的是`dependencies`，不看`tools/`。
   **唯一要新加的一条门**：`tools/model/`不得被`src/`import，自检形制抄0025。
4. **同行证据支持"工具在仓内、依赖在外"，不支持另建仓。**
   SOFA把无头GUI管道留在仓内、只把**开窗**GUI推到外部仓；
   MuJoCo的`simulate/`在仓内靠CMake选项挡GLFW；
   **Drake拆出去的是资产不是工具**，且是被PyPI 100MB硬限制逼的——**本仓没有那个限制**
   （wheel 274678字节）。

### 4.1 明确不做的两条

* **现在建平台仓**——platform/03与05已裁"A形态立即阶段推荐"，
  而M1—M2前置（协议闭环＋两个纵切）一条都没走。
  **为一个CSV读取器触发那条路线是本末倒置。**
* **把真实资产放进本仓**——三条现成反例：
  Bullet issue #2918（297MB、物理库占**2.4%**、维护者答复大意是
  "没法在不破坏所有已有clone和fork的前提下改写历史，只能忍着"——**单向门**）；
  Chrono仓内`data/` **1165MB**；
  Drake被PyPI 100MB逼出一次**−1186238行**的手术。
  MuJoCo menagerie另说明**许可证污染比体积更难回退**（71个模型目录里69个各带自己的LICENSE）。
  `cases/mesh_asset_integrity/assets/tetra.stl`那种**284字节合成资产**是对的形态。

## 五、裁决二：模型的结合形态维持"内核只吃解析形状与声明"，但补上回路

**维持不变的部分**：内核不解析网格字节，`MeshAsset`携带声明的AABB与`convexity`，
`geometry.mass_properties`对网格失败关闭。

**理由不是"通行做法"，是三条本仓特有的**：

1. **零依赖让"内核读网格"的代价与同行不同。** 同行的代价是加一个依赖；
   本仓要么破承诺，要么手写。手写可行（17行二进制STL已在仓里），
   但读进来立刻要回答"凸包谁算"——**凸包不是17行**。
   MuJoCo旧文档写过"凸包计算是编译器做的最慢的操作"。**这条路第二步就撞墙。**
2. **诚实条款让"声明式"在本仓比在同行更有价值。** 声明式＋包含门得到的是
   "**声明可以是错的，但错了会红**"——比"引擎自己读所以一定对"更合本仓其余部分的形制。
   （本次核查确认MuJoCo连关掉凸包的开关都在3.2.5删了。）
3. **但今天那道门只覆盖了一个语料。** `cases/mesh_asset_integrity`用的是仓内284字节合成四面体；
   `examples/`里的KUKA连杆资产在WII仓，case.md第四节明写"无字节可查、不判"。
   **所以0017抓到的那种缺陷，在真实资产上今天仍然没有门。**

**要补的回路：工具产出的声明，必须能被本仓的门验回去。** 三步，按依赖顺序：

| 步 | 做什么 | 依赖 | 解锁什么 |
|---|---|---|---|
| 1 | `mesh_aabb.py`：读STL/OBJ出真实AABB＋SHA-256，产出可直接粘进`physics_scene` JSON的字段 | **纯标准库** | 把"包盒是编的"从人工填写变成**工具生成＋案例门复验** |
| 2 | `centerline_csv.py`：22列CSV＋sidecar → `GrooveStation`元组 | **纯标准库** | plans/15阶段二2.1；0067第七节第7条"本仓一份真实中心线都没有"第一次有路可走 |
| 3 | `step_extract/`：从STEP取命名边并按弧长均布采样 | OCCT或gmsh，独立venv | 见第六节——**本仓定契约，不开工** |

**第2步有一条纪律**：`laydown`那五条语义**不许有默认值**（0067已裁），
工具在读CSV时**不许替调用方拿主意**——它把CSV变成元组，语义仍由调用方显式给出。

## 六、裁决三：STEP取命名曲线，本仓**定契约不开工**

调研的结论很干净：**"从CAD取命名曲线喂给仿真"在仿真世界里没有任何实现，
但每一块都在货架上**——

* gmsh的`Geometry.OCCImportLabels`**默认为1**，配`addPhysicalGroup(dim=1,…)`就能拿命名曲线；
* OCCT链文档化且稳定：`TopExp_Explorer`→`BRepAdaptor_Curve`→`GCPnts_UniformAbscissa`（按弧长均布）；
* **Chrono有读STEP、也有曲线约束族，但两头不接**——其cascade模块只有`BRepAdaptor_Surface`（面→三角形），
  没有`BRepAdaptor_Curve`。

**真正的先例在CAM与AFP/缠绕，不在物理引擎**（FreeCAD CAM把CAD边当一等输入；
AFP路径规划在曲面自己的(u,v)域解微分方程；NTNU那组从STEP AP242抽edges生成焊接位姿）。
**与本仓场景同型**：槽中心线是CAD曲面派生的**一等工艺曲线**，不是三角形。

**但本仓不做它**，两条理由：

1. **中心线的权威生产者是GCW**，spec/11第三节明写"不迁移GCW的B-Rep管线"。**本仓做它等于抢上游的活。**
2. **一条硬约束**：OCCT XDE用户手册原话是STEP有两级命名，Part Names被支持，
   Entity Names"很少使用，因为它倾向于让数据结构过载"。
   **不要假设STEP文件会把边的名字交给你**——可行路子是用户侧命名、按层/颜色标边、或前缀约定。

**本仓该做的是定它的输出契约**，即第五节第2步那个reader认什么。

## 七、另外三条不该做的（都有出处）

1. **不要vendored一个凸分解库。** Bullet把V-HACD vendored进`Extras/`，最后提交2021-08-07，
   而上游V-HACD已宣告EOL并把开发迁到CoACD——**Bullet被永久钉在一个五年前的、已死的库的副本上**。
   对照：MuJoCo把凸分解**指向外部**（CoACD），换工具只改一行依赖。
2. **不要把工具塞进产品面。** Drake issue #21868记着"只是构建`MultibodyPlant`就把
   vtk_internals、X11、OpenGL、GLX全拉进来了"——**那是viewer/网格解析住在求解器仓里的账**。
   本仓自己已经写过正确版本（`cases/mesh_asset_integrity/case.md`第二节：
   "把25行struct塞进产品面等于顺手改了产品的能力边界"），本页只是核查了它在同行那里被反复证实。
3. **不要动`laydown`归力学域这条。** 它带来一个本仓独有的形态——
   **一条CAD派生的语义曲线以"声明＋显式语义"的形式住在物理域里**。
   同行没有对应物。**这不是缺陷，是本仓领先于同行的一块。**

## 八、本页明确没裁的

* **映射层要不要建**（research/12第2.3节登记的"一个对象三套表示＋映射"）——
  SOFA那套mapping有四个开关且力经`applyJT`往上传，代价不小；本仓今天没有消费方要它。
* **`MeshAsset`的质量模型**（spec/11第二之二）——Chrono从B-Rep直接给惯量、MuJoCo从凸包算，
  本仓两条都不走。**触发条件仍是"第一个真需要网格惯量的消费方"。**
* **第五节三步的排期**——第1、2步是纯标准库、随时可做；第3步不由本仓开工。
  **具体什么时候做，看plans/15阶段二什么时候开工。**
* **调研里"没查到"的六条**（MuJoCo menagerie拆仓的官方理由、
  ROS2那个Hausdorff工具的权威仓、Omni Asset Validator规则清单等）——**如实留白，不推测**。
