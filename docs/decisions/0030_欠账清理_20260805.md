## 一、`AxialStretch`的Hessian有独立解析oracle了（0024第六节登记的缺口）

### 1.1 独立路径是怎么搭的：两条精确有理路径，互为对拍源

生成器**不import`physics_engine.energies`，被验代码的函数一个也没复用**
（spec/12第3.2节的独立oracle路径条款）。它只从`oracles`取清单落盘的机械件。

- **路径A（机械求导）**：`fractions.Fraction`上的二阶前向jet，只实现
  `+`/`−`/`×`/`√`四条链式法则，然后把
  `U = ½·(EA/l0)·(|x_j − x_i| − l0)²`**照定义写一遍**让它自己求二阶导。
  **它一个字也没提`d⊗d`、没提横向项**——它不知道答案长什么样，
  这正是它作为独立路径的价值。
- **路径B（手推闭式）**：把`U`写成`½k·s − k·l0·√s + ½k·l0²`（`s = Δ·Δ`），
  只有`√s`不是多项式，对它求两次导得
  `∂²U/∂Δ_a∂Δ_b = k·[ δ_ab·(1 − l0/L) + l0·Δ_aΔ_b/L³ ]`。
  这与内核那个`k·d⊗d + (k·ε/L)(I − d⊗d)`代数等价但**形式不同**，是第三种写法。

**两条路径在全部六个构型上逐位相等**（`Fraction`精确相等，不是容差比对），
这是生成脚本里的`assert`。开方要精确就要求被开方数是完全平方；六个构型里五个是
（勾股型边矢量），第六个`irrational_length`故意不是，那里退化成60位十进制有理截断，
金标自身相对误差 < 1e-60，比float64机器epsilon低44个数量级。**这个例外是声明过的，
不是无声的近似**。

### 1.2 容差是算出来的：而且算出来的结论与直觉相反

0024第三节立过一条：拉伸能的相对误差被`|x_j−x_i| − l0`的相消放大约`L/δ`倍
（那个案例是200倍）。**本次把同一个分析做到梯度与Hessian上，结论是它只进梯度、
不进Hessian**：

- **梯度**：力 = `k·δ`**正比于伸长量**，δ的相对误差原封不动进结果。所以判据是
  逐项相对，容差 = `(16 + 4·L/|δ|)·u`（`u = 2⁻⁵³`）。
- **Hessian**：横向系数`t = k·δ/L`的**绝对**误差 = `(k/L)·|Δδ| = (k/L)·(c·u·L) = c·u·k`
  ——**δ在里面约掉了**。而块的尺度就是`k`，所以块的相对精度回到O(u)。
  判据因此是**按刚度尺度的绝对**判据：`abs = 16·u·k_max`，`rel = 0`。
  逐项相对判据在这里是错的选择：横向对角项量级是`k·δ/L`，δ取小它趋于零，
  相对判据会在一个物理上无关紧要的小量上炸。

**实测印证**：`near_rest_ratio_25600`（L/δ=25600）的Hessian偏差只有`1.00u·k`，
而`irrational_length`（L/δ=449.5、且是唯一一个`fl(L)`带舍入的构型）的**梯度**偏差
是`100.7u`——放大因子在梯度上明明白白，在Hessian上不见了。
另有一条附带发现：`fl(L)`精确时（边长是完全平方），`δ = fl(L) − l0`按**Sterbenz引理**
也精确，相消**根本没有发生**——那时把`L/δ`写进容差是凭空放宽，所以容差里那一项
只在`fl(L)`不精确时才出现。

逐条实测与余量（余量 = 容差 / 实测最坏）：

| 构型 | L/\|δ\| | 梯度实测 | 梯度余量 | Hessian实测 | Hessian余量 |
|---|---|---|---|---|---|
| `at_rest` | — | 0（**零容差**） | — | 1.02u·k | 12.5× |
| `large_strain` | 5 | 0 | — | 1.02u·k | 15.6× |

**容差没有被放宽到能过为止**：这道门最难抓的一个真实物理错误——在
`near_rest_ratio_25600`（δ/L = 1/25600）上漏掉整个横向项——其量级是

1e12—1e14之间。判据地板与真实错误之间隔着十个数量级以上。

### 1.3 为什么放`cases/`不放`tests/`

三条理由：①它是**判据**不是单元测试——轴7要求金标带`expected`与逐条带理由的

### 5.1 校验为什么能拒掉"读全场状态"

"读全场状态"只有三种写法，各堵一条：

1. **把状态布局的字段名当观测量**——带材每个节点的精确位置在布局里就叫`node17_x_mm`。
   规则：通道的量名不得是所校验布局里的字段名。
2. **声明一个维数等于自由度数的大通道**——规则：总观测维数必须**严格小于**`dof_count`。
3. **编一台"能测全场"的仪器**——通道的量必须被它绑定的仪器的`measures`覆盖，
   且仪器种类必须在`REALIZABLE_INSTRUMENT_KINDS`白名单内（失败关闭）。

### 5.3 明确的边界（如实登记，不许被"过了校验"盖过）

- **维数判据是必要条件不是充分条件**：声明维数`dof_count − 1`的传感器照样过得去。

- **没有`read`、没有`observation_space`**。spec/10的`Sensor`接口尚未冻结
  （按0003的纪律，没有实现的设计只能0.x起步），本模块**故意停在声明层**；
  有一条门断言`SensorDeclaration`上不存在`read`属性，守的是这个范围。
- **不需要新的面**。本模块不落盘、不跨边界。传感器声明哪天要写进场景文件或
  run package的manifest，那时才需要一个`physics_sensor_declaration`面，
  且要先去`engine_facets.py`登记再落盘——**那个文件是闸门，加面走一次闸门提交**
  （0017的教训：`cli.py`从0.3.0起就在落盘一个没登记的形制）。
- `REALIZABLE_INSTRUMENT_KINDS`是白名单不是穷举表。它的作用不是列全世上所有仪器，
  是**逼声明者说出真机上那台东西叫什么**——一个说不出仪器种类的"传感器"，
  多半是仿真里的一个读数而不是真机上的一个器件。加一种要改`sensors.py`并补测试。
