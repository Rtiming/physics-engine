# 0050 接触形制：状态布局与接触模型（2026-08-05）

状态：**已裁决，代码已落六片**（2026-08-06更新；本页立时是「代码未动」）。本页是接触轨道的形制前置——
按决策0048第七节"**接触的形制一旦定错，后面全要返工**"，这一页必须先于第一行代码。

本页裁两件：**接触锚点放进状态的什么位置**（0033挂了很久的那条），
以及**接触用哪一类模型**。

## 一、第一件：0033的状态布局——三条路都不选，选第四条

### 问题回顾

0033已裁决：粘着锚点**是真历史**（带粘着的库仑摩擦本质上历史相关，
"这一点现在粘着还是滑动"不能从当前位形算出来），**必须进状态并随状态被复现**。

但0043第3.3节实测确认`StateLayout`装不下它，并列了三条路：

| 选法 | 代价 |
|---|---|
| 每种活动集一份布局 | 活动集一变指纹就变，**跨步守恒量断言全废**（spec/12第2.1节） |
| 引入可变长段 | `fingerprint()`语义要重定义——它今天寻址"这个具体形状"，那时要寻址"这类形状"，**而那是决策0019的承重条款** |
| 锚点留在状态之外 | **0033已否**：它是真历史，留在求解器里连run package都进不去 |

0043的结论是"三条今天都还开着，**只差一个真实需求来裁**"。

### 关键观察：0043列的三条路，分母都取错了

三条路都假定锚点数量**由活动接触集决定**——而活动集随构型变，所以布局随构型变。

**但活动集不是唯一可用的分母。** `scene.py`（决策0045）里已经有一样东西：

```
FinalizedScene.contact_pairs: tuple[ContactPair, ...]
```

它是**声明期定死、冻结、有序**的。`ContactPair`的docstring写得很明白，
留住次序是因为"接触对清单是要交给求解器按序处理的"，
而次序随`PYTHONHASHSEED`变会让接触结果不可复现（轴3规则5）。

**于是：按"已声明的接触对"给锚点分槽，而不是按"此刻活动的接触点"。**

- **声明的对数在一个案例内是常数** → 布局定长 → **指纹跨步不变**；
- **活动与否变成一个值，不是一次布局变更**：每槽带活动标志与锚点坐标，
  活动集变化时**变的是向量里的数，不是`fields`元组**；
- `fingerprint()`语义**一个字不用改** → 0019那条承重条款不动；
- 跨步守恒量断言**继续成立** → 0043那四层判据（全是跨步守恒量与跨步相位积分）
  不会在活动集变化的那一步失去意义。

### 为什么0043没看见这条

**因为它看不见。** 0043是Track R（刚体），0045是Track S（场景装配），
**两条轨道在同一波里并行**。R写第3.3节时，S正在把接触对清单做成定长有序表——
**而并行轨道之间按设计是互相不知情的**。

这正是0048第六节说的并行盲区的一个具体实例，且它的形态值得记：
**不是两条轨道改了同一个文件，是一条轨道的结论建立在"某样东西不存在"之上，
而另一条轨道当时正在把它造出来。** 分槽规则挡不住这一类——
它挡的是字节冲突，挡不住**过期的前提**。

### 裁决

**锚点按`FinalizedScene.contact_pairs`分槽，每对固定`max_points_per_pair`个槽位，
在`finalize()`时由该对的形状族确定。**

今天窄相只有球/胶囊族（`collision.py`第一片，圆柱/盒/网格明写"等下一片，不冒充"），
该族的最近点是唯一的，故**今天`max_points_per_pair = 1`**。
盒/网格族进来时它会>1，**那时必须在`finalize()`按形状族声明，不许由求解器临时决定**。

每个槽位的状态字段（`is_history=True`，走`StateField`既有机械）：

| 字段 | 宽度 | 含义 |
|---|---|---|
| 活动标志 | 1 | 该槽这一步是不是活动接触（`is_dimensionless=True`） |
| 粘着锚点 | 3 | 锚点在**某个体的本体系**里的位置（mm） |
| 粘着/滑动判别 | 1 | return-map的状态（`is_dimensionless=True`） |

**代价要如实写下来**：自由度按**声明的对数**算，不按活动的对数算。
一个声明了1000对而每步只有3对活动的场景，要为997对空槽付内存与打包成本。

**这个代价是可接受的，且它是设计的一部分而不是妥协**：
`Scene.declare_contact_between`本来就是**显式声明**的——
本仓从一开始就不做"任意两个体都可能碰"的全局接触，
`allowed_pairs`是使用者写出来的。**声明的对数是使用者控制的量。**

**触发条件（什么时候重开这条裁决）**：出现一个"声明对数远大于活动对数
且大到打包成本真的疼"的真实场景时。**在那之前，为它引入可变长段是预支**
（三前提第二条）。**登记在此，不预支。**

## 二、第二件：接触模型——罚函数式法向 + return-map摩擦，**不走LCP**

### 三类候选

| 类 | 代表 | 与本仓的适配 |
|---|---|---|
| **罚函数/柔顺接触** | Chrono的DEM、多数FEM接触 | **法向可写成能量项**，直接插进既有`EnergyTerm`四方法协议 |
| **互补/LCP** | Bullet、MuJoCo（凸优化变体） | **没有能量函数**，是变分不等式；要一套全新求解器 |
| **增广拉格朗日** | Chrono的NSC、Abaqus | 介于两者之间，要外层迭代与乘子状态 |

### 裁决：罚函数式法向 + return-map摩擦

**理由一：法向接触写成能量项，它就走完了整条路。**
本仓今天的求解器是**能量式**的（`energies`装配 → `solve_equilibrium`牛顿+回溯+带状LU）。
柔顺法向接触是一个势能项，**它满足`EnergyTerm`的四方法协议**
（`energy`/`gradient`/`hessian`/`quantities`），插进去即可。

这一条的分量要说清：`cases/README.md`第一节之二那张表里，
**走完`state`→`energies`→`solve`的只有3条，而且全是没有接触的梁**。
接触做成能量项，意味着**第一条带接触的案例天然落在第一行**——
而0048第三节说的"做成了那张表才会变"，指的正是这个。

**理由二：LCP要的东西本仓一样都没有。** 它要投影Gauss-Seidel或锥互补求解器、
要活动集迭代、**要放弃能量式装配**。而本仓是零运行时依赖、纯Python。
更要紧的是：**换求解器等于让接触绕开既有的全部门**
（能量项协议门、Hessian对拍门、带状求解门）——
那样做出来的接触，验的是一套新机械，而不是这个引擎。

**理由三：C档那三条的判据不要求LCP。** 第7条三球金字塔来自Chrono的
`utest_DEM_pyramid.cpp`——**DEM就是罚函数式**，判据是"同一模型只改摩擦系数，
一边必须撑住一边必须塌"。第8条斜面阈值`θc = arctan(μs)`是静力学阈值。
**判据是行为判据，不是算法判据。**

### 罚函数的代价，写在前面不写在事后

1. **穿透不为零。** 柔顺接触按定义允许穿透，刚度越大穿透越小、条件数越差。
   **这不是缺陷是模型**，但它必须**出现在案例页的"本案例不是什么"里**，
   且刚度必须是**声明的输入**，不许是代码里的魔数；
2. **摩擦不是势能。** 库仑摩擦耗散、非associative，**写不成能量项**。
   摩擦走**return-map**：法向力定摩擦锥，切向试探力超锥则投影回锥面并**更新锚点**。
   这一半**不在`EnergyTerm`协议内**，它是求解器的一个带历史的步骤——
   **这正是第一节那些锚点槽位存在的理由**；
3. **因此接触是"半个能量项"**：法向在能量里，摩擦在return-map里。
   **这条分界必须写进spec/12**，否则下一个人会以为整个接触都能从势能推出来。

### 明确不做（第一片）

- **不做恢复系数与弹跳**（C档第9条）：那是瞬态问题，要先有隐式积分族，
  而本仓一个都没有。**第一片是准静态。**
- **不做自接触**（场景⑤）：要先有"同一个体的两段"这种对，而`ContactPair`今天是体对体。
- **不做网格/盒窄相**：窄相第一片只有球/胶囊，**接触不冒充几何**。

## 三、判据阶梯（先定判据，再写代码）

按本仓纪律"跑通=有解析或独立oracle、判据带理由的容差、每条门验过红、进`accept.py` full"：

| # | 案例 | 判据 | 为什么它排这里 |
|---|---|---|---|
| 1 | **斜面滑动阈值** | `θc = arctan(μs)`，**θ<θc必须粘住、θ>θc必须滑**（阈值两侧行为相反） | 解析闭式；**阈值判据比数值判据强**——它两侧的结论是定性相反的，抄不出来也蒙不出来 |
| 2 | **三球金字塔双向** | 同一模型只改μ，一边撑住一边塌（Chrono `utest_DEM_pyramid.cpp`） | research/05说它是"本次调研里判据设计最好的一条"；**它同时验法向与摩擦** |
| 3 | 粘着锚点的历史性 | 同一终态、**不同加载路径**给出不同的锚点与不同的切向力 | **这条验的是0033那句"锚点是真历史"**——若实现里锚点能从当前位形算出来，这条必红 |

**第3条是本轨道最该有的一条**，因为它验的不是公式而是**形制**：
如果我们把锚点做错成"可从位形导出"，第1、2条**照样能过**。

## 四、这一片会碰哪些既有承重件

| 件 | 会怎样 |
|---|---|
| `StateLayout` | **加字段不改机械**——`is_history`与`history_fields()`早就在（0033建的） |
| `fingerprint()` | **语义不变**（第一节的全部意义所在） |
| `EnergyTerm`协议 | 法向项按现协议进；**协议本身不动** |
| `solve_equilibrium` | 要接return-map——**这是它第一次要处理"求解过程中会变的历史"** |
| `Scene.finalize` | 要多产一样东西：每对的`max_points_per_pair`与锚点布局 |
| spec/12 | 补接触节：第二节写"半个能量项"那条分界，第四节写return-map在牛顿迭代里的位置 |

**唯一真正有风险的是`solve_equilibrium`那一行**：牛顿法在活动集变化处**不可微**，
线搜索会在那里失效。0029第八节已经登记过一条同源的脆点（强非线性的全局化）。
**这条现在登记，不假装它不存在。**
