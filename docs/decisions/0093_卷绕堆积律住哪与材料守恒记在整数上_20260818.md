## 一、裁决一：三处"半径随卷绕生长"的关系——**新的那一份是中间缺的一段，不是第三份**

派活书要求"先裁清楚三者的关系，不许悄悄写第二份同样的东西"。逐处读过之后：

| 在哪 | 式子 | **自变量** | 走什么单位 | 它回答什么 |
|---|---|---|---|---|
| `drives.SpoolTension.radius_mm` | ``R = R₀ + n·t`` | **匝**``n`` | mm | 这卷现在拉得多紧（``T = M/R``） |
| `modelgen.generate_spool` | ``R_eff = (r₀ + m·τ)·L`` | **层**``m`` | 无量纲比值×特征长度 | 这卷长什么样（产出`FiniteCylinder`） |
| **新落的**`winding.WindingPack` | ``R = R₀ + (t/packing)·m(n)`` | **匝**，经``turns_per_layer``换成层 | mm | **匝怎么变成层、层怎么变成半径、长度怎么变成匝** |

**裁：新模块补的是`匝 → 层`的换算与堆积因子，外加`长度 ↔ 匝`。**
那两处旧式子各自都缺这一段：`drives`默认"一匝＝一层"（盘香式），
`generate_spool`直接吃层数、不知道一层里排几匝。

### 1.1 先纠正台账里一条已经过期的话

S5.3的`missing`原文是"**有效半径随层数生长引擎侧为零**（WDS有`WindingSurface`可搬）；
`modelgen.generate_spool`只做了静态几何"。

**这句话今天不成立。** `generate_spool`第245—247行、281行明写：

    筒的半径随已卷层数生长（WDS `WindingSurface.effective_radius_mm`）：
        R_eff = (barrel_radius_ratio + wound_layers · layer_thickness_ratio) · L

它甚至在绕满溢出法兰外径时失败关闭。**"引擎侧为零"是错的，"只做了静态几何"是对的**
——生成器产出的是一个形状，不是一条随过程走的律。
这一格建议在合入时按证据重写`missing`（本页第六节"能力位建议"给了措辞）。

**这道门保证两份式子今天说的是同一句话，保证不了明天有人只改其中一份。**
登记成GAP（第五节）。

同一形制的第二道门守`generate_spool`那一侧：取`cases/generator_determinism`

与生成器产出的``FiniteCylinder.radius_mm``逐位相同（都是``68.0``）。

### 1.3 `layer_advance`两个形制不是口味

* ``"continuous"``——**盘香式**（pancake / edge-wound）：每匝即一层，半径随匝连续长。
  HTS带材绕单饼线圈是这一类，`drives`那一份是它的``turns_per_layer = 1``特例；
* ``"stepped"``——**排绕式**（traverse-wound）：一层排``turns_per_layer``匝，
  层内半径不动，跨层才跳。`generate_spool`的``wound_layers``说的是这一类。

**没有默认的"随便"档**：同一组参数下两者给出不同半径，猜错一个方向就是一整层的误差。

### 1.4 ``turns_per_layer``不该是调用方随手给的一个数

它由几何决定：``⌊W_channel / w_tape⌋``，而``W_channel``正是
`modelgen.generate_spool`的``barrel_width_ratio × characteristic_length_mm``
（那个参数的文档写着"即两片法兰内侧面的轴向间距，对应WDS的``flange_channel_width_mm``"）。
落成`winding.turns_per_layer_from_widths`——**这是本页把生成器那一侧接进来的第二根线**
（第一根是1.2那道逐位门）。

**取下取整不是四舍五入**：排不下的那小半匝去下一层，``round``会让
``47.9/12``报出4匝而第4匝有0.1mm在法兰外面。必红实测：改成`round`红2处。
**带比槽宽是失败关闭而不是"每层0匝"**——返回0会让`WindingPack`因
``turns_per_layer < 1``而炸，但那时报出来的是"每层匝数不合法"，
**读的人查不到真正的原因是带装错了盘**。

## 二、裁决二：长度是半径的积分，不是半径乘匝数

    L(n) = ∫₀ⁿ 2π·R(s) ds = 2π · Σ_{k<n} R(k+½)

两条常见的错写法各自错在一头：``2π·R(n)·n``把整卷当最外一匝、``2π·R₀·n``当最里一匝。
中点半径``R(k+½)``让"逐匝周长之和"与积分**恒等**——``R(s)``在一匝内要么线性
（连续式，中点法则对线性被积函数精确）、要么常数（台阶式），两种都不是近似。

**这条恒等式的价值在于分辨力**：把中点写成``R(k)``或``R(k+1)``（半径更新晚一匝／早一匝），
**任何单点半径检查都照过**——差一匝只差一个``t``，在任何"rel 1e-6"的判据下是绿的——
而求和当场差``2π·n·t/2``，13匝那一档``≈408mm``。

### 2.1 "零容差"在本页里是什么意思，以及它凭什么能成立

**是浮点``==``，不是"1e-15"。** 三处判``==``各自说明了理由：

* **提出2π之后的半径积分**：``Σ_{k<n} R(k+½) == ∫₀ⁿ R(s) ds``。
  参数取2的幂之和（``64``、``0.5``、``1/512``），乘加全程无舍入。
  五种形制×32个匝数全部逐位相等；
* **与`drives`／`generate_spool`的退化对应**：见1.2；
* **喂料段账**：整数，与浮点无关。

**带``2π``的长度那一版判的是实测相对偏差**（最坏``2.2573e-16``，判``1e-15``）。
``2π``是恒等式两边的公因子，乘进去之后剩的是这个浮点常数的舍入，**那不是守恒的问题**。
把两件事混着说"长度守恒是零容差"是吹的，本页不这么说。

## 三、裁决三：喂料这一侧——**顺着拉格朗日走，欧拉式材料注入不做**

派活书第3条问的是"扩展`feed.py`还是另起一个欧拉式的"。

**裁：扩展，且只加接线；欧拉式不做，留空并登记GAP。**

理由不是"来不及"，是**它是一次新裁决**：`feed.FeedFront`是拉格朗日的
（每个节点始终是同一块材料），而0050那条承重条款（布局定长⟹指纹跨步不变）
与0062丙1整个建立在"节点是物质点"上面。改成欧拉式要重裁"节点是不是物质点"，
那会动到`fingerprint()`的语义。plans/18第五节的契约第3条明写"不确定就留空或模块化，
不阻塞"，本页照办。

`feed.py`因此只加了两样**纯追加**的东西：一个整数原语`fed_segment_count`，
与两段交叉引用文档。**既有字节形制、方法签名与七条已有的门一个字没动。**

### 3.1 材料守恒**记在整数段上**，不记在浮点长度上

    segments_fed == segments_in_free_span + segments_on_spool

这是**整数恒等式**，判``==``、零容差、与浮点求和次序无关。

**为什么不记在长度上**：``k·h``与``(k−1)·h + h``在浮点上不是同一个数
（``h = 0.1``、``k = 4``时差一个ulp）。把守恒写在浮点长度上，"零容差"就只能靠
``h``恰好二进制精确来兜——**那是运气不是形制**。实测把这份运气量了出来：
``h = 0.1``时1392个喂料档里**373档**浮点长度逐位不守恒，最坏相对偏差``2.2170e-16``；
``h = 0.25``时处处逐位守恒。**整数恒等式对两组都成立。**

### 3.2 落位前那个``min``是记账不是钳位

``segments_in_free_span = min(已喂段, 跨距段)``。前沿还没走到盘上时盘上恰为0段——
那些料**真的还在跨距里**，恒等式两边都认，不需要为"落位前"开一个特例分支。

## 四、抓到的空门与真缺陷（本页最值钱的一节）

### 4.1 空门一：守恒恒等式对"两边同时错了一个常数"是**盲的**

必红实测里，把``segments_in_free_span``的``min``删掉——让跨距无条件吃掉
``free_span_segments``段——**整数守恒那道门一条都不红**：
``7 + (k−1−7) == k−1``在``k < 8``时照样成立，只不过**盘上是负的**。

**这是plans/09教训一"两处各说各的"的数值版：两边各自自洽，合起来无意义。**
补了`test_the_spool_never_holds_a_negative_amount_of_material`
（另在conformance里补了同形的一条），那个变异体从**0红**变成**1红／3红**。

### 4.2 空门二：金标与被验量出自同一支笔，实测偏差因此恰为``0.0``

`generate_oracle.py`的`_concentric_length_mm`第一版写的是``2π·(R₀n + t·n²/2)``——
与`winding.radius_integral_mm`**逐字符同构**。于是"金标 vs 被验"相对偏差恰为``0.0``，
那条oracle当时**验不了任何东西**。

改成机械手册的**平均直径式**``π·n·(2R₀ + t·n)``之后，两边代数恒等而结合次序不同，
那个零变成了真的舍入（``1.5794e-16``）。

**结论写进案例页第2.1节：相对偏差恰好为零，往往是金标出了问题，而不是实现特别好。**

### 4.3 空门三：拿冻结值对它自己

``spiral_arc_length_mm``（真阿基米德螺线的弧长）原本住在oracle的``expected``里，
而引擎**有意不算**螺线弧长——于是conformance测试只能把``case.expected[...]``
原样喂回``check_all``。那一格当时**永远绿，验的是JSON读得对不对**。

已挪进``inputs``：``expected``的语义是"**被验内核应当产出什么**"，参照量不属于那里。

### 4.4 一对互相矛盾的容差声明

``relative_deviation``判``rel 1e-5``而由它取``log₂``得来的``observed_order``判``abs 1e-6``。
**后者比前者紧**——1e-5的相对搅动在阶上是约``2.9e-5``的绝对量，
于是那两格是一对不可能同时成立的声明。已改成``1e-4``并把推导写进理由列：
**下游量的容差要从上游推来，不能另立。**

### 4.5 一条真缺陷：`turns_at_length_mm`的数值稳定写法**验收不完整**

反解走``n = 2S/(R₀ + √(R₀²+2cS))``而不是``(−R₀ + √(R₀²+2cS))/c``，
因为后者在薄带（``c → 0``）时是两个几乎相等的数相减。**但把它换成坏的那一支，
`tests/test_winding.py`只红2处、conformance只红1处**——两处的参数都还没进到严重相消区。

**这说明"数值稳定的写法"这件事只有薄带极限才验得动**，而本批没扫到那一角
（``t/R₀ < 1e-6``且``n < 1``）。写进案例页"已知失效清单"第2条，解封条件是S5.6。

## 八、本页不主张什么

* **不主张引擎会算真螺线的落位点**。`winding`的长度是**同心圆理想化**，
  案例第三条oracle量的正是这个理想化的误差预算（``ε = 7.81e-3``时``7.06e-7``，二阶）。
  真螺线几何是`laydown`的中心线语义（S1.3），本页没碰；
* **不主张场景⑤能跑通**。S5.2（自接触）、S5.5（带-带摩擦）、S5.6（张力传递）
  三位一个都没动，而plans/04第八节把"匝怎么叠、张力怎么传"与"半径怎么长"
  并列为本场景三问——**本页只答了第三问**；
* **不主张`packing_factor`是从真机标定来的**。它是一个声明期入参，
  本仓不对任何一卷真实带材的堆积因子做声明。
