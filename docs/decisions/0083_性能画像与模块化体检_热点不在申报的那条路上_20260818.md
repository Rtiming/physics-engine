## 三、复测一条本仓自己申报了很久的复杂度：**稠密LU今天不是瓶颈**

[0030](0030_欠账清理_20260805.md)第四节申报：

> 求解那一步是稠密LU：实测成本按自由自由度约``n^2.6``增长……
> **它是全仓当前最陡的复杂度，也是下一个在册杠杆。**

`solve.py`的文件头至今照抄着这句话。**实测与它相反**：

* `solve_equilibrium`的**自时间只有2.067秒**（205.5秒里的1.0%）；
* 它的cumtime是75.23秒，但那75秒**几乎全在装配层**——
  `energies.py:1114 hessian_entries` 一个函数就cum 40.75秒（21180次调用）；
* `solve.py:88 bandwidth_of` 1.348秒也比求解本身可观。

**结论**：0030那条声明**不是错的，是在当前规模上不适用的**。
链式Hessian半带宽恒为2，带状消元已经把求解压到`O(m·b²)`，
于是`accept full`这个规模（27116次调用、每次几十到几百自由度）上
**装配完全盖过求解**。

**要动LU得先有一个真正大规模的消费方**——没有那个消费方之前，
优化LU属于本仓明令不受理的那一类（spec/13第一节义务1：
"**没有热点数据的优化提案不受理**"，而热点数据现在说的正是"不在这里"）。

**为什么这条要单独留痕**：本仓刚栽过一次"转述失真变成一个进位"。
一条申报了很久、**没人复测过**的复杂度声明，同样属于该被复测的东西。

## 四、改了什么：两处，都在"声称结果不变"那一档

### 4.1 每步重建走**直接构造**，不走`dataclasses.replace`

`SpanTransportLoop.step`与`ClosedTensionLoop.step`末尾的
`replace(self, ...)`换成直接调本类构造器并逐字段列出。

**语义逐字相同**：两类的全部字段都是`init=True`、没有`InitVar`，
`replace`做的就是"把未覆盖的字段读出来再调一次`__init__`"。
省掉的只是标准库每次都要重走一遍的`__dataclass_fields__`自省与kwargs字典。

**`__post_init__`照常跑，一条校验都没有被跳过。**
——这一点要说死：本仓有`_from_validated_pairs`那种"跳过校验的私有构造"的先例，
**本处不是那种**。派活方的第2条要求（"既有的重建即重验如果本身在挡什么，
要说清你把它挪到哪去了"）在这里的答案是：**没有挪，一条都没动**。

### 4.2 两个校验器加一条**派发上的**快路

`transport._require_finite` / `transport._require_positive` /
`tension_control._require_finite`的第一行原本是两次`isinstance`。
现在先判`value.__class__ is float`：

```python
if value.__class__ is float:
    if math.isfinite(value):
        return value
    raise TransportError(f"{name} must be finite: {value!r}")
<原来的四行，一个分支都没删>
```

**为什么这不是"省掉校验"**：`value.__class__ is float`成立意味着类型**已经确定**
不是`bool`、不是`int`、不是`float`子类；而对一个`float`来说
`float(value) is value`——**返回值逐位相同**。其余一切类型（含`float`子类）
原样落到下面的慢路。

### 4.3 逐字节对拍的证据

判据**不比最终产物**。理由是当天一个活生生的反例：`autodiff.ad_dot`的融合路径
与float路径**在每个顶点上本来就不同**，而判总和的那道门一直绿——
**靠的是求和时误差抵消，换台机器就红**。

因此对拍判的是**还没被求和的那一层**：`tools/parity_transport_samples.py`
把`SpanTransportSample`与`TensionControlSample`的**每个字段、每一步**
用`float.hex()`打出来，工况取`cases/closed_loop_tension_step`与
`cases/free_span_tension_step`的声明输入（5个工况、共**158818行**）。

## 五、`contact_pipeline`补上一条"h相对接触刚度"的步长上限

### 5.1 缺的是什么

research/17第五节逐条核过：显式积分＋接触有**两条独立的**时间步上限，
而本仓只声明了一条。

| 上限 | 挡的物理 | 本仓此前 |
|---|---|---|
| `h < 2.785/\|ω\|_max` | **转动模态** | `rigidbody.RK4_BODY.declaration.step_bound`，有 |
| TinyDEM式49 `Δt = Rmin√((1−ν²)/E)` | **罚刚度模态**（弹性波穿过颗粒） | **一条都没有** |

`contact/`目录今天没有任何一条"h相对接触刚度"的上限声明。
research/17的原话：M6若给罚刚度定值，"**必须同时声明一条h相对刚度的上限**，
并写明这是刚度模态不是转动模态、两条独立、取更紧的那个——
否则会重犯`rigidbody.py`已经很小心避开的那类错
（'看似有一条`step_bound`、其实只挡了一半物理'）"。

### 5.2 **不照抄TinyDEM那个式子**，理由是量纲

`Rmin·√((1−ν²)/E)`按字面**缺一个密度因子**：量纲上`[R]·√(1/[E])`不是时间，
补上`√ρ`才是（`R·√(ρ(1−ν²)/E) = R/c`，`c`是弹性波速）。
它是一份把密度吸收进常数的工程写法，**照抄进本仓会变成一个量纲不齐的判据**。

本仓用等价而量纲齐全的那一支，且它**在仓里已经存在**：
`contact/damping.py`的`linear_dashpot_parameters`早就在算`ω0 = √(1000·k/m_eff)`
与`stability_rate_per_s`。缺的从来不是这个量，是**一条把它读成步长上限的声明**。

### 5.3 落地形制

`src/physics_engine/contact_pipeline.py`新增：

* `CONTACT_STIFFNESS_STEP_BOUND`——**一句可引用的声明**，形制对齐
  `integrate.IntegratorDeclaration.step_bound`（上限是被声明的，不是被口头说的）；
* `RK4_STABILITY_RADIUS = 2.785` / `EXPLICIT_EULER_STABILITY_RADIUS = 2.0`
  ——**上限的分子属于积分器、分母属于物理**，两条上限只在分母上不同；
* `contact_stiffness_step_bound(...) -> ContactStiffnessStepBound`
  ——中间量（`ω0`、`ζ`、`stability_rate`、约化质量）全部进结果。
  理由与`SolveResult.backtracks`同源：**一个只给最终数字的上限，
  读的人无法判断它是不是算错了**；
* `governing_step_bound(...) -> GoverningStepBound`
  ——"**取更紧的那个**"这句话的执行体，返回值同时报出**是哪一条在管**
  （`contact_stiffness`／`rotational_mode`／`both`）。只报数字不报出处不行，
  research/17抓到的正是这个错；
* `SphereContactPipeline.stiffness_step_bound(context)`
  ——扫**全部声明候选**取最紧的一条，**不扫活动集**：定步长显式积分器
  在撞上的那一帧才发现步长太大已经晚了，那一步已经跨过去了。
  "现在没接触"不是"这个步长安全"的理由。

**没有碰`contact_dynamics.py`**（M4正在同一个文件上），也没有碰`contact/`。

### 5.4 注错验证第一轮（11条，每轮清`__pycache__`）

| 轮 | 注错 | 结果 |

### 5.5 一处**声明容差**而不是逐字节的地方，如实写明

`ω0`两边输入逐位相同、式子逐字相同 → **逐字节对拍**（`float.hex()`），

但`ζ`是**往返**出来的（那边由ζ算`c`、这边由`c`反算ζ），中间过了一次浮点乘除，
**往返不是逐位运算**。实测e从0.999到0.001共12点，`ζ`与`stability_rate`的偏差
**最大1 ULP**（相对1.85e-16与1.78e-16），判据取`rel=4e-16`（约2 ULP），留一倍余量。
**不是放宽到能过——是把往返的舍入算出来再留余量**（0024第三节的先例）。

## 六、M7 依赖图体检：**结论是"今天不该拆"**

### 6.1 五者的实测依赖（AST静态扫，全包）

```
rigidbody         → energies, geometry, integrate, shapes, state
rotation          → energies, state
contact/          → energies, laydown, rotation, solve, state
contact_dynamics  → rigidbody
contact_pipeline  → collision, contact, energies, scene, shapes, state
```

反向：`rigidbody ← contact_dynamics`；`rotation ← contact`；
`contact ← contact_pipeline`；`contact_dynamics`与`contact_pipeline`**无人依赖**。

**全包扫描无环。** 域隔离门（5条）与公开面清册门在本worktree全绿
（`tests/governance`除两条**结构性**失败外全过——见第八节）。

### 6.2 对照research/17第六节的同行分层

同行分层是：`broad → narrow（法向/穿透/杆臂）→ 力矩装配 → 积分器回调`，
且**积分器不该知道接触**。逐条核：

| 同行的那一层 | 本仓 | 符合？ |
|---|---|---|
| 积分器不知道接触 | `rigidbody`的import里**没有一条**指向`contact*` | ✅ 符合 |

| 接触**产出**几何量喂给装配层 | **不符合，见下** | ❌ |

### 6.3 **一处不符合：那条边今天是断的**

research/17第六节要的是"`contact_pipeline`产生几何量（法向、穿透、**杆臂**）
→ 力矩装配层"。实测：

* `contact_pipeline`的`ActiveSphereContact`产出的是
  `penetration_mm` / `radii_sum_mm` / 两个节点下标 / 刚度阻尼——
  **没有法向，也没有杆臂**。它产的正好是**准静态罚势**要的那一组，不是装配层要的；
* `contact_dynamics`只import`rigidbody`，**与`contact_pipeline`之间一条边都没有**。
  杆臂与力由**调用方**手工提供。

**这不是环，是断链**：分层的形状对了，中间那一节今天由使用者用手接。

### 6.4 裁决：**不拆、不接，写清理由**

1. **接那条边要先裁一件没裁的事**。`contact_dynamics`文件头自己声明"不做多体"，
   而球-球两个都在动时"杆臂各取谁的半径"**没有裁过**。
   在那之前接上等于把一个未裁的选择固化进依赖方向；
2. **今天没有第二个消费方**。本仓纪律是"**不为想象中的第三个消费方预支通用性**"
   （0035那条判据的原话："`state`升基座……**否决**，理由是今天没有任何光学代码需要它"）。
   动态球-球接触今天走的是准静态罚势那条路，转动那条走的是`contact_dynamics`，
   **没有任何一个消费方同时要两条**；
3. **M7的硬约束是"既有产物逐位不变"**，而拆动的收益今天是零——
   没有任何门、没有任何案例因为这条边是断的而变红或变慢。
   **一次不改变任何输出、不解锁任何能力位的搬动，是纯风险。**

**触发条件**（哪天重开）：`contact_pipeline`第一次需要产出法向或杆臂时——
那意味着有一个消费方真的要把动态检测接到力矩装配上，届时先裁多体杆臂，再接边。

### 6.5 顺带记一条**事实**，不是问题

接触子系统今天**通过两条路各自认识一套转动表示**：
`contact/stepper → rotation`（指数映射，准静态）与
`contact_dynamics → rigidbody`（四元数，动态）。
[0074](0074_真实网格进接触_碰撞归本仓_距离场是根本形制.md)第四节已裁：
**同一个群的两种参数化，不是两套互不认识的转动状态**。
其**后果**要写出来：**同一个体今天不能同时走这两条路**。
0063第六节已记过"没有消费方需要同一个体同时走两条"，本页只是把它在依赖图上确认一遍。
