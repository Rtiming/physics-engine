# 0016 数值加速档：核心零依赖 + 可选NumPy加速档（2026-08-05，用户裁决，解0015张力A）

状态：已裁决。取**甲案**——`physics_engine`核心保持`dependencies = []`，
数值内核写成可替换形式，检测到NumPy即走加速实现，两实现以对拍为进仓门。
乙案（NumPy升为运行时依赖）不采纳。

## 一、裁的是什么

0014立的零设施承诺（运行时零依赖、单wheel离线安装）与"真求解器要快"直接冲突：
纯Python的稠密线性代数与逐节点循环跑不过NumPy/BLAS。本裁决在不破承诺的前提下
拿到速度。

## 二、三条执行条款

1. **核心零依赖不破**。`pyproject.toml`的`dependencies = []`保持不变；
   `import physics_engine`与其全部公开操作在**没有NumPy的机器上必须可用**，
   离线单wheel安装的承诺原样有效。NumPy进`[project.optional-dependencies]`
   的加速档（暂定名`accel`），不进核心。
2. **数值内核按可替换形式书写**（spec/13规则2既有条款的兑现）：
   无状态纯函数 + 显式状态数组，数值命名空间收窄到可替换
   （纯Python实现 ↔ numpy ↔ 将来的cupy/jax同形制）。
   **后端只执行声明好的数学，永远不得重新定义物理**（spec/13规则1）。
3. **两实现对拍是进仓门**。任何有加速实现的内核，随批附
   纯Python与加速实现的对拍：声称结果不变的走**逐字节对拍**，
   数值路径不同的走**分量声明容差**的对拍（spec/13第一节义务2）。
   对拍缺失即不得合入。加速档与核心的差异等级按spec/13规则5申报确定性等级。

## 三、承认的代价

两套实现要长期并行维护并一直对拍。这是本方案的真实成本，接受它的理由是
它同时守住0014的零设施承诺与0015的性能要求；而"可替换数值命名空间"本来
就是spec/13为后端预留的接入面，不是为本裁决新造的概念。

## 四、由此解锁与仍被阻塞的

- **解锁**：plans/02的T4力学地基轨可以确定数值书写形式并开工（仍需第二个
  前置：力学域规范面`spec/12`）；T5搬迁轨的内核形态随之确定。
- **仍阻塞**：光学域进不进引擎（FTS光学全线依赖numpy——本裁决使"进来"
  在技术上可行：其数值路径落加速档、核心保持可选，但归属本身仍待裁决）。
