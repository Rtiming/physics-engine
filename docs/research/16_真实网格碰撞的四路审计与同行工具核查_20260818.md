# 16 真实网格碰撞：四路审计与同行工具核查

日期：2026-08-18
状态：**审计与调研记录**。不加能力、不改分母、不裁任何事。
用户口径"我们是要针对WII里面相关的模型直接跑的是要有真实的物理碰撞等东西的，
你再重新审阅一下看看到底缺什么，以及去调研一下有哪些开源的已经有的工具"。

四路并行：WII资产清单／WII碰撞栈与坐标约定／WII网格质量与工件形态／同行开源工具。
所有数字都可复算，脚本与命令注在各节。**查不到的写"没查到"，不推测。**

## 零、一句话

**"拿WII的模型跑真实物理碰撞"这件事，已经有一半做完了，而那一半不在本仓。**

WII那边**已经有一套真实的三角网格碰撞引擎**（自研NumPy＋BVH，可选FCL前置粗筛），
它给得出最近距离、穿透深度、接触点与接触法向；
**它缺的是力**——全仓没有任何接触力模型，判定停在几何层。

本仓正好相反：**有力没几何**。罚法向、粘着弹簧、库仑与椭圆摩擦、准静态步进、
动态检测—响应流水线都在，但形状只到球／胶囊的闭式窄相，`MeshAsset`只带一个**声明的**AABB。

**所以缺口不是"再写一个网格窄相"**——那会重复WII已有且更成熟的一套，
而且本仓零依赖意味着只能纯Python自造（第四节的调研确认市面没有可用的现成件），
同时源码余量只剩26259字节。**缺口是那条把几何接到力学上的缝，以及它下面压着的转动自由度。**

## 一、WII有什么模型（资产清单）

**结论：真实资产是完备的，而且已经是"visual/collision两套"的成熟形制。**

| 处 | 数量 | 形制 |
|---|---|---|
| `tool-visuals/` | 6个二进制STL（collision 3、visual 3） | 三对同一实体的**简化碰撞版＋精细外观版** |
| `static-visuals/` | 6个二进制STL | 工位静态件，最大的33.5万三角 |
| `optimized/` | 7个glb（另有13个机器人连杆glb） | glTF2，供前端 |
| `collision-audit/` | 22个二进制STL | 场景快照，含KUKA六连杆的碰撞版与精细版 |
| `workpieces/` | 39个目录、20个STEP＋62个STL | 工件，STEP由OpenCASCADE 7.9导出 |

**collision与visual是同一实体的两版**（包围盒逐轴相同、三角数差数十到数百倍）：
`e1_carrier` 336对128666、`e1plus_new` 1320对153156、`fixed_module` 696对24490。

**最要紧的一条发现**：`tool-visuals/collision/`与`static-visuals/collision/`下
各配一份`*.collision.bounds.json`，schema是`winding_pose_solver.collision_bounds.v1`、
`strategy: "surface-aabb"`、`grid_cell_mm: 60`，内容是**一组AABB而不是一个**：
`e1_carrier` 28个、`fixed_module` 58个、`e1plus_new` 110个、
`static_009_new` 5128个、`static_009_new1` 5104个。

> **一个非凸体在WII那边已经被表示成AABB的并集了。**
> 而AABB并集是本仓今天的形状词汇**已经能表达**的东西（`RoundedBox`／`FiniteCylinder`），
> 不需要三角形，也不需要凸分解。这一条改变了"从哪儿下手"的答案。

**另一条会影响判断的**：`workpieces/`看着有39个目录，但**其中15个的`centerline.csv`字节完全相同**
（`sha256 = 487988693d15fb31…`，同一个`coil_4`骨架被原样导入15次，只改了目录名与config里的`name`）。
真正互不相同的骨架只有6条（`v1-coil-1/2/3/4`、`v2-coil-01/02`），
而**这6个目录反而都没有挂STL**，只有centerline。
**"我们有几十个真实语料"是个错觉。**

## 二、WII的碰撞是怎么算的

**结论：Python一套自研NumPy三角网格引擎，FCL只当保守前置粗筛；有穿透深度，没有接触力。**

* **broad phase**：`collision_broadphase.py`（414行），axis-sweep AABB候选对；
  AABB重叠判定在`collision_geometry.py:124 _aabb_overlap`；
* **空间结构**：自己写的`TriangleBVH`（`collision_assets.py:71-77`，叶子96三角），
  `requirements.local-worker.txt`声明了`rtree`但源码零import；
* **narrow phase**：`collision_narrowphase.py`（460行），先按面法向分离下界剪枝，
  再对幸存三角对算**精确距离平方**——"6点-三角 + 6段-三角相交 + 9段-段"；
* **FCL的身份**：`collision_fcl.py`把`python-fcl==0.7.0.8`用作**保守前置过滤**，
  文件自述"被FCL否掉的对进不了昂贵的Python三角路径"，
  **产出细节的仍是自研引擎**。后端由请求参数`collision_backend`选（`auto`／`fcl`／`python`）；
* **返回的是数不是布尔**：`minimum_distance_mm`、`minimum_overlap_mm`、`clearance_mm`，
  FCL路还给`contact.penetration_depth`、`contact_position_mm`、`contact_normal`；
  顶层的`collision_free`是对这组数的汇总，不是原始判据；
* **没有力**：全仓搜`contact_force`／"接触力"零命中。
  另有一层CHOMP式可微距离场（`collision_distance_field.py`），
  但它自己写明"**不替代碰撞判定**……只可用于排序"；
* **JS侧没有第二套实现**：`motion-module`只把请求转发到`/api/collision/check`并做高亮与报告校验。

**关键词核查**：`GJK`／`EPA`／`SAT`／`bullet`／`pybullet`／`rapier`／`cannon` 在三个包的`src`下**零命中**。

### 2.1 坐标与装配约定（接线时会用到）

* **单位统一mm**，多处独立声明（`LENGTH_UNITS_TO_MM`换算表、`frame_math.md`、
  manifest的`units: "mm"`、场景文件`units: mm`、字段名一律带`_mm`后缀）。
  渲染/加载路径上**查不到0.001或1000的缩放**——网格本身就是mm尺度；
* **位姿是4×4齐次矩阵**（`bind_pose_robot`、`visual_pose_correction_robot`），
  **不用四元数或欧拉角字段**；**仓内没有`.urdf`**，装配走
  `model-manifest.json`（静态绑定）＋运行时`winding-scene.json`（逐帧FK）两层JSON；
* **右手系、Z轴朝上**（`camera.up.set(0, 0, 1)`，网格地面从Three.js默认的Y-up绕X转90°）。
  **文档与代码有一处不一致**：`animation_system.md:154`说要做"Y-up ↔ Z-up转换"，
  而实际代码全程Z-up、不做中转——以代码为准；
* **没有单一世界原点**：原点由一条相对刚体变换链逐级给出
  （`parent_frame → frame2 → carrier_base → e1_axis → workpiece`）。

## 三、那些网格的质量（**这一节决定哪些近似不能用**）

**结论：collision网格既不凸也不都封闭。任何"当成凸体"的近似都会静默出错。**

| 文件 | 三角 | watertight | 凸性单侧检验通过率 |
|---|---:|---|---:|
| `e1_carrier.collision.stl` | 336 | **否**（6条非流形边） | 26.19% |
| `static_009_new.collision.stl` | 61536 | **是**（100%流形） | **0.15%** |
| `workpiece.collision.stl`（clean_a） | 16054 | **否**（10条非流形边） | 3.72% |

三个文件的非2次引用边**全部**是"≥3次引用"的非流形边，**一条开放边界边都没有**——
形态像是多实体布尔或多子网格拼接后没做焊接，不是"有洞的开曲面"。

**工件那一侧**：`whole-assembly.step`是真实的多零件B-rep装配
（10个PRODUCT、7个`MANIFOLD_SOLID_BREP`、10426张`ADVANCED_FACE`、71200个`CARTESIAN_POINT`），
STL由OpenCASCADE网格化导出。中心线来自另一个源网格`coil_4.stl`（**单位是米**，
而交付的STL是mm），二者同源但不同文件。

**联动校验只到身份级**：`gcw_bundle_import.py:1034 _verify_same_frame()`
比的是`frame_id`**字符串**一致，**不核对中心线点是否真的落在网格附近**。
只有"手工挂网格"那条旁路才做几何邻域检查
（`conforming_workpiece_import.py:195`，它的docstring自陈原因：
"GCW的bundle上真出过（整机STEP曾在源世界系，取件时静默飘出5.5米）"）。

**工件挂载位姿是CAD名义值，未经现场标定**——`workpiece-config.json`自述
"名义值，尚无现场校核……未经现场TOOL/BASE实测"。

## 四、同行开源工具核查（**结论决定了本仓不该做什么**）

### 4.1 纯Python无重依赖的窄相：**没有**

调研范围内找不到一个"纯Python＋仅numpy、无numba、无C扩展"的成熟GJK/EPA/SAT库。
最接近的`distance3d`（BSD-3，0.9.0，2024-02-23）把**numba列为必需依赖**，
而numba拖llvmlite——直接撞`dependencies = []`。
**推论：本仓若要在内核里长出窄相，只能自造，没有现成件可拿。**

### 4.2 能给"物理需要的那三样"的库

物理需要的是**穿透深度＋接触法向＋接触点集**，不是"碰没碰上"或最近距离。

| 项目 | 许可证 | 非凸-非凸 | 给不给那三样 |
|---|---|---|---|
| FCL / python-fcl 0.7.0.11 | BSD-3 | 走BVH，**不强制先凸分解** | 给 |
| Coal（原hpp-fcl）v3.0.4 | BSD-3 | 走BVH/heightfield/octree | 给，还给接触面片 |
| Bullet | zlib | **不支持运动中的非凸-非凸**，官方建议先凸分解 | 给接触流形 |
| MuJoCo | Apache-2.0 | **限定凸geom**（SDF插件例外），非凸要用户自己分解 | 给 |
| Drake hydroelastic | BSD-3 | rigid可吃非凸表面；compliant要预先给四面体体网格 | 给接触面片 |
| IPC-toolkit v1.6.0 | MIT | 直接在三角网格上做CCD | 产出是势垒梯度，**语义与刚体接触点不同** |
| Open3D / trimesh | MIT | — | **都不做真窄相**；trimesh直接把这活外包给python-fcl |

### 4.3 凸分解：V-HACD已死，CoACD活着

* **V-HACD**：BSD-3，仓库已标记`DEPRECATED & ARCHIVED`，最后发布v4.0（2022-04-07），
  **上游自己在README里导流到CoACD**；
* **CoACD**：**MIT**，v1.0.12（2026-08-13），2026年内已发6次，
  官方PyPI包`coacd`，平台覆盖含macOS arm64。

本仓0073第七节第1条已经写过这条的判例：Bullet把V-HACD vendored进`Extras/`，
最后提交2021-08-07，**于是被永久钉在一个已死库的副本上**。**核查确认那条判例成立。**

### 4.4 查看器

`meshcat`（MIT，服务端极轻、渲染全在浏览器）与`viser`（Apache-2.0）最贴合本仓
"自己不渲染、把产物交出去"的形态；`rerun`（MIT/Apache）时间序列回放最强但最重（Rust）；
`polyscope`／`trimesh viewer`偏静态查看，没查到内置时间线回放。

### 4.5 同行怎么分层——**共识很干净**

| 项目 | 凸分解在哪 | 窄相在哪 |
|---|---|---|
| MuJoCo | **核心之外**，文档直接建议用CoACD | 核心内 |
| Bullet | **核心之外**（`ENABLE_VHACD`是CMake开关） | 核心内 |
| Drake | 非凸体网格生成推到外部预处理 | 核心内 |
| PyElastica | 不做通用网格处理 | 核心内（rod专用，非通用窄相） |

**四家无一例外把窄相放在核心里，把凸分解放在核心外。**
本仓的特殊性在于：零依赖让"窄相进核心"等价于"自己用纯Python写一个"，
而4.1说明这条路上没有可借的现成件。

## 五、把两边并排：缺口到底是什么

| 环节 | WII有没有 | 本仓有没有 |
|---|---|---|
| 三角网格broad/narrow phase | **有**（自研NumPy＋BVH＋FCL粗筛） | 无（只有球/胶囊闭式） |
| 穿透深度／接触点／接触法向 | **有** | 只有球/胶囊那三类对能算 |
| 非凸网格 | **有**（本来就在非凸网格上跑） | 无 |
| AABB并集表示 | **有**（`collision_bounds.v1`，28—5128个盒） | 词汇有，**窄相没有** |
| 接触力／摩擦／平衡 | **无**（明文停在几何层） | **有**（罚法向＋粘着＋库仑/椭圆摩擦＋两条步进路径） |
| 转动自由度／力矩 | 不适用（它不做力学） | **无**（`state.py`强制`node_dof_count % 3 == 0`，`contact/`零力矩） |
| 刚体惯量 | 不适用 | **无**（`spec/11`：`MeshAsset`无质量模型） |

### 5.1 四条缺口，按依赖顺序

1. **几何→力学的接缝没有面。** WII已经能交出接触点/法向/穿透，本仓没有一个facet吃它。
   **纯接线，最便宜，且不需要任何新物理。**
2. **转动自由度。** WII的模型是刚体（KUKA连杆、载具、工件），刚体接触必然有力矩；
   本仓的接触体今天是**质点＋半径**。0051已裁"多点接触的前置是转动自由度"、
   0063量出不建它的代价（金字塔`μc`差1.392倍、斜面滚球加速度差1.4倍——
   **模型不会摇晃，它只是安静地给出一个偏了四成的数**），
   而且0063第五节第1步的金标**已经用精确有理算术算完**。**这是最硬的一条。**
3. **接触斑块／多点同时接触**（0051第五节登记，明确排在转动自由度之后）。
4. **网格质量属性**（惯量／质心，`spec/11`第二之二节，`capability_ledger` S3.3 todo）。

### 5.2 三条不该做的（都有出处）

* **不该在内核里重写一个三角网格窄相。** WII已有一套更成熟的，且4.1说明本仓只能自造；
  加上源码余量只剩26259字节（0069第五节裁"该由撞破它的批次自己带理由抬"）。
* **不该vendored凸分解库。** 0073第七节第1条的Bullet判例本轮核查成立（V-HACD已归档）。
* **不该把collision网格当凸体近似。** 第三节实测：凸性通过率0.15%—26.19%，三个全非凸。

## 六、本页没裁的

* **接缝往哪个方向定**（WII把接触事件推给引擎，还是引擎去查询WII的服务）——未裁；
* **AABB并集要不要成为第一条网格接触路径**（第一节那条发现指向它，但它同样要转动自由度
  才能表达"盒子被顶得转起来"）——未裁；
* **转动自由度走0063的路径A还是路径B**——0063已把两条路各自解的题分清，但没排期；
* **查看器选哪个**（4.4给了候选，没选）。

带材的接触伙伴是参数化的槽而不是三角网格、转动自由度的权威表示是SO(3)、
