# 引擎的使用面：三层用法与扩展规范（2026-08-04夜）

问题（用户原话）：其他工具都是怎么用的？是不是直接传参数就行、
肯定不用对库直接进行更改？我们能实现吗？

答案先立住：**对——"用户永不改引擎源码"是全行业铁律**，而且它是分
三层实现的，每层有自己的机制。改源码的只有引擎开发者本人。

## 一、三层使用规范（外部实测）

### 第1层：数据层——文件+一条命令（约九成用户住在这层）

- **MuJoCo**：场景内容100%住在`model.xml`（MJCF）里；用户侧五行——
  `MjModel.from_xml_path("model.xml")` → `MjData(model)` → `mj_step`循环
  （官方文档的规范用法）。换机器人、换重力、换时间步=改XML，不碰库。
- **Gazebo**：`gz sim world.sdf`一条命令起世界；headless加`-s`。
- **SOFA**：`runSofa scene.scn`同型。
- **参数研究的规范**：扫参=**生成一批变体文件**，不是改代码——与我们
  design/16 §5.1的实验清单（引用基础案例SHA、逐点生成闭包）完全同律。

### 第2层：脚本层——用户自己的入口代码调公开API（控制与编排）

用户写**自己仓里的**脚本：每步写`data.ctrl`、读传感、编排episode；
或纯API构造场景（PyBullet `loadURDF`/`createMultiBody`、Genesis
`scene.add_entity(morph)`）。用户代码永远在库外面——这正是用户问的
"写个入口代码+把参数传进去"的形态。

### 第3层：扩展层——新物理也不改库，走声明加载的插件

这层最关键，是"永不改库"能对**新能力**也成立的原因：

- **MuJoCo engine plugins**：SDF形状、执行器、传感器插件是一等扩展，
  **在模型XML里声明加载**，插件代码住在库外；
- **Gazebo system plugins**：**SDF文件里写`<plugin filename=… name=…>`**
  ——连"要加载哪些系统"都是世界文件的一部分，命令行插件先加载、
  SDF声明的随后（官方server配置语义）；
- **SOFA**：组件插件包，场景文件按名引用。

铁律的完整表述：**用=传文件；编排=库外脚本调公开API；扩展=库外插件包
+文件内声明加载。三层没有一层碰引擎源码。**

## 二、对照我们：一半已实现，缺口三件

| 层 | 我们的现状 | 缺口 |
|---|---|---|
| 1 数据层 | **WDS已达标且已验证**：`.case.yaml`+`case_cli run`，零代码用户路径，产物自动原子发布+指纹（这是别家没有的加强） | **引擎侧缺场景文件入口**——今天用shapes/collision要写Python |
| 2 脚本层 | **已达标**：v0.2.0 wheel+分档公开API，任何仓`--find-links`装上就调 | 无 |
| 3 扩展层 | 注册表形制蓝本齐全（WDS的ENERGY/CONTACT/case注册表、FTS的effects registry，全是"注册+失败关闭分发"） | 引擎侧的注册表与**文件内声明加载**未立（属M-E3装配层：finalize校验+registry） |

诚实边界（各家皆同）：自定义控制器永远是第2层的用户代码；真正的新
物理律（新能量项、新接触格式）永远是第3层的插件——**但都不改库**。
我们的门禁哲学反而把这条铁律焊得更死：库的受验字节绑着回执与指纹，
"顺手改两行库"在我们的体系里根本过不了门。

## 三、结论与差距清单

**能实现，且方向早已对齐**——WDS的案例引擎就是第1层的正确形状，
引擎仓补三件即到位：

1. **场景文件格式**（`scene.yaml`：体+形状+位姿+白名单，按轴1登记面、
   轴2单位、轴3寻址）——spec/11声明层的文件化；
2. **`pe-scene`CLI入口**（第一个动词：`check-collisions`，产物走
   run_package原子发布）；
3. **插件声明加载**（M-E3装配层，随第一个真实扩展需求落地，
   蓝本=Gazebo的SDF内声明+WDS注册表）。
