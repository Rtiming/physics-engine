### 每个栈最独特的那个设计判断（一句话一个）

1. **DOLFINx**：**弱形式是源代码，离散内核是编译产物**——用户写UFL（数学记号），
   FFCx把它编成C内核，DOLFINx只负责装配的编排。代价是整条链变成编译链：
   每个form在运行期JIT编译（CFFI），DOLFINx的**默认JIT超时是10秒**。
2. **Firedrake**：**同一门语言，换一套编译器，赌"把代数结构保留得更久就能生成更优的代码"**——
   TSFC先把UFL降到GEM（未调度的张量代数IR）、再降到Impero（已调度的IR），
   比FFC/UFLACS更晚才展平成标量循环。官方表述："TSFC aims to maintain the algebraic
   structure of the input expression for longer, which opens up additional
   opportunities for optimisation."
3. **MFEM**：**不装配矩阵**——partial assembly把算子分解成
   "全局自由度→子域→单元→求积点"四层，利用张量积结构直接算算子作用。
   官方称其"requires the optimal amount of memory transfers (with respect to the
   polynomial order) and near-optimal FLOPs for operator evaluation"。
   **限制官方也写明**："partial assembly is currently implemented for tensor-product
   elements (i.e. quadrilaterals and hexahedra). Partial assembly for simplex
   elements (triangles and tetrahedra) is planned."
4. **deal.II**：**维度无关的模板化编程**——同一份代码把`dim`换个数就在1D/2D/3D都成立。
   官方自述："deal.II is a state-of-the-art finite element library focused on
   generality, dimension-independent programming, parallelism, and extensibility."
5. **Elmer**：**没有API，只有输入卡**（`.sif`，关键字对格式），
   并且**把许可证按"库"与"模块"劈开**——库LGPL让你自己写的求解器模块可以用任何许可证，
   而现有物理模块留在GPL。这是一条用许可证做产品边界的判断，不是技术判断。
6. **SfePy**：**"term"（弱形式项）是一等公民**，问题描述文件就是Python数据结构；
   它同时是"黑箱PDE求解器"与"可以拿来搭自己应用的Python包"。
7. **preCICE**：**它不解任何物理**——黑箱分区耦合，两个既有求解器各自不改内部，
   只在耦合面上换数据。这是本清单里唯一一个"用不做什么来定义自己"的栈。
8. **PETSc**：**算法选择是运行期的命令行选项，不是编译期的类型**（`-pc_type jacobi`、
   `-ksp_type gmres`、`-snes_type newtonls`）。换求解器不改一行代码。
9. **Trilinos**：**按包分治，连许可证都按包分**——不能对Trilinos整体下许可证结论，
   要用哪个包查哪个包。
10. **scikit-fem**：**赌"不编译"这件事本身就是产品**——纯Python、零编译代码，
    换来的是`pip install`一行装完，代价是能力面窄。

## 二、算法层：我们该学的四件（本页核心）

逐条给"它怎么做的＋我们今天怎么做的＋差在哪＋迁移代价"。

### 2.1 装配：单元/形函数与物理分离

**他们怎么做（三层，缺一层形制就不成立）**

1. **单元与物理分离**：一套单元库（形函数、等参映射、求积点）服务全部物理；
   物理只提供"在一个求积点上、给定基函数值与梯度，本项贡献多少"。
   DOLFINx这一层由Basix（单元）＋UFL（物理）＋FFCx（把两者编到一起）三件分担。
2. **局部→全局的自由度映射**：单元算出一个小的稠密局部矩阵，
   再按一张`local_dof → global_dof`的映射表散射进全局矩阵。
   **物理代码从不知道全局下标。**
3. **稀疏结构与数值分家**：deal.II把这条做得最露骨——
   `DynamicSparsityPattern`（构造期，"only allocates as much memory as necessary
   to hold the currently added entries"）→ 压缩成`SparsityPattern`（CSR）→
   `SparseMatrix`只存值不存位置。理由官方写得很直白：
   "one often has several matrices that share the same sparsity pattern;
   examples include the stiffness and mass matrices necessary for time stepping schemes."

**我们今天怎么做**

`energies.py`（889行）里**四个能量项各自带一套硬写的离散**：

- `AxialStretch._edge_energy`：自己从`state.vector`按下标取三个分量、自己算delta、
  自己算范数与单位方向、自己算全局行列号；
- `LinearBending._stencil_vector`：另一套；
- `DiscreteElasticBending._vertex_terms`／`_vertex_blocks`：又一套；
- `UniformGravity`：还有一套。

**差在哪——但先说一件已经不差的**：0028落地的`hessian_entries`
（返回`(row, column, value)`流、注册表在`EnergyRegistry.hessian_entries`里汇总）
**已经是上面第3层的一半**——它就是COO形制，而且0039的`bandwidth_of`
直接吃这个流算带宽。**这条不必重学。**

真正差的是第1、2层：**今天每个能量项自己算全局下标**。
今天四个能量项，重复劳动还没到痛的地步；到第五、第六个就是纯成本。

**迁移代价：10²—10³行的重构，不是新功能。**
形态：定义一个`Stencil`（一组它触及的全局自由度下标）＋一个局部块，
让`quantities`返回"局部块＋映射表"而不是"已经散射好的全局项"。
**因为它是重构，对拍档位是spec/13第一节义务2的第一档：逐字节。**
这是好消息——逐字节对拍是我们最熟的那道门。

**一条必须同时说的话**：这条形制**不要求我们有单元库**。
"局部块＋映射表"对2节点边、3节点弯曲模板同样成立，
它只是把"每项自己算下标"变成"每项声明自己触及谁"。
research/09门槛2那个10³—10⁴行的单元库是**另一件事**，这条不依赖它。

### 2.2 线性求解的分派：按矩阵结构选算法

**他们怎么做**

- **运行期分派**：PETSc的`-ksp_type`（GMRES/FGMRES/BiCGStab/CG/TFQMR）与
  `-pc_type`（jacobi、sor、ilu、bjacobi、asm、**gamg**、hypre的**boomeramg**、
  ml、amgx、fieldsplit、bddc）是命令行选项。
- **稀疏直接解分三阶段**：MUMPS的Analysis（`Job=1`，做排序＋符号分解）→
  Factorization（`Job=2`，数值LU/LDLᵀ）→ Solve。
  **符号阶段可以复用**：结构不变、只有值变时不必重做。
  多前沿（MUMPS）与超节点（SuperLU）是这一层的两条主流实现。
- **迭代解＋预条件**用在直接解填充太大的地方。

**我们今天怎么做**

`solve.py`只有**两格**，判据是结构性的（`solve.py:216-220`）：

```
band = bandwidth_of(entries, position)
step = _solve_banded(reduced, rhs, band) if 2 * band + 1 < len(free) // 3 else _solve_dense(reduced, rhs)
```

0039实测链式Hessian**半带宽恒为2**（40/160/320段都是2），
端到端加速在320段上47.0×，且有一道门守着"半带宽不随规模长"这个前提。

**下一格该是什么、判据是什么——本节最要紧的一段**

先给一个必须先摆上桌的事实，它会改掉直觉的答案：

> **嵌套剖分（nested dissection）的复杂度对二维网格图是O(N^1.5)、对三维是O(N²)，
> 而且这两个界是渐近最优的——已被证明对任何消元排序都成立。**
> 填充量对应地是O(N log N)（2D）与O(N^{4/3})（3D）。（检索2026-08-05）

也就是说：**"上一个通用稀疏直接解"在三维问题上最好也只能到O(N²)——
而我们今天的稠密LU实测是n^2.6（决策0030第四节）。那不是一代之差，是0.6个指数之差。**

这不是纸上推导，有一个与我们同世界的实测印证。scikit-fem（纯Python＋SciPy，
零编译代码）README里的实测表（M2笔记本，P1四面体上的Laplace，
`scipy.sparse.linalg.spsolve`，检索2026-08-05）：

| 自由度 | 装配(s) | 线性求解(s) |
|---|---|---|
| 4096 | 0.02679 | 0.07657 |
| 8000 | 0.05288 | 0.33537 |
| 15625 | 0.11714 | 1.81805 |
| 32768 | 0.26042 | 11.48140 |
| 64000 | 0.54313 | **62.69441** |
| 125000 | 1.10499 | **nan** |
| 1030301 | 12.58563 | **nan** |

按4096→64000那两格拟合，**它的稀疏直接求解标度指数是2.44**
（`log(62.694/0.07657)/log(64000/4096) = 6.708/2.749`），
而125000自由度起干脆没跑完（表里是`nan`）。
**这就是通用稀疏直接解在三维拓扑上的天花板，测在一个纯Python栈上。**
对照：**我们的链式问题带宽恒为2，带状LU是O(m·b²)＝O(m)，是线性的。**

**结论：下一格不是"更好的直接解"，是"按拓扑分派"。判据是问题的图结构，不是矩阵的数值。**
三条判据，按拓扑维数分：

| 拓扑 | 半带宽 | 该走什么 | 我们今天 |
|---|---|---|---|
| 链／带状（一维） | 小且不随规模长 | 带状LU，**O(m)** | **已有**（0039） |
| 树／一维分支 | 排序后仍小 | 稀疏直接解，填充可控 | 无 |
| 二维网格 | 随规模长 | 直接解注定O(N^1.5) | 无 |
| 三维网格 | 随规模长 | 直接解注定O(N²) → **此时才轮到迭代解＋预条件** | 无 |

**而在破零依赖之前，还有一格更便宜的**：**对称分解（Cholesky／LDLᵀ）**。
理由三条，第三条最值钱：

1. Hessian是对称的——spec/12第3.1节已把"对称化后返回"写成义务；
2. 对称正定时省一半算术，且**不需要选主元**——不选主元意味着**带状结构不被破坏**，
   而0039第三节栽的那个跟头（高斯-约当上下都消把带状结构毁掉，
   收敛比从4.0掉到0.01）正是这件事的反面教材；
3. **分解过程中出现非正主元，本身就是"Hessian在此非正定"的检测器。**
   这一格顺手把2.3那件事的探针也做了——**一次实现，两个用途**。

### 2.3 非线性与时间：Newton的全局化

**他们怎么做（PETSc SNES／TAO，检索2026-08-05）**

- **求解器族**：`SNESNEWTONLS`（线搜索牛顿）、`SNESNEWTONTR`（信赖域，
  官方称"similar to the one developed in the MINPACK project"）、
  **`SNESNEWTONAL`（弧长延拓，用二次约束面追平衡路径）**、
  `SNESQN`（L-BFGS／Broyden）、`SNESNGMRES`、`SNESANDERSON`、
  `SNESFAS`（非线性多重网格）、`SNESNASM`／`SNESASPIN`。
- **线搜索类型**：`bt`（**三次回溯，默认**）、`basic`、`none`、`secant`、
  `cp`、`nleqerr`、`bisection`。
- **Hessian非正定的对策**（TAO的`ntr`/`ntl`）：
  "For problems where the Hessian matrix is indefinite, the perturbed system of
  equations is solved to obtain the direction, where ρ_k is a positive constant.
  If the direction computed is not a descent direction, the (scaled) steepest
  descent direction is used instead."
- TAO的三条全局化路线：`nls`（线搜索）、`ntr`（信赖域）、
  `ntl`（**信赖域＋线搜索兜底**：步被信赖域拒绝时退回线搜索）。

**我们今天怎么做**

`solve.py`：牛顿＋**二分回溯**线搜索（`scale *= 0.5`），无信赖域、
无载荷步生长、无同伦延拓、Hessian非正定无修正。
模块文档字符串把这些**全部如实申报了**（spec/12第4.3节的义务），
包括那句"不收敛就如实返回不收敛，不偷偷二分"。

`solve.py:247-252`那条失败分支写得很准：

```
"线搜索{max_backtracks}次回溯后仍无法降低能量——"
"这不是步长问题，是牛顿方向不再是下降方向（可能已在鞍点或Hessian非正定）"
```

**这句诊断是对的，但今天我们只能诊断不能治。** 决策0029已把这条登记为
"最担心的跨平台脆点"；research/09第2.3节第3条已如实登记
`large_deflection_cantilever`的参数是"可行点不是稳健区间"。

**差在哪：三格，按可落地性排**

| # | 该补的 | 学谁 | 代价量级 | 零依赖？ |
|---|---|---|---|---|
| 1 | **Hessian非正定时解加扰动系统（H＋ρI），方向仍不下降就退（缩放的）最速下降** | TAO的`ntr` | **10²行** | 是 |
| 2 | 三次回溯代替二分回溯 | PETSc的`bt` | 10¹—10²行 | 是 |
| 3 | 载荷步自适应／弧长延拓 | `SNESNEWTONAL` | 10²—10³行 ＋ **一整套收敛判据** | 是 |

第1条是全清单里性价比最高的一条：**它精确对准`solve.py:247`那条今天无解的分支，
而且它的探针（非正主元检测）可以由2.2的对称分解顺手提供。**

第2条的收益**必须实测，不许按理论宣称**——spec/13第一节义务1（profile先行）
与spec/12规则4（声明的阶数与实测的阶数不是一回事）都管这条。

第3条有一处**必须先解决的冲突**：`solve.py`现在的申报是
"它一次解一个载荷；不收敛就如实返回不收敛，**不偷偷二分**"。
**载荷步／延拓恰恰就是"把一个载荷拆成多个"**。
所以加延拓不是加功能，是**改申报**，要走决策记录。列入第七节。

### 2.4 自适应与误差估计：**本条的结论是"不抄"**

**他们怎么做**

deal.II的`KellyErrorEstimator`：按**解的梯度在单元各面上的跳跃**积分，
缩放因子`c_F = h_F/(2 p_F)`（`h_F`是面的直径、`p_F = max(p⁺,p⁻)`），
结果喂给`GridRefinement::refine_and_coarsen_fixed_number`／`fixed_fraction`。

**但本条最该学的不是算法，是那句诚实话。** deal.II官方文档自己写着
（检索2026-08-05，原文）：

> "Kelly estimator is not truly an a posteriori error estimator, even if applied
> to the Poisson problem only. It gives good hints for mesh refinement, but the
> estimate is not to be trusted."

一个业界标配的、被无数论文引用的误差估计子，**官方文档写"不要信这个估计"**。
这与本仓轴7"容差必须带非空`reason`"、spec/12规则7"有限差分门验不了物理"
是同一条纪律的三种说法：**判据要说清自己在验什么、不验什么。**

**我们今天怎么做**：人工加密＋收敛阶判据（案例里写死refinement阶梯）。

**差在哪 → 我的判断是这一条不抄，理由两条：**

1. **我们没有网格，h/p自适应今天无从谈起**——这一条挂在research/09门槛1之后。
2. **更要紧的是：我们今天的做法在判据强度上比它硬。**
   收敛阶是**可证伪的**（阶掉了就红），估计子是**启发式的**（官方自己说不可信）。

### 3.1 符号codegen那条路：实际能拿到多少倍，代价是什么

research/03第三节记着"**符号codegen**（其M5阶段B3，多日，必须逐字节对拍）"
是**单解唯一在册杠杆**。本节要给那句话补上它一直缺的数——
并且**把三件不同的东西拆开，不许混着说**。

**(a) codegen对手写内核的代数优化收益：局部7.9×，端到端2.8×。**

Kirby & Logg 2012（FErari，作为FFC的优化后端），实测：
"reduced local operation counts of a factor of as much as **7.9** and speedups for
the assembly of the global sparse matrix of as much as a factor of **2.8**"，
而同一篇摘要里另一句是 "FErari provides very little speedup"（在另一些情形下）。
（arXiv:1205.3027，检索2026-08-05）

**这是本页最该记住的一个数：局部运算数降7.9倍，只换到端到端装配2.8倍。**
差的那一截去哪了？去了散射进全局矩阵、去了几何量计算、去了循环外的一切——
**也就是2.1节那个"局部块＋映射表"形制里，局部块之外的那一半。**

**(b) 结构性优化的收益是指数不是倍数，但前提我们不满足。**

和积分解（sum factorization）在高阶张量积单元上把算子作用的复杂度
从`p^{2d}`降到`d·p^{d+1}`——deal.II的step-37原话是
"reduces the complexity for computing this product from p^4 to 2 p^3, where p-1
is the degree of the finite element…… or p^{2d} to d p^{d+1} in general"
（检索2026-08-05）。
**这是真正的量级杠杆。** 但它的两条前提我们一条都不满足：
①要有多项式阶`p`——我们的"单元"是2节点边与3节点弯曲模板，**没有阶**；
②要有张量积基函数（四边形/六面体）——我们**没有基函数**。
MFEM自己也写明partial assembly"currently implemented for tensor-product elements
…… for simplex elements …… is planned"。

**(c) codegen对解释执行的收益：本仓有自己的实测，不必引外部数字。**

公开来源对"C比CPython快多少"的量级说法是紧数值循环上10—100倍，
**但本页不引这个当结论**——它与具体循环强相关，属spec/13义务1要挡的那种"印象"。
本仓有更好的替代品：research/06第3.1节实测，梯度装配里
**真正的算术（`math.sqrt`）只占1.66%，包着它的迭代器机器（三个genexpr＋`builtins.sum`）占30.45%**。
那30.45%正是codegen能吃掉的那一段，**其Amdahl上限是1.44×**（research/06 A2已算过）。

**所以对本仓，符号codegen的诚实答案是：**

> research/03记的"符号codegen是唯一在册的两个量级杠杆"，
> **对WDS成立、对引擎今天不成立。**
> 那两个量级来自(b)与(c)：(b)我们没有单元因而结构性不适用；
> (c)我们已经用profile量到上限只有1.44×。
> **我们今天能拿到的是(a)那一档，而(a)的端到端实测天花板是2.8×。**

**代价**：编译链。DOLFINx每个form运行期JIT、默认超时10秒。
以本仓规模（N=512一次能量装配0.567ms，research/06第二节）算，
**一次10秒的编译要跑约17600次装配才摊平**。
这是`p≈1.05`的直接推论，第五节展开。

### 5.1 p≈1.05意味着哪些手段对我们无效（用户点名要）

research/06测得引擎能量装配的标度指数`p≈1.05`（R²≈0.99989），
含义写在那一页第一节："**没有可摊薄的固定成本，每个节点、每条边都各自付一次解释器的钱。**"

**先说本页调研中推翻我自己假设的地方，原文保留。**

我最初的假设是："`p≈1.05`说明我们的装配形制落后于那些向量化的栈——
它们批量摊薄，所以`p`会更低。"**核实之后这个假设不成立。**

用scikit-fem README那张实测表拟合它的**装配**指数
（1000自由度→0.00823s，1030301自由度→12.58563s）：

```
p = log(12.58563/0.00823) / log(1030301/1000) = log(1529.2)/log(1030.3) = 7.332/6.938 = 1.057
```

**scikit-fem的装配也是p≈1.06，跨三个数量级。而它是彻底NumPy向量化的。**

所以：**`p≈1.05`不是我们独有的病，是一个线性装配器该有的样子。
向量化改的是常数与可达上限，不改指数。**
这一条直接改掉了第二档第1条的**理由**——
换NumPy装配不是为了改指数（指数不会变），
是为了改那个常数、从而改可达的规模上限。**理由写错了，将来会拿错的判据去验收。**

**那么`p≈1.05`真正让哪些手段无效？逐条给理由。**

**（1）一切"摊薄一次性成本"的手段无效——因为分母上就没有一次性成本。** 点名两条：

- **符号分解与数值分解分离**（MUMPS的Analysis/Factorization分家、
  deal.II的`SparsityPattern`复用）。它的价值是"一次符号、多次数值"。
  **而我们今天走的带状LU根本没有符号阶段**——半带宽是结构性的常数2，不需要分析。
  **这个业界标配形制对我们今天的求解路径收益为零。**
  （它会在第三档第1条之后重新变得有意义，那时才谈。）
- **JIT编译缓存**。DOLFINx每个form默认JIT超时10秒；
  以N=512一次能量装配0.567ms算，**一次10秒编译要约17600次装配才摊平**。
  一次牛顿迭代一次装配、一次求解几十次迭代——**那是几百次求解才回本**。
  在"跑一个案例"这个粒度上，codegen的编译成本盖过它的收益。

**（2）matrix-free／partial assembly（MFEM的招牌）结构性不适用。**
它的收益公式是高阶张量积单元上`p^{2d}`降到`d·p^{d+1}`，
前提是有多项式阶、有张量积基函数。**我们两样都没有**（见3.1节(b)）。
MFEM自己也写明单纯形上还没实现。

**（3）GPU批量无效。** research/06 C1已给Amdahl论证（回调占87.24%，后端上限1.146×，
实测0.71—1.07×，小规模上NumPy还慢25—29%）。本页补一条`p≈1.05`特有的：
N=512一次能量装配0.567ms、梯度装配1.401ms，
而单次kernel launch是微秒量级——**只差两三个数量级，
而我们的规模上限（约1536自由自由度，决策0030）注定跑不到能盖过启动成本的批量。**

**（4）"更少更大的调用"（WDS的处方）无效。**
research/06第一节已经写了这条，本页只补一句诊断学上的话：
**这条处方对`p<1`的实现有效，对`p≈1`的实现无效，
而这两种实现同时存在于同一个项目的两个仓里**——
所以plans/02那条"消灭派发开销是当前唯一在册的大杠杆"
必须继续按research/06第六节(4)的订正读，不许回潮。

**反过来，`p≈1.05`让哪些手段仍然有效**（不写这一半就是把结论读歪）：

- **减少每节点做的事**——因为成本全在每节点上。research/06 A2上限1.44×。
- **改指数的那几层**——Hessian装配`p=2.02`（0028已做）、
  求解`n^2.6`→带状`O(m)`（0039已做，320段实测47.0×）。
  **本仓两次最大的收益都来自改指数，两次都不是靠摊薄。这是一条应当被记住的规律。**
- **把每节点的解释执行换成批量数组执行**（第二档第1条）。
  **它不改指数但改常数**，而scikit-fem给出了那个常数能到多少的实证。

## 七、要用户裁的事（本页不裁，列成清单）

1. **装配形制要不要现在抄？**（第一档第3条）我倾向"等第五个能量项"——
   今天四个，重复劳动还没到痛的地步，而重构要付逐字节对拍的成本。
   但"等到痛"意味着到时候要在赶工里做重构，这是已知的坏形状。**归用户。**
2. **载荷步／弧长延拓与`solve.py`现有申报直接冲突。**
   现在的申报是"不收敛就如实返回不收敛，不偷偷二分"；延拓恰恰就是把一个载荷拆成多个。
   要不要现在改这条申报？还是等到大挠度悬臂那个案例真的在别的机器上红了再改？
3. **LGPL在纯Python世界里的边界要不要现在定？**（4.1节末）
   0025那条"GPL类只对拍不复制"是在C库世界写的；
   `import`一个LGPL的Python包算不算动态链接，**本轮未核实**。
   今天不咬人，碰pyprecice（LGPL-3.0）那天会咬。
4. **要不要把scikit-fem列为第二个对拍同行库？**（0025形制）
   它是BSD-3、纯wheel、依赖只有NumPy/SciPy，**装进`validation/.venv`的成本几乎为零**，
   而它能给我们一个"同世界的第二个证人"。
   代价是0025第三节那四步在它每次发版时都要重跑一遍。
5. **2.4节那条立场（"有网格之前不做后验误差估计，收敛阶判据是替代物"）
   要不要写进spec/12或spec/13？** 写下来的成本是零，收益是挡住将来
   "要不要上误差估计子"这个问题被当成新问题重开一遍。
6. **research/03第三节那句"符号codegen是唯一在册的两个量级杠杆"要不要加口径行？**
   本页3.1节已给出它对引擎不成立的理由与数。**本轨道不改那一页，归用户裁是否要改。**
7. **`Matrix = tuple[tuple[float, ...], ...]`这个公开类型什么时候换？**
