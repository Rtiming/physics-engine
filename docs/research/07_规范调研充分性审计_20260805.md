# 规范调研充分性审计（2026-08-05）——十六页规范，逐页问它的证据从哪来

问题（用户原话）："看看我们相关的规范调研充分吗？如果不充分的话，你再补充一波调研。"

本页只审**证据**，不审规则对不对。一条规则可以完全正确而它的证据一句都不成立——
本仓已经有过多次"看似通过实则错"的教训，调研文档同理：**转述不等于核实**。
所以本页做三件事：给每页定证据来源与正本位置（第二节）、
挑最承重的断言去核原文（第三节）、把该补的排序（第五节）。

检索日期：2026-08-05。核不到的一律标"未核实"，不用似是而非的转述充数。

## 一、判定口径

三档，判的是**证据**不是规则：

- **充分**：页内每条承重断言，要么是本仓/消费方可当场复核的实测，
  要么有指向具体文档的外部锚点，且抽验属实。
- **薄**：有承重断言的证据链断在某处——引了外部但无正本、
  正本无抽验记录、或转述与原文有出入。**"薄"必须指出薄在哪一句**，否则本页自己就是一句空话。
- **无证据**：承重断言既无实测也无外部锚点，纯设计。
  注意：**无证据不等于错**——0003纪律允许新设计以0.x起步，
  但它必须被认出来，不能被当成"行业如此"。

一条前置说明：本仓十六页规范里**大半是内部蒸馏**，
它们的证据是两个创始消费方仓里的实测代码。这类页的"正本"天然在仓外，
本仓只留指针（多数带文件路径与行号）。**这是合规的**，
本页不因"正本不在本仓"就判薄；只有当指针含糊到无法复核时才判。

## 三、载重引用抽验（核了什么，核到了没有）

挑的是"这一句如果不成立，那一节就塌"的断言。逐条给原文与结论。

### 3.1 核实属实（六条）

**（1）spec/13规则1的稀疏/稠密分发**。规范括号写"稀疏/稠密按硬件分发"。
MJX文档原文：默认`auto`设定下"sparse if `nv >= 60`（60或更多自由度），
或MJX-JAX检测到TPU作为默认后端，否则dense"，
并给了理由"现代TPU有针对稀疏矩阵快速运算的专用硬件，而GPU倾向于稠密矩阵更快"。
**属实，且原文比规范写得更具体**（规范只说"按硬件"，原文给了阈值与判据）。

**（2）spec/15第五节preCICE那一格**。规范写"各域黑盒求解器，按耦合窗口交换边界数据；
弱（交错显式）或强（隐式子迭代＋拟牛顿加速）；preCICE（流固耦合起家）"。
preCICE官方文献指南：自述为"coupling library"、"partitioned simulation coupling"、
"black-box"集成、支持"explicit and implicit coupling"、隐式档有"quasi-Newton acceleration"、
根在"fluid-structure interaction"、同时讲"surface coupling"与"volume coupling"。
**逐项属实，转述准确。这是spec/15唯一一条经核完全站得住的外部锚点。**

**（3）research/01的MuJoCo网格凸包**（spec/11规则2据此写"mesh碰撞默认凸包，不声明就是暗坑"）。
MuJoCo文档原文："unlike mesh geoms which are convexified for collision purposes"。
**属实。**

**（4）research/05第四节的Drake性能门口径**（spec/13零之二与决策0018据此立"墙钟不进门"）。
Drake `multibody/benchmarking/README.md`原文："This program does not serve as a
performance regression test as it has no way to normalize for changes in hardware
or other environmental factors"，其定位是"a platform where performance can be
measured, code tweaked, and performance measured again"。
**属实，且原文给的理由（无法归一化硬件与环境）正是本仓0014"目标机器状态未知"的同一条**。

**（5）research/05第一节的PyElastica反面教材**。
`examples/run_all_examples.sh`实核：判据是`if python "$script_path" > /dev/null 2>&1`，
输出全部重定向到`/dev/null`，**无输出校验、无断言检查、无结果验证**，只看退出码。
**属实。**

**（6）COMSOL的AC/DC与RF分野**（research/08第二节要用，本页顺带核）。
AC/DC模块管"static and low-frequency electromagnetic fields"，
接口为Electrostatics／Electric Currents／Magnetostatics／Electromagnetics／
Electric Machinery／Electrical Circuits；full-wave归RF模块，
判据是"when propagation delays become important…appropriate for structures of
electrical size 1/100 and larger"，且两者有"overlapping range"。**属实。**

### 3.2 核实但与规范转述有出入（一条，重要）

**spec/13第二节规则1的MJX那句**，规范写：

> **单一物理定义，多后端执行**（MJX形制，官方文档核实：同一数据模型与算法，
> CPU/GPU/TPU无缝切换）。

MJX文档原文三句：

- "MJX-JAX is a re-implementation of MuJoCo that uses the **same algorithms** as
  the MuJoCo implementation"——**算法相同属实**；
- "MJX **deliberately diverges** from the MuJoCo API in a few places"，
  且"Some fields are **missing** from mjx.Model and mjx.Data"——
  **"同一数据模型"不成立**，它是有意分歧且有字段缺失；
- "MJX will **raise an exception** if asked to copy an mjModel to the device that
  references unsupported features"——**"无缝切换"不成立**，
  它是特性有缺口且遇不支持就失败关闭。

**结论**：这条载重引用**被转述得比来源强**。而最要紧的一点是：
**来源的真实形态比规范的转述更支持规范自己**。
spec/13规则3写着"等价性门硬性……任何后端上线前过同一套解析oracle＋跨后端对拍"，
规则5写着确定性要分级申报——MJX真实的样子（跨后端有特性缺口、遇不支持抛异常、
稀疏稠密按硬件换算法）**正是"多后端不是免费的"这个论点的证据**，
而"无缝切换"这个转述反而把它洗成了"这事很顺"。**转述削弱了它自己要立的规则。**

### 3.3 核实为不成立（一条）

**spec/15第五节把COMSOL对应到"单体（monolithic）"型**。规范表里那一格：

> **单体** | 跨域项进同一个矩阵一起解 | COMSOL预定义multiphysics interface | 最侵入

实核COMSOL文档：预定义耦合之外，"manual multiphysics couplings can be defined and
solved using **fully coupled or sequential** approaches"。
即**fully coupled（单体）与sequential（分区）是求解器层的选项，不是interface的属性**——
同一个预定义multiphysics interface既能单体解也能分区解。
**"预定义interface＝单体"这一步转述不成立。**

顺带一条：research/03第二节给COMSOL记的"三档（全自动预定义／手动＋预定义耦合节点／
自定义表达式）"，我核到了前两档（预定义 vs 手动），**第三档"自定义表达式"未核实**。

**后果**：spec/15三型里，**单体型今天没有一个站得住的行业实例**。
这不影响选用规则（"单体永远是最后选项"本来就是叫人别用它），
但它意味着那一格是空的，而表读起来像满的。

### 3.4 核不到／未核实（如实登记）

- **spec/10的四家同行"收敛出的同一形状"**（PyElastica/Chrono/SOFA/libuipc）——
  本轮未核。理由：不在用户点名的两处重点内，且要核它需要另开一轮调研
  （四家的场景装配API各是一片）。**列入补研清单第3条**。
- **spec/10第二节"MuJoCo mocap形制"、第三节"MuJoCo环形缓冲形制"、
  第六节"形状对齐Gymnasium"**——三条外部锚点，本轮未核，同上。
- **research/03第二节COMSOL的第三档"自定义表达式"**——未核实（见3.3）。
- **spec/13第四节"Metal无fp64"**——来自WDS design/09实测，属内部证据，
  本轮未跨仓复核（正本在消费方仓，本仓只有指针）。

## 四、两处已知薄弱的独立复核（不只信判断，核过再说）

### 之一：spec/13——薄在两处具名的地方

用户的判断是"整页只有一条外部锚点，确定性分级的行业依据没有正本调研"。**两条都属实**，
但复核之后我要把它说得更准，因为**"薄"的位置和用户说的不完全是同一处**。

**页末"参考"实测**：MuJoCo MJX官方文档、WDS AGENTS既有法条、其design/09、
design/24七之二、research/03。**除MJX外全部是内部来源。所以"唯一一条外部锚点"属实。**

**第一处薄（用户没点到的）**：那唯一一条锚点被转述得比来源强，见3.2。
**这一处比"锚点少"更值得修**——锚点少是密度问题，转述失真是准确性问题。

**第二处薄（用户点到的）**：规则5的确定性分级
（`bitwise`/`same_hw_deterministic`/`nondeterministic`）与第三节"驱动版本进run包"，
**合计三条规则零外部出处**，全页只有一句"行业在GPU原子加上栽的跟头"，
没说是谁、栽在哪。这恰好是全页最像"行业共识"、最容易被后人当成已核实的部分。

**但复核的结论不是"分级错了"——分级是对的，而且能找到逐级对得上的正本。**
NVIDIA cuBLAS文档的Results Reproducibility节给的正是这三级的判据：

| spec/13的等级 | cuBLAS原文 | 差异 |
|---|---|---|
| `same_hw_deterministic` | "All cuBLAS API routines **from a given toolkit version**, generate the same bit-wise results at every run when executed on GPUs with the **same architecture and the same number of SMs**" | 原文有**三个**限定：同架构、**同SM数**、**同toolkit版本**；规范只写了"同硬件同序" |
| `nondeterministic` | 对使用原子操作的备选实现，"the results are **not guaranteed** to be bit-wise reproducible **because atomics are used**" | 坐实了规范那句无出处的"GPU原子加" |
| （规范没有的一维） | "bit-wise reproducibility is **not guaranteed across toolkit versions**"；且多CUDA流并发时保证也失效 | 见下 |

**这里核出一条规范内部没连上的线**：cuBLAS明说逐位一致**还取决于toolkit版本**，
而spec/13第三节恰好要求`runtime_environment`记录驱动/工具链版本——
**第三节的义务正是规则5等级的成立条件，但两节之间没有一句话把它们连起来。**
`same_hw_deterministic`这个名字里只有"same_hw"，读的人不会知道换个CUDA版本它就不成立了。
补这条研的成本极低（一页官方文档），产出却不是加个脚注，而是**改规范内容**。

### 之二：spec/15——薄在三处，其中一处是转述错误

用户的判断是"耦合三型来自research/03第二节，那节只有preCICE与COMSOL两个锚点、
且是二手概述"。**属实，且我核出了它更具体的形状。**

**第一处薄：research/03第二节是全部六页调研里唯一没有抽验记录的一节。**
这是横向比出来的，不是印象：research/01写"载重引用抽验3/3属实"；
research/05逐条给了文件路径（`multibody/benchmarks/free_body/free_body.h`、
`data/testing/joints/`、`test/user/testdata/dzhanibekov.xml`……）；
research/06全部数字来自可复跑的`tools/bench.py`。
而research/03第二节的"来源"行写的是"COMSOL官方（comsol.com）、
preCICE（precice.org**系文献**）"——**"系文献"不指向任何具体文档**。
spec/15页末又写"外部（**经research/03核实**）"，
**这是一句转手声明：spec/15声称research/03核过，而research/03自己没有记录核过什么。**
证据链在这里断了一环，且断得很安静。

**第二处薄：COMSOL对应到单体那一格经核不成立**（见3.3）。
于是三型里的**单体**今天是空的。

**第三处薄：分区型只有preCICE一个锚点，而分区是规范推荐的第一升档目标。**
spec/15第五节的选用规则是"默认从单向链起步；**需要反馈才升分区**；单体永远是最后选项"——
即分区是三型里唯一**会被主动选中**的那一型（单向链是缺省、单体是禁区）。
**它的证据密度应当最高，实际最低（n=1）。**

**一条本轮顺手核到、比现有两个锚点都更有用的东西**：
COMSOL的Joule Heating and Thermal Expansion接口明写同一条链里两段的耦合方向不同——
"The thermal–electric coupling is **bidirectional**, with Joule heating and
temperature-dependent electrical properties, while the temperature coupling to the
Solid Mechanics interface is **unidirectional**"。
这是spec/15第五节"升型要有证据"条款的**第一个可引用的行业实例**：
同一条链，电-热段因为物性温度依赖而需要反馈，热-力段不需要。
今天那一页一个这样的实例都没有。详见research/08第五节。

### 之三：轴2的单位后缀集——不是"证据薄"，是"取样范围窄"

单列一类，因为它不该被判成薄，但也不该被漏掉。

spec/03轴2规则3（物理量跨边界必须带单位）的证据是两个创始消费方的实测，**充分**。
但`identity.py`的`BASE_UNIT_SUFFIXES`注释明写它是"两仓**实测在用**的单位后缀基础集"——
**它的取样总体是两个域（力学、光学），不是"物理量"**。
后果在电磁进来时立刻显形，且已实测（research/08第四节）：
电磁的七个基本单位后缀一个都不在集里（失败关闭，**这是对的**），
但`charge_c`会**静默通过**——因为`_c`已被摄氏度占用。
一个后缀集"已登记"不等于"语义唯一"，而轴2的门只查前者。

这不需要改轴（轴2是冻结轴，且规则本身没错），
但**它是"证据取样范围与将来用途不匹配"的一个标本**，值得单独记一条。

### 之四：30/120秒预算的依据（轻微，登记备查）

spec/07轴6规则1把30/120秒冻结为共同预算，理由写的是
"这组数两仓在**互不知情时各自选中**"。**这是n=2的巧合被当作收敛证据。**
research/05第四节查的是"性能门要不要进CI"（Drake/MuJoCo口径），
**不是"预算取多少秒"**——后者至今无外部对照。

判轻微的理由：规则1自己写着"预算只裁决开发吞吐，不裁决物理正确性"，
所以就算这组数取偏了，代价也只是开发节奏。**不进补研清单前三，登记备查。**

## 五、排序的补研清单

排序判据两条：**将来吃重程度**优先于**当下缺口大小**；
**会改规范内容**的优先于**只加脚注**的。

### 第1条：spec/15跨域耦合（最该补）

**为什么第一**：三条理由叠加。①用户点名的电磁扩展，第一件撞上的就是这一页；
②它的唯一来源是全部调研页里唯一无抽验记录的一节，且spec/15用一句转手声明
（"经research/03核实"）把这件事盖住了；③**已核出一处转述错误**——
其余各页的抽验全部属实，只有这一页核出了不成立的一条。
证据质量已经不是"密度不够"，是"有一格是错的"。

**补什么**（四件，按可核性排）：

1. **改COMSOL那一格**，按原文重写：预定义multiphysics interface是**耦合的声明方式**，
   而fully coupled（单体）与sequential（分区）是**求解器层的选项**，两者正交。
   这一改会让单体那一格暂时空出来——**空着比填错好**，
   或另找一手锚点（monolithic FSI文献）。
2. **给分区型补第二个锚点**。今天n=1，而它是三型里唯一会被主动选中的。
   候选：Elmer＋OpenFOAM的EOF-Library（开源分区耦合，MHD带自由面）、
   或COMSOL的sequential求解路径。
3. **把Joule heating那条链的方向性收进来**当"升型要有证据"的样板
   （电-热双向、热-力单向，理由是物性温度依赖，见research/08第五节）。
   这是那条款目前**唯一**可引用的行业实例。
4. **补一句"一条链可以混型"**。今天第五节的表是按型举例（一型一行），
   表达不了"同一条耦合链里不同段用不同型"。规则本身不用改
   （规则是对型说的，不是对链说的），但读的人会以为一条链只能一型。

### 第2条：spec/13确定性分级与驱动版本（第二该补）

**为什么第二**：补研成本最低、产出最实。一页cuBLAS官方文档就能把三条零出处的规则
（规则5三个等级＋第三节的版本记录义务）全部落地，而且**产出是改规范不是加脚注**：

- `same_hw_deterministic`要补两个限定（**同SM数**、**同toolkit/驱动版本**），
  今天这个名字漏掉了后者；
- 第三节"驱动版本进run包"从"轴3的自然延伸"（本仓自己的推理）
  升级为**有外部依据的必要条件**——cuBLAS明说跨toolkit版本不保证逐位一致，
  所以不记版本就没法声称等级；
- 顺带补上"多流并发保证失效"这一条，今天规范完全没有。

**同批做掉的一件**：按3.2改MJX那句转述。改法两条，需裁决（见第六节待裁1）。

### 第3条：spec/10内核接口（第三该补）

**为什么第三**：它是**外部锚点最多而正本一条都没有**的一页
（四家同行收敛五条＋MuJoCo mocap＋MuJoCo环形缓冲＋Gymnasium），
而且它正在往冻结走——决策0034刚把`Episode`从冻结前提里摘出去，
就是为了让这一页能冻。**冻结前补锚点比冻结后补便宜**：
冻结后每改一句要走决策记录＋版本跳变（轴1规则6）。

**补什么**：另立一页"场景装配与接口形制调研"，

（PyElastica的`finalize`、Chrono的系统容器、SOFA场景图、libuipc的Geometry/Constitution），
并核MuJoCo mocap与执行器时延两条。

## 六、待裁清单（本轨道只出调研正本，以下请裁）

**待裁1：spec/13规则1的MJX转述怎么改。** 两条路：
①**改转述贴合来源**——写成"同一套算法、多后端执行；后端间有特性缺口且遇不支持失败关闭
（MJX形制）"。推荐理由：来源的真实形态比原转述**更支持规范自己的规则3与规则5**，
改了之后那一页反而更硬。
②**降级**——把MJX从载重引用降为"形制启发"，规则1改由本仓自己的边界推理支撑
（"后端≠第二套物理实现"本来就是前端"不得重算物理"的算力版，这一步不需要外部背书）。
**倾向①**，但这是规范措辞，请裁。

**待裁2：spec/15第五节单体那一格怎么处理。** 经核COMSOL的预定义interface不等于单体。
两条路：①空着并写明"单体型本仓无一手锚点"；②另找一手锚点补上。
**倾向①**——理由是选用规则本来就是"单体永远是最后选项"，
一个没人该选的型没有实例并不损害规则，而填一个错的实例会让人以为那条路是被验证过的。

**待裁3：轴7规则1与电磁域主流基准族的冲突，登记在哪。**
轴7规则1（**已冻结**）："金标来自仓内解析oracle……**实测数据不作金标**"。
而电磁域最成体系的基准族TEAM问题（COMPUMAG发布）的定义就是
"each backed by a **real laboratory device, on which measurements can be made**"——
**电磁侧最主流的基准是实测型的**。
这条冲突今天不发生（无电磁域），但电磁真进来那天必须有结论。
**本页的立场是现在只登记、不改轴**（改冻结轴代价大，且今天没有触发）。
要裁的只是登记位置：留在research/08第六节，还是现在就进一条决策记录。
**倾向前者**——按0001"不为想象中的消费方预支"，今天没有电磁消费方。

**待裁4：单位后缀集要不要加"域"维度。** 今天`_c`是摄氏度，而库仑的SI符号也是C；
`charge_c`能过轴2的门但含义错（实测见research/08第四节）。
两条路：①给后缀集加域维度（改`identity.py`，而它服务轴2这条冻结轴）；
②靠命名约定绕开（`charge_coulomb`这类不缩写的写法）。
**倾向②**——它不动冻结轴，代价只是命名啰嗦；
但这件事要在第一条电磁材料记录出生**之前**定，否则就是既成事实。
