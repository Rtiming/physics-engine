# 什么才算真实的完成（2026-08-05）

用户问："**怎么样才是最真实的、最符合现实规律的完成？**"并说这一波之后收尾。

本页正面回答。**结论不好听，但把它写在这里比写在将来的汇报里诚实。**

## 一、两个分母讲两个故事，而其中一个在恭维我们

决策0040 定的成功分母是 research/05 的 C 档 13 条同行案例，**今天 7/13**。

> **订正（决策0049第十节）**：**真值是 6/13**，缺 7 条。7 这个数继承自 0040 汇总行（该行比 0040 自己的表多 1），0046 打钩时未回表重数。**本页论证不受影响——分子更小，第一节这个结论只会更强。**
听起来"过半了"。

但用户在 0040 之后给出了**六个真实场景**（plans/04）。按那个分母：

| 场景 | 今天能算什么 | 真实结论 |
|---|---|---|
| ①超导带绕一圈的电流分布 | Norris **直薄带**自场闭式 | **算不了**。绕成一匝几何就变了，且无电流自由度 |
| ②多线圈互感与电容 | **理想细丝圆环**的互感闭式 | **部分**。真线圈有截面、有多匝；**电容零** |
| ③不规则体落漏斗 | 刚体自由飞行 | **算不了**。无接触 |
| ④光学散射/干涉/衍射 | 双光束干涉闭式 | **部分**。散射零、一般衍射零 |
| ⑤平面带材绕十几匝 | — | **算不了** |
| ⑥完整放线链路 | 装配成立、接触对声明出来 | **算不了**。一次接触都不算 |

**诚实的说法：六个场景里两个有理想化的部分答案，四个一点都算不了。
端到端能跑通的是零。**

**7/13 与 0/6 是同一个仓的两个真相**，而前者是用别人的题打的分。
0040 选同行案例当分母的理由（"用别人的题比自己出题自己打分诚实"）当时是对的，
**但那是在不知道引擎要用来算什么的时候定的**。现在知道了。

## 二、这一波六条轨道，只有一条真正穿过引擎

这是比上一节更硬的一刀：

| 轨道 | 穿过哪些层 | 算不算锻炼了引擎 |
|---|---|---|
| **P 点载荷/Euler屈曲** | `state`→`energies`→`solve` | **算**。唯一一条走完整条路的 |
| R 刚体自由飞行 | `state`→`integrate` | **半条**。不碰能量装配与求解器 |
| E 互感 · N Norris · O 干涉 | 都不碰 | **不算**。是仓内的闭式计算器 |
| S 场景装配 | 不碰物理 | 不算（它是前置，不是物理） |

**六条里一条半真正锻炼了引擎的机械。** 其余四条半是"被严格验证过的公式"。

它们不是没价值——判据强度是第1档，容差是算出来的，必红门逐条实测过，
而且**抓到了两个真缺陷**（`materials.py` 的长度制漏项、我们自己 0029 那条只对一半）。
但**它们证明的是"这个公式我们抄对了"，不是"这个引擎算得对"**。

## 三、这是这一波最大的风险，必须写下来

六条轨道、六个绿灯、905条测试、19个案例、三个物理域——**这一波非常顺**。

**正因为顺，风险才在这里**：如果下一波重复同一个模式，
我们会得到一个**被严格验证的公式库**，而且它**看起来会非常像一个引擎**——
测试数、案例数、域数、每条容差都有理由、每道门都验过红。

**纪律的成熟会掩盖物理的单薄。**

本仓验证纪律的强度在同行里是罕见的（research/12 实测：NVIDIA 237个样例里
带定量容差的只有1个，SOFA 是 474:1）。**但验证纪律不是物理能力。**
把前者当成后者，是这个仓最可能犯的错，因为它是从治理层长出来的。

## 四、"符合现实规律"缺的是什么——四条结构性的

用户第一句定位是"**我们是三维的模型，也是带有厚度的那种**"。
现实里的物体有体积、会接触、有历史、多个物理同时发生。**这四样我们都没有。**

| 缺什么 | 为什么它是结构性的 | 阻塞哪些场景 |
|---|---|---|
| **体积与厚度** | 今天一切都是中心线或闭式。**截面上没有任何自由度可放**——应力、电流、温度都无处安放 | ①⑤，以及"三维带厚度"这条定位本身 |
| **接触** | 唯一一条**一次解锁三个场景**的。且它逼着解 0033 | ③⑤⑥ |
| **耦合** | `src/physics_engine/couplings/` **目录根本不存在**（spec/15 只留了模块位）。而场景①**本质就是耦合**：应变改变Jc、电流产生洛伦兹力 | ①⑤ |
| **历史** | 0033 未裁；Track-R 实测确认 `StateLayout` 装不下"数量随构型变"的量，**且语义障碍比机制障碍更硬**——跨步守恒判据会在布局变的那一步全废 | 摩擦、磁滞、塑性 |

**这四条不是"再加几个案例"能补的。** 加案例只会让第一节那两个分母
差得更远：同行阶梯涨，用户场景不动。

## 五、核对时发现的一个门的洞（本页新增，非代理发现）

`tests/perf/test_budgets.py` 的源码字节门用的是 `glob("*.py")`——**只扫顶层**。

实测：`optics/` 52097 字节、`electromagnetics/` 63147 字节，
合计 **115244 字节从未被这道门看见**，占源码树 **24%**。

**而按 spec/15，新物理域就是子包。** 所以：
**这条绊线的洞，恰好开在仓被设计成要生长的地方。**

0041 预抬上限时写的自我约束是"收口复测，若实际增量远小于预支额度就调回"。
复测结果反而相反——**全树 475269 字节，×1.4 = 665376，已经超过 655360 的现行上限**。
预支没有过度，**但门看不见的那 24% 让"预支是否过度"这个问题本身失去了意义**。

修法：门改成 `rglob`，并把台账的 `measured` 口径与门统一
（Track-P 报告的口径不一致，正是同一个洞的另一面）。

## 六、那么"真实的完成"是什么

**不是"做完了"，是把状态说清楚到别人（包括将来的我们）不会误判。**

具体六件，全部可执行：

1. **发 0.5.0**，把 164 条未发变更收成一个可引用的版本；
2. **成功分母改成两条并列**：同行阶梯（7/13，验"算得对不对"）
   与**用户场景阶梯（0/6 端到端，验"算不算得了我们要算的"）**。
   后者是主，前者是从。**理由：0040 定分母时还不知道引擎要用来算什么。**
3. **README 的能力边界写成可证伪的**：不写"实验档"三个字了事，
   写"你的六个场景里，哪个能算、算到什么程度、缺哪一块"；
4. **修第五节那个门的洞**，并把台账口径统一；
5. **裁 spec/14 规则1**（实测已证明不可满足）；
6. **把第四节四条结构性缺口立成正本**——它们才是"能不能变成真引擎"的判据，
   而不是案例计数。

## 七、下一次该做什么——一条，不是六条

**接触。** 三条理由：

1. **唯一一条一次解锁三个场景的**（③⑤⑥）；
2. **它逼着解 0033**——那条挂了很久的状态布局问题，
   Track-R 已经把三种选法和各自的语义后果摆清楚了，**只差一个真实需求来裁**；
3. **它是"公式库 vs 引擎"这条分界线上的东西**——接触没有闭式解可抄，
   必须真的求解。**做成了，第二节那张表才会变。**

**这一波是广度，下一次必须是深度。** 而且不该再是六条并行——
接触一条就够，因为它前置着别的东西，且它的形制一旦定错，后面全要返工。
