# 缺口清册（2026-08-05立，正本）

**本页是全仓缺口的唯一汇总入口。**

立它的理由是实测出来的：欠账散在**13份决策记录 + 5个源码文件**里，
形态是"登记在此""触发条件：……"。全仓共**53处触发条件、44处待裁、16处已知缺口**，
**而在本页之前没有任何一个地方能回答"我们一共欠了多少"**。

散着的欠账有一个共同结局：**它们各自都写得很清楚，合起来没人看得见**。
2026-08-05连着抓到的三个错（冲突标记进主干、pre-commit钩子根本跑不通、
从分母多算一条）**全都属于"以为已经核对过"的那一类**——
没有汇总，就没有"核对一遍"这个动作可做。

本页配了一道防过期的门：`tools/check_gap_register.py`（第七节）。

## 七、这份清册自己怎么不过期

**一份会过期的缺口清册比没有更坏**——它会让人以为已经数过了。

`tools/check_gap_register.py`守两条：

1. **每一份写了"触发条件"的决策记录，必须在本页第六节被引用。**
   新决策记录登记了欠账却没进本页，**当场红**；
2. **本页引用的决策记录必须真的存在。**

这道门**不判断内容对不对**——它判断的是"有没有被汇总"。
内容的正确性靠人读，**而人只有在东西被汇总到一页上时才读得动**。

**它挡不住的**：源码里的触发条件（第六节列了5个文件，但门只扫决策记录）。
理由是源码里的登记形态自由，硬扫会误红。**登记在此**，
触发条件：源码里的触发条件超过10处时给它也上门。
