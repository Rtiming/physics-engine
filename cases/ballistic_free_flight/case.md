# ballistic_free_flight 弹道自由飞行：常加速度下三个积分器的误差常数

`case/ballistic_free_flight`。B档，spec/12第九节判据1与判据2。
**这是引擎第一次推进物理状态所对应的案例**——在它之前引擎只有声明、校验、溯源与几何量。

## 一、物理/几何设定

一维质点，常加速度（重力）自由飞行，无阻尼、无接触、无约束。

| 量 | 值 |
|---|---|
| 加速度 | −9806.65 mm/s²（标准重力） |
| 初位置 | 0.0 mm |
| 初速度 | +1000.0 mm/s |
| 总时长 | 1.0 s |
| 步长阶梯 | 1.0e-3 / 5.0e-4 / 2.5e-4 s |
| 行程量级 | 约4.9e3 mm |

精确解 `x(T) = x0 + v0·T + a·T²/2`。量级选得让行程落在米级——太小会让
"误差恰为a·T·h/2"被浮点噪声淹没。

## 二、参考解出处

闭式，推导在`generate_oracle.py`的docstring里，一行可独立核对：
设步数N、`N·h = T`。半隐式先更新v再推x，`x_N = x0 + Σ_{n=1..N}(v0+n·a·h)·h`，
减精确解得 **+a·T·h/2**；显式用旧v推x，求和从0到N−1，得 **−a·T·h/2**。
velocity Verlet的 `x + v·h + a·h²/2` 对常加速度**就是精确解**，误差只剩浮点噪声。

生成器与被验内核不共享代码路径：生成器只算闭式常数，不调`integrate`。

## 三、判据表

| 量 | rel/abs | 理由 |
|---|---|---|
| `error_over_predicted`（半隐式=+1，显式=−1） | abs 1e-8 | 误差常数由闭式给出，被验内核只做加减乘；实测比值1±5e-11，判据留六个数量级余量。**必须带符号** |
| `relative_error`（Verlet） | abs 1e-12 | 对常加速度精确，剩下的只是浮点噪声（实测2.4e-14/1.5e-14/2.9e-14），留约两个量级余量 |
| `exact_position_mm` | rel 1e-15 | 解析终点位置，只受双精度舍入影响 |

**这张表最要紧的一行是第一行的"必须带符号"**：显式与半隐式的误差**同幅反号**
（实测 +1.000000000009784 对 −0.999999999990215），按`abs()`写的判据分不开这两个积分器。

## 四、已知失效清单

- **不覆盖速度相关的力**。有阻尼时velocity Verlet不再是二阶，本案例的"精确"结论不成立。
- **不覆盖多自由度耦合**。一维质点，加速度与状态无关；耦合系统的误差常数不是这个形式。
- **步长阶梯只有三档且都在渐近区内**。它证明的是误差常数，不是收敛阶——收敛阶在`harmonic_oscillator`。
- 未在Windows/Linux复核。纯加减乘的双精度运算跨平台预期逐位相同，但没测过就是没测过。

## 五、档位与负载级

B档（需要新增`integrate.py`），**interactive**（<1s）。实测：9条oracle全跑0.02s。

## 六、本案例不是什么

- **不是积分器选型依据**。它只说误差常数对不对，不说哪个积分器该用于生产——
  三个积分器的`production_ready`今天全是`False`。
- **不是性能基准**。墙钟不进门（决策0018）。
- **不验证`geometry.py`或质量属性**。加速度是直接给的，没有经过力/质量这一环。
- **逐字节对拍门抓的是"求值方式分叉"，不是"公式写错"**。实测两条破法：
  加速档改用`float32`→**红**（真的换了数学）；把`(a+b)+c`改成`a+(b+c)`→**不红**，
  因为改的是**共享的公式源**、两个后端一起变了。这不是门的漏洞而是
  "一份公式源"设计的直接结果——公式错由判据表那三行抓，
  后端分叉由这道门抓，两者各管一段，都不越权。
